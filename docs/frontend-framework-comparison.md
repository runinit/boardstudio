# Rust frontend framework comparison

Research checked 2026-09-25 against the official framework documentation. This
is a comparison for planning; it does not select a framework or authorize a UI
migration. Current frontend ownership and the no-cutover boundary are recorded
in [current architecture and validation](architecture.md) and the
[repository cleanup inventory](repository-cleanup.md).

## App context

The `app` package is a React 18.3.1 and Vite 6.3.5 browser application. Vite
currently handles multiple HTML entries, TSX, module workers, and asset loading
([package.json](../app/package.json), [vite.config.ts](../app/vite.config.ts)).
The UI calls the core, case, and export workers through
[`CoreClient`](../app/src/CoreClient.ts),
[`CaseClient`](../app/src/CaseClient.ts), and
[`ExportClient`](../app/src/ExportClient.ts). The app also registers its
service worker from [`main.tsx`](../app/src/main.tsx), with the service-worker
script generated by [`write-sw.mjs`](../app/scripts/write-sw.mjs).

The near-term fit is therefore a **client-rendered, static browser app** that
can keep its existing worker clients and Rust core boundary while UI work is
evaluated. Server rendering and native desktop/mobile output are not current
requirements. The previous research already proposed Leptos CSR with Trunk as
one possibility; this comparison checks that against Yew and Dioxus.

## Comparison

| Concern | Yew | Leptos | Dioxus Web |
| --- | --- | --- | --- |
| **Docs/version reviewed** | Official docs identify version 0.23. | The book is rolling documentation; docs.rs surfaced Leptos 0.8.20. | The requested web guide is on the stable 0.7 docs; the release page lists 0.7.10 and a 0.8 alpha. |
| **Static and offline deployment** | CSR with Trunk produces a `dist` directory with HTML, JS glue, and WASM. Static hosting is suitable; router fallback and WASM MIME configuration need to be correct. | CSR with Trunk explicitly publishes the generated `dist` directory to static hosting. | `dx bundle --web` emits a web bundle with HTML, assets, JS glue, and WASM. Its web guide also covers full-stack server deployment; use the client-only path for this app. |
| **Vite and worker boundaries** | Adds a Rust/WASM build alongside Vite. The current TypeScript clients can remain as the bridge while the UI moves in slices. | Trunk is a separate build path; combining its output with the existing Vite entries and service-worker asset manifest needs a deliberate integration step. Keep the current worker clients initially. | The `dx` CLI adds another build path. Keep worker messages and TypeScript clients stable initially; validate asset staging and service-worker precaching against `dx` output. |
| **Browser APIs** | Uses the WebAssembly browser ecosystem (`wasm-bindgen`, `web-sys` and related crates). | `wasm-bindgen` and `web-sys` are explicit escape hatches; JavaScript libraries can be called, with care around shared DOM ownership. | Uses `wasm-bindgen`/`web-sys`; Dioxus also documents `use_eval` for JavaScript interop. |
| **Accessibility** | Renders web DOM through Yew's HTML macro. | Renders web DOM through Leptos views. | Renders web DOM through Dioxus RSX. |
| **Testing** | Has component snapshot support and `wasm-bindgen-test`; its 0.23 docs say component testing ergonomics remain a work in progress. | The book shows ordinary Rust tests, browser tests with `wasm-bindgen-test`, and Playwright E2E. | The 0.7 guide documents RSX snapshot-style checks and Playwright E2E; it notes there is not a full hook-testing library. |
| **Migration shape** | JSX-like `html!` syntax may feel familiar to React authors, but components, state, routing, and build integration still need rewriting. | Fine-grained reactive views and signals offer a different state/rendering model; adopting CSR avoids adding a server requirement. | `rsx!` and signals provide a Rust component model; cross-platform support is optional value, with additional platform/tooling scope beyond this browser-only need. |

### Static hosting is not the same as offline support

All three can target browser WebAssembly and produce static web assets. That is
a good starting point for offline delivery, but none of the framework choices
alone preserves offline behavior. The service worker must continue to cache the
HTML, JavaScript glue, WASM, and app assets correctly, including update and
subpath behavior. The browser worker protocol and generated asset paths also
need to remain aligned. These are integration questions for a later prototype,
not properties established by framework documentation.

### Accessibility and test coverage

The framework docs do not establish an accessibility winner for this app. All
three render browser DOM, so semantic elements, labels, focus handling,
keyboard behavior, and announcements still need to be implemented and checked
in the actual workbench interactions. This is an assessment from their browser
rendering models, not a claim that the frameworks provide identical tooling.

Keep the existing Playwright suite as the end-to-end product check during any
future UI experiment. Rust tests can cover extracted logic, and framework or
WASM tests can exercise component behavior, but neither replaces browser
checks for focus, keyboard flows, worker integration, offline reload, or the
multiple Vite/Trunk/`dx` asset paths.

## Maturity and uncertainty

The docs reviewed show Yew 0.23; Leptos 0.8.20 on docs.rs, with a 0.9
pre-release in its release history; and Dioxus 0.7.10 stable, with 0.8 in
alpha. Yew's official testing page describes component testing as work in
progress. Leptos has a broad book covering CSR, server rendering, browser APIs,
and tests. Dioxus documents web, desktop, and mobile targets, which gives it
the broadest platform scope of these candidates. These are useful ecosystem
signals, not a reliable ranking of project health or community size. Their
docs cover the browser path, but integration evidence for this app is absent:
no framework has been built into the current Vite setup, tested against the
worker clients, or measured for download size, startup, or offline reliability.
Pinning exact crate and CLI versions would be necessary for a prototype.

The main cost is not translating markup syntax. A meaningful migration would
replace React component state and effects, custom controls, routing, and
test/build wiring while preserving the worker contracts, browser storage,
service-worker behavior, and existing user interactions. A hybrid can keep
React and Rust UI in separate DOM roots for a while, but they must not both
manage the same subtree; this is an architectural constraint to verify during
integration.

## Provisional recommendation

Use **Leptos CSR as the first prototype candidate**, not as a framework choice.
It extends the earlier migration note, has a clearly documented Trunk-to-static
deployment path, and documents direct browser API interop. Yew remains a useful
comparison for its focused browser target and JSX-like markup. Dioxus is worth
including if desktop or mobile reuse becomes a real requirement, but that
cross-platform scope does not currently reduce the web migration work.

Before selecting anything, compare the same small workbench slice in all three
frameworks: one inspector edit, one keyboard-accessible control, and one call
through the existing core worker. Record the build/output integration, test
setup, offline reload behavior, and measured startup/download impact. No such
prototype or code migration is part of this research milestone.
