# Adopting a shadcn-style component system in BoardStudio

**Research checked:** 2026-10-11
**Question:** How can BoardStudio get the component-library workflow and visual language the user likes in shadcn/ui while remaining a Dioxus/Rust application?

## Recommendation

Adopt DioxusLabs' **first-party Dioxus Components** as the basis for a shadcn-style BoardStudio component library: reusable visual controls and reusable keyboard/accessibility behavior, both owned by BoardStudio. Adapt a small set of copied components to existing Tailwind 4.1.5 aliases and keep product actions with their existing owners. The first pilot should include Button/Toggle on real Layout and Case consumers plus keyboard-rich behavior for Layout's existing selection menu. This is not a stylesheet-only imitation, package install, or frontend rewrite. The upstream source is not shown to be drop-in for BoardStudio styles, callbacks, or interaction contracts, so compatibility must be established in the pilot.

This path keeps the existing Rust/Dioxus presentation and operation ownership while giving the team a real component catalog and repeatable style surface. It preserves BoardStudio's current tokens rather than installing shadcn's color system wholesale. It also avoids migrating the page runtime to React merely to consume React/TypeScript components.

## What “use shadcn” means here

The current shadcn docs describe an open-code and distribution workflow: component source is copied into the application, customized locally, and kept in the app's control; the CLI and registry distribute code rather than requiring the app to treat a package as an opaque component library. [shadcn introduction](https://ui.shadcn.com/docs) That workflow is portable as a product and maintenance idea. The exact React component source and APIs are not portable: the current official implementation offers both Radix and Base UI backends, with Base UI now the default for new projects. [shadcn Base UI changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)

The visual approach is more portable than component behavior. BoardStudio can reuse the principle of composable variants, semantic state, focused defaults, and open code, but needs to map those choices to its own `--wb-*` variables and current UI contracts. shadcn's Tailwind v4 documentation describes its React 19/Tailwind v4 setup; it does not establish that its TSX components run in Dioxus. [shadcn Tailwind v4 guide](https://ui.shadcn.com/docs/tailwind-v4)

## BoardStudio constraints that shape the choice

- The web app and shared UI crates pin Dioxus to `=0.7.10`; the app's browser UI is compiled through Dioxus to WebAssembly. The repository's Tailwind input uses v4.1.5, imports theme and utilities only, omits Preflight, and already maps colors, fonts, type sizes, and motion aliases in `@theme inline`. Those are project facts from `web/Cargo.toml`, `web/crates/ui-shared/Cargo.toml`, and `web/tailwind.css`; the official [Dioxus 0.7 web guide](https://dioxuslabs.com/learn/0.7/guides/platforms/web/) documents the Rust/WASM web model.
- Reuse existing BoardStudio theme aliases. Do not replace them with shadcn's default `--background`, `--primary`, `--muted`, `--ring` palette or introduce a parallel semantic token system. The aliases and Tailwind input already exist; migration work should be concentrated on component class/style mapping and explicit cascade behavior.
- Legacy component CSS is largely unlayered while Tailwind emits utilities in layers. A component's copied class list may not override the older selector for the same property. Each pilot must identify and deliberately migrate or override only its competing selector; no blanket CSS conversion or Preflight import belongs in this adoption.
- Components may own reusable presentation and local interaction mechanics, but must not own BoardStudio selection, document edits, undo, edit admission, precision parsing, or generation readiness. These remain with the existing Layout, Case, and operation owners.

### Dioxus-native foundation evidence and limits

DioxusLabs describes [Dioxus Components](https://github.com/DioxusLabs/dioxus-components) as a shadcn-style Dioxus component library, with unstyled `dioxus-primitives` and styled preview components. The README's workflow uses `dx components add` to copy source into an app and link its `dx-components.css`; it instructs contributors to follow WAI-ARIA practices for new primitive behavior and to test behavior with Playwright. Its gallery has keyboard-interactive previews for components including button, toggle, toggle group, popover, dialog, and select. [official gallery](https://dioxuslabs.github.io/dioxus-components/)

The official workspace manifest currently declares Dioxus `0.7.8` (caret requirement) and the primitive crate is version `0.0.1`, MIT OR Apache-2.0, with a default `router` feature. [workspace manifest](https://github.com/DioxusLabs/dioxus-components/blob/main/Cargo.toml), [primitives manifest](https://github.com/DioxusLabs/dioxus-components/blob/main/primitives/Cargo.toml) BoardStudio pins Dioxus exactly to 0.7.10, so compatibility appears plausible within the 0.7 line but must be checked in this actual workspace: feature unification, default router activation, web/WASM dependencies, generated stylesheet integration, and license provenance have not been built or reviewed here. The official Button source uses Dioxus CSS-module styling and the upstream attributes helper; its visual variables are not automatically BoardStudio Tailwind class aliases. [official component repository](https://github.com/DioxusLabs/dioxus-components) So the copied source's interaction/accessibility implementation can be a foundation while its CSS layer is adapted to BoardStudio's tokens. The official repository recommends a separate unstyled primitive layer for behavior/accessibility and a styled layer for design, but the source checked does not establish direct compatibility with BoardStudio's existing controls.

### Community port evidence and limits

The community project [`yuxuetr/dioxus-ui`](https://github.com/yuxuetr/dioxus-ui) states that it provides headless behavior/accessibility primitives, Tailwind-styled components, source-copy and Cargo workflows, and 82 components. Its current workspace manifest is 0.6.6, MIT, Rust 1.88+, and Dioxus 0.7; its styled crate uses per-component Cargo features. [README](https://github.com/yuxuetr/dioxus-ui), [workspace manifest](https://github.com/yuxuetr/dioxus-ui/blob/main/Cargo.toml), [styled crate manifest](https://github.com/yuxuetr/dioxus-ui/blob/main/crates/dioxus-shadcn/Cargo.toml)

That is a concrete alternative worth comparing, not proof of production readiness. The upstream README marks the API pre-1.0 and explains its compatibility policy; page-script-driven components may also require app-side `serde`, `serde_json`, and `wasm-bindgen` setup, and Tailwind must scan the component source. [upstream README: compatibility and generated CSS setup](https://github.com/yuxuetr/dioxus-ui) The repo contains explicit web/desktop verification examples and a release checklist, which are useful maintenance signals, but this research did not run its checks or verify its browser behavior. [repo verification examples and release checklist](https://github.com/yuxuetr/dioxus-ui/tree/main/examples)

## Proposed staged path

The user selected the first-party Dioxus Components route and explicitly approved exported shared controls on 2026-10-11: “you are free to add exported shared controsls, this is required for the UI refresh.” The accepted CSS unit is captured at `4aeb78ef`; root still records the exact pilot path lease and schedules compatibility builds and acceptance. Community and React ports are alternatives only and are not the recommendation.

### Stage 0 — compatibility spike (small; no tracked dependency/API change)

The pinned upstream revision inspected is `9a758255ea26e2b20c8cecf4c1c946feb9e71da7` (`DioxusLabs/dioxus-components`, observed main head on 2026-10-11). The primitive manifest declares `dioxus-primitives` 0.0.1, `MIT OR Apache-2.0`, default feature `router`, and `web = ["time/wasm-bindgen"]`. Proposal for the spike: in a disposable, untracked scratch crate, test this exact Git revision with `default-features = false` and `features = ["web"]` against BoardStudio's exact Dioxus `=0.7.10`; record resolved features, wasm compile result, generated JS requirements, and copied-source licenses. Do not add the dependency or expose an API during this spike. `dx components --help` was checked locally and exposes `add`, `remove`, `update`, `list`, `clean`, and `schema`; no command was run that adds or lists components. Actual dependency resolution, wasm compilation, generated CSS and browser behavior remain unverified.

**Effort:** small. **Risk:** low for the isolated spike; a failed compatibility check stops the proposal before tracked changes.

### Concrete shared-controls pilot — Layout first (medium)

The first tracked slice would add `web/crates/ui-shared/src/controls.rs`, export it through `web/crates/ui-shared/src/lib.rs`, and add a direct target-wasm dependency in `web/crates/ui-shared/Cargo.toml` on `dioxus-primitives` at the exact revision above with `default-features = false` and `features = ["web"]`; `Cargo.lock` would record resolution. The workspace root manifest does not need a dependency entry based on the current crate manifest layout. Do not change `web/tailwind.css` unless the pilot demonstrates a specific source-scan or generated-style need. Add a compact provenance note for the copied/adapted upstream pieces, their revision and license. The styled upstream preview `Button` uses a CSS module, so it is not the Tailwind wrapper to copy verbatim: build a small BoardStudio-styled native button around Dioxus markup, and use the upstream primitive for controlled Toggle and Popover behavior.

Proposed shared API is intentionally small: `BoardButton` takes a finite BoardStudio variant and density, native `disabled`, optional `onclick`, and children; `BoardToggle` takes caller-controlled `pressed` and `disabled`, an `on_pressed_change` callback, and children; `BoardPopover` takes controlled `open`/`on_open_change` and composes the upstream trigger/content primitives. Its exact Rust prop types should mirror the pinned primitive (`ReadSignal<Option<bool>>`, `ReadSignal<bool>`, `Callback<bool>`, and Dioxus event handlers) once the compatibility spike confirms they compile. Components render ordinary elements with caller-controlled content/styles; consumers retain product state and callbacks.

Map appearance to the aliases already in `web/tailwind.css`; do not import a new theme or Preflight. Limit style variants to the states and density needed by these consumers. Resolve only the specific competing legacy unlayered selectors that affect pilot styles.

**Layout first consumer:** `web/crates/layout/src/objects/layout_toolbar.rs::LayoutSelectMenu` (currently around lines 649–718) owns the open menu state and `on_selection_kind`. Keep its buttons as a `role="group"` of pressed buttons. The upstream Popover is not a drop-in menu: pinned `PopoverContent` renders `role="dialog"` and `aria-modal` when modal, while `PopoverTrigger` is a native button without an `aria-expanded` relationship. Configure non-modal behavior and explicitly preserve the existing trigger's `aria-controls`/`aria-expanded` and content's group/label semantics. The primitive supplies controlled open changes, Escape and outside-dismiss listeners; source inspection did not establish focus restoration or menu-item arrow-key navigation. Keep Layout's existing focus/close policy and validate those behaviors instead of claiming the primitive provides them.

**Case second consumer:** `web/crates/case/src/case_assembly_layers.rs::CaseLayerButton` and `ComponentLayerButton` (around lines 230–343) can consume the same button/toggle visuals after Layout passes. Keep selection and visibility as separate owner callbacks. Preserve selected/visible `aria-pressed`; selection remains disabled when not selectable or unavailable, and visibility remains disabled when unavailable. Component rows stay disabled for loading/missing models. No numeric field, transform inspector, or E-owned matrix/runtime path is in this pilot.

### Acceptance gates for the pilot

- First, the isolated compatibility spike must resolve the pinned dependency with Dioxus `=0.7.10` and compile the wasm target with the proposed `web` feature and no default `router` feature.
- After compatibility succeeds and the path lease is recorded, typecheck/build the actual web target and browser-verify the Layout pilot. Check keyboard trigger activation, Tab/focus-visible behavior, Escape and outside dismissal, focus returning to the trigger, and preservation of the existing selection group semantics. Verify the caller still owns open state, each option calls the same selection callback, and selection closes the menu without changing its existing action/undo result.
- In the Case follow-on, verify selection and visibility invoke only their respective callbacks, unavailable/loading/missing rows remain disabled and uninvokable, and available rows retain their pressed state and existing undo behavior. Add behavior regression tests only for new or changed contracts (keyboard/dismissal/focus or availability/callback semantics), not tests that mirror styling.
- Inspect computed styles/generated CSS to confirm existing BoardStudio aliases win for migrated properties and legacy unlayered rules do not silently override the pilot.

**Effort:** medium. **Risk:** medium: this adds a public shared API and overlay interaction while the primitive crate is 0.0.1; passing the spike and browser gates is required before broader reuse.

## Maintenance and migration rules

1. **Pin every imported source.** Record upstream repository, exact commit/tag, license file and copied paths in the component header or a compact source manifest. For a source-copy route, compare the local copy against that pinned upstream version periodically; a copied file does not receive updates automatically. For a Cargo route, exact-pin the package and lock resolution, document its update cadence, and check license/dependency changes before upgrades.
2. **Keep BoardStudio tokens authoritative.** Map candidate component roles to current color, type, spacing, radius, and motion aliases. Reconcile the candidate semantic names to local tokens in a small adapter stylesheet or component-level style table; do not wholesale change application surfaces. Tailwind 4.1.5 is the project's compiler and remains pinned; current shadcn docs now use both Base UI and Radix variants and may show newer syntax.
3. **Preserve semantic contracts.** Components may render HTML semantics and local focus/keyboard mechanics. They do not decide which layout item is selected, whether a layer is available, whether a precise dimension is accepted, whether an edit enters undo, or whether geometry is ready.
4. **Migration is by consumer, not by catalog.** Inventory only Button/Toggle/Popover uses needed by the selected Layout and Case pilots. Keep existing consumers until each one has behavior and browser evidence. Do not convert numeric inputs or every toolbar/menu just because the candidate offers analogous components.
5. **Maintain an evidence ledger.** For each adopted primitive record source revision, license, required dependencies/features, generated/required CSS, covered keyboard states and gaps, BoardStudio overrides, owners/callbacks, tests, and next update review. Upstream accessibility claims are a starting point; they do not certify BoardStudio's composition or styling.

## Decision points before implementation

The implementation handoff should name the pinned Dioxus Components revision and extracted files, confirm the Popover's fit for the existing Layout menu keyboard/focus contract, and preserve distinct Layout and Case owner callbacks and availability semantics. These are source-verification tasks, not open library-choice questions.

Exported shared controls are explicitly user-approved; do not request that approval again. No dependency, source copy, or runtime was installed during research. Exact dependency resolution and interface compatibility remain pilot verification tasks. Rough effort is relative scope, not an ETA.

## Limitations

This report used current official docs and upstream source/manifest files, plus the project manifests and design files listed above. Upstream `main` branches can move after this check; record a commit SHA before any future compatibility spike or source copy. No BoardStudio dependency resolution, build, browser validation, accessibility audit, or adoption was performed. The candidate repositories' documentation and automated tests do not prove that their components satisfy BoardStudio's actual workflows, visual design, browser support, or keyboard requirements. React-island integration cost is described as an architectural inference from the two runtimes, not as a measured migration estimate.
