# Remaining `ReplaceDocument` resolvers: provisional inventory

This is a decision aid for tickets 17 and 19. The inventory was first assembled from worktree snapshot `e877dc115` on 2026-10-07; that snapshot remains provisional because ticket 15 was in parallel work. Source references were refreshed against the current shared follow-up tree on 2026-10-07 for concepts that remain in scope. Recheck the inventory after the parallel merge before treating it as final. The counts in the architecture review describe its own earlier snapshot and are not counts of this inventory.

“Frequency” below is a reasoned estimate from the user-facing workflow, not telemetry. Core's `ReplaceDocument` returns every part ID and top-level outline feature ID from both documents as changed, reapplies scripts, and calls `layout::resolve` ([core/src/lib.rs](../../../core/src/lib.rs#L1420), [changed_ids](../../../core/src/lib.rs#L1437)). Separately, `CoreEngine::edit` sends every operation through shared validation/component synchronization, then calls the outline geometry pipeline when `affects_outline` says so ([edit](../../../core/src/lib.rs#L495), [outline dispatch](../../../core/src/lib.rs#L543), [affected operation list](../../../core/src/lib.rs#L995)). `ReplaceDocument` is in that list, and only `MoveParts` supplies the previous outline cache, so replacements recompute feature geometry instead of reusing cached paths ([geometry::outlines](../../../core/src/geometry.rs#L271)). A new typed operation avoids that outline path only if Core does not classify it as outline-affecting; it does not skip the shared edit pipeline.

Typed operations do not automatically make Undo cheaper or more granular: each committed edit pushes the full prior `ProjectDoc`, and history restores full document snapshots ([core/src/lib.rs:573](../../../core/src/lib.rs#L573), [history](../../../core/src/lib.rs#L631)). They can report more precise changed IDs and avoid replacement-specific script/layout preparation or outline recomputation where appropriate. A typed operation remains one history step, just as a replacement is.

## Initial ranking and decision aid

1. **`mode_resolver` → `SetWiringMode`** is the best initial slice if the goal is a small, clearly bounded Core seam demonstration. The current proposal has modest policy (board existence, default Matrix mode, unchanged check, then update/create the board configuration), so the domain-rule extraction is limited. The concrete gain is precise changed IDs and avoiding `ReplaceDocument`'s script/layout preparation and no-cache outline recomputation, if the new operation is not marked outline-affecting. Acceptance: add `SetWiringMode { board_id, mode }`, preserve the current default/create/no-op behavior, and report only the board/configuration IDs Core considers changed; migrate the existing resolver and cover queueing behind an unrelated edit plus unchanged/unknown-board behavior at the Session/Core boundary. This does not reduce Undo snapshot size or create finer Undo steps: history still stores the whole prior document per commit. This is an inferred recommendation, not a usage-data ranking.
2. **`part_net_resolver` plus `apply_resolver` → focused wiring/net intent** is the stronger alternative if wiring edits dominate real usage. Reviewed application changes multiple connections atomically, so this is a larger Core design and implementation slice; it also has more duplicated electrical policy to centralize. Acceptance should test net identity/uniqueness and reviewed plan application, with changed IDs limited to affected part/net/connection IDs. Its typed operation should retain the outline pipeline only if its changed data actually affects outlines.
3. **Outline version feature actions → typed version-feature operations** rank high for domain duplication and outline work, but they are a broader and riskier first slice: active-version checks, identity, validity and version-only feature storage all need explicit Core semantics. Existing `CopyOutline`, `RemoveOutline`, and `SetOutline` reduce the scope for automatic outlines, but do not cover every version feature branch.
4. **Board/project rename** is the smallest implementation, but its user frequency and domain duplication appear lower; it may be an easy early cleanup if the project values a very small API addition over meaningful rule removal.

For a new effort/map, a coherent first effort would contain the selected concept, Core operation, resolver migration and Session/Core acceptance tests; avoid precommitting to a map until the ranking is accepted. A longer-term restriction of `ReplaceDocument` to import and recovery is attractive because it would make accidental whole-document replacement harder, but requires classifying legitimate bulk actions such as physical setup, script application, component/assembly creation and reviewed wiring plans. These should become explicit typed batch intents or remain documented exceptions before enforcement.

Evidence that could change the ranking: product telemetry or user interviews showing another panel is used much more; proof that a typed mode operation cannot preserve current behavior; measurements showing replacement preparation/outline recomputation is negligible for these edits; exact post-merge ticket-15/17 inventory; or a design requirement that project setup/import operations remain bulk document replacements. Undo cost alone does not distinguish typed from replacement edits in the current Core history implementation.

Questions for the human decision: Is the priority frequent everyday interaction, the most duplicated/highest-risk domain rule, or the smallest demonstration of the Core seam? Should the first effort include only a single operation or a cohesive set of wiring edits? Is `ReplaceDocument` expected to remain for import-like product workflows (footprint import, routed-board asset upload, generator/script materialization), and should setup/wiring batch plans be explicit typed operations before the restriction lands?
