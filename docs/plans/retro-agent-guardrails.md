# Retro guardrails implementation plan

[Research and evidence](../research/2026-10-30-retro-guardrails.md) describes the observations, options and limits behind this plan. The goal is to reduce wasted CI build time and misleading verification while preserving the planned Node removal. Measure critical-path wall time, including any duplicated gates, using existing measurements; this is not a broader security project.

## Current changes

The stale CodeGraph and Gortex blocks have been removed from [AGENTS.md](../../AGENTS.md), and delegation handoff criteria clarified in [model routing](../agents/model-routing.md). Cleanup ownership, browser selection, receipt attempts and the retained-gate contract have been implemented with focused checks. The full local gate passed on 2026-10-30 before this status update; hosted checks were not run.

Receipt correlation remains partial. The browser receipt compares the observed main-page document body to the sampled built index, while source-to-build and the other served resources remain unknown. Source snapshots cover tracked and non-ignored untracked files, not every build input, and cannot rule out transient changes. Cleanup on non-Unix platforms preserves the directory and reports an error. The scheduler cancels owned process groups on interruption and records incomplete cleanup when it cannot confirm termination. A Python worker that remains blocked can still delay interpreter exit; process groups do not cover descendants that deliberately create a new session. These limits remain open; do not treat a green command gate as proof of complete source-to-served binding.

## Order and checks

1. **Cleanup ownership.** Address both the observed agent-driven shared-profile deletion and the harness cleanup path. Agent cleanup must identify its own targets and ask before deleting unowned or shared files; process inactivity alone does not establish ownership. In [browser harness directory creation](../../tools/browser-harness/src/lib.rs) and [shutdown](../../tools/browser-harness/src/shutdown.rs), investigate retaining the owned run-directory identity from creation and using one owner for explicit and drop cleanup, after owned processes stop. Fail closed on ambiguous ownership; do not sweep a shared root. Use existing harness lifecycle tests and add focused regression coverage: two runs and an unrelated sentinel survive each other's cleanup; substituted or missing ownership deletes nothing; normal and failed launches clean only their own directory. First demonstrate the regression fails for the intended reason. If path-replacement resistance is claimed, test that case and establish what the implementation actually guarantees; a marker or path check alone does not prove race freedom.

2. **Actual browser and driver selection.** Inspect every wasm-pack launch in [run-wasm-tests.py](../../scripts/run-wasm-tests.py) and [check.py](../../scripts/check.py); pass the resolved driver explicitly where needed, retain the browser capability, and diagnose missing or unusable selections before a build. Extend [runner tests](../../scripts/test-run-wasm-tests.py) and [check tests](../../scripts/test-check.py): conflicting environment and PATH drivers must not override the selected argument, and an invalid selection must fail early. A focused real session should correlate actual executable launch with session-reported browser and driver versions; a stub proves wiring only, and reported versions do not prove executable identity. Compare its cost on the CI critical path.

3. **Same-run receipts.** After selection and cleanup are reliable, extend the existing [verification collector](../../scripts/verification_receipt.py), [drag browser receipt](../../scripts/run-drag-browser.py), and their existing tests as appropriate. Give each invocation and retry a distinct identity; retain command, result and parent relationship for every attempt. Record defined source scope before and after the build, completed build output identity, and served artifact and request/session observations in the same browser run. Use existing response probes and receipts, including observed cache or service-worker provenance where applicable. Missing or inconsistent links must be unknown or invalid for the claim. Test changed source during build, stale output or page JSON, wrong run identity, failed then successful attempts, missing provenance, cache/service-worker behavior and interruption. Matching snapshots do not prove source was unchanged throughout a build or that every input and browser byte was observed; stronger claims need controlled inputs and observation. A previously served package without build binding is diagnostic only. Keep evidence in existing receipt mechanisms, not custom `.evidence/` manifests or source copies.

4. **Retained gate and replacement.** Add a focused structural contract in [test-check.py](../../scripts/test-check.py) for the current [Node parity gate](../../scripts/test-ergogen-parity.cjs), its tooling registration in [check.py](../../scripts/check.py), and CI invocation in [check workflow](../../.github/workflows/check.yaml). Removing it or moving it to opt-in, or omitting tooling from CI, must fail the contract. An intentional cutover updates that contract with a reference to the replacement plan and evidence; a fixture cutover should demonstrate that the structural check accepts the documented transition. The check cannot establish semantic equivalence. Retain the old gate until replacement coverage, negative controls and relevant outer CLI behavior have explicit evidence and required independent review. Fixture parity alone does not establish the sandbox boundary. This contract supports a reviewed Node removal rather than permanently forbidding it.

Cleanup and selection may proceed independently. Receipt correlation depends on knowing which browser and driver ran; the structural contract can be developed independently, but replacement and retirement depend on its evidence and review. Use the user's approved trust in the pinned Chrome and source-bound driver, and scope the replacement review to functional parity and normal failure handling.

## Completion and evidence

For each change, record the focused failing regression, passing fix and affected checks, with claims limited to what those checks observed. Reuse existing scripts and receipts. A local source-bound build/browser run requires its own valid source, build and served-content linkage; local focused checks or old receipts do not substitute for it. Record independent review separately where required, and report hosted CI separately from local results. Report missing or blocked gates rather than treating them as passed.
