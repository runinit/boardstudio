# Candidate 02 — Make readiness and dispatch agree

Research note, 2026-10-20. Read-only investigation; no interface or implementation proposed.

## Finding

**Worth deepening, but narrowly.** The Export workspace calculates availability from accepted-scene flags, a separately published wiring plan, and CAD preview state, then stores callbacks alongside those decisions. Runtime independently admits an export from its *current* accepted snapshot and scope, Session may reject a pending/not-ready source, and output builders can reject additional prerequisites. This is useful defense in depth, but the displayed “Available” is not reliably a prediction that the click can start and finish the named handoff. A shared interpretation of *output prerequisites at the admission seam* could improve locality; replacing export ownership or final-delivery checks with UI readiness would be incorrect. ## Current route and exact friction

- `ExportWorkspace` obtains `runtime.model()`, derives rows, and passes each to `ExportRowView`; the view disables a button on `!ready || !available` and invokes its stored callback. The ZMK row is a special presentation branch: its `ExportRow.on_export` is `None`, and a separate `ZmkFirmwareExportPanelInput` supplies its ready state and callback. Portable project export is outside these rows. [web/src/presentation/export_workspace.rs#L25-L36](../../web/src/presentation/export_workspace.rs#L25-L36), [web/src/presentation/export_workspace.rs#L133-L167](../../web/src/presentation/export_workspace.rs#L133-L167), [web/src/presentation/export_workspace.rs#L178-L228](../../web/src/presentation/export_workspace.rs#L178-L228), [web/src/presentation/export_workspace.rs#L375-L388](../../web/src/presentation/export_workspace.rs#L375-L388).
- The row calculation is a mixture, not one policy: PCB readiness is board-specific with a conservative multi-board fallback; outlines use board readiness or aggregate fallback; authored STEP asks Core's authored-case readiness; footprints check definitions; keycaps check scene revision and board existence; mechanical package checks outline, matching exact CAD scene and generation diagnostics. [web/src/presentation/export_workspace.rs#L236-L264](../../web/src/presentation/export_workspace.rs#L236-L264), [web/src/presentation/export_workspace.rs#L300-L302](../../web/src/presentation/export_workspace.rs#L300-L302), [web/src/presentation/export_workspace.rs#L323-L485](../../web/src/presentation/export_workspace.rs#L323-L485).
- STEP, mechanical and keycap callbacks capture scope/token (STEP and mechanical also session epoch), re-read the model on click and decline stale owners. SVG/DXF, footprints and both KiCad callbacks instead call Runtime directly without row-owner validation; they can therefore invoke an export against the *then-current* board after a retained stale callback, although Runtime/Session still decide whether it proceeds. This is an asymmetry, not proof of a stale download. [web/src/presentation/export_workspace.rs#L265-L322](../../web/src/presentation/export_workspace.rs#L265-L322), [web/crates/runtime/src/runtime.rs#L5060-L5101](../../web/crates/runtime/src/runtime.rs#L5060-L5101), [application/src/session.rs#L2444-L2459](../../application/src/session.rs#L2444-L2459).
- The most concrete ready/dispatch gap is ZMK. UI readiness requires a current board-scoped resolution, matching revision/identity, no error diagnostics, controller ID and assignments; its click additionally requires workspace, scope generation, full UI scope/instance, accepted document/scene identity and executor epoch. Runtime's `export_firmware` itself checks only scope and accepted snapshot before starting; the actual build resolves firmware plans anew, enforces split instances/roles, a reviewed controller profile and transport/peripheral prerequisites. Thus a ready dot need not mean the click passes owner admission or the package can be built. The test plan used for the ready predicate has `controller_profile: None`, a value the request adapter explicitly rejects; this proves the *predicate* is weaker, not that a production user necessarily sees that fixture. ## Ownership must not be collapsed into readiness

Session owns accepted state and ordering; presentation owns display state, not another writable document. An export remains a strict captured-revision operation, unlike queued field edits. Incomplete split designs must remain saveable while dependent outputs are gated specifically. [docs/adr/0014-document-authority-and-captured-lifetimes.md#L5-L13](../adr/0014-document-authority-and-captured-lifetimes.md#L5-L13), [docs/adr/0005-resolve-queued-edits-at-execution.md#L16-L20](../adr/0005-resolve-queued-edits-at-execution.md#L16-L20), [docs/adr/0027-save-incomplete-split-designs-with-output-specific-readiness.md#L5-L11](../adr/0027-save-incomplete-split-designs-with-output-specific-readiness.md#L5-L11), [GLOSSARY.md#L178-L188](../../GLOSSARY.md#L178-L188), [GLOSSARY.md#L283-L292](../../GLOSSARY.md#L283-L292).

Runtime captures kind, accepted snapshot, scope, executor epoch and worker identity in an operation lease; Session admits `RunExport` only for a ready, non-pending current snapshot/scope. During work it checks Session operation ownership and the matching lease. On `ExportFinished`, Session emits a separate `DeliverExport`; delivery compares artifact token/scope with the still-retained lease and current source, *without requiring Session active membership*. Settlement then removes the lease. Do not reuse the active-work predicate for final delivery: a completed export would be suppressed. Nor should a disposable preview refresh alone revoke an export. [web/crates/runtime/src/export_lease.rs#L9-L123](../../web/crates/runtime/src/export_lease.rs#L9-L123), [application/src/session.rs#L680-L696](../../application/src/session.rs#L680-L696), [application/src/session.rs#L1304-L1339](../../application/src/session.rs#L1304-L1339), [application/src/session.rs#L2428-L2474](../../application/src/session.rs#L2428-L2474), [web/crates/runtime/src/runtime.rs#L2124-L2255](../../web/crates/runtime/src/runtime.rs#L2124-L2255), [web/crates/runtime/src/runtime.rs#L6122-L6208](../../web/crates/runtime/src/runtime.rs#L6122-L6208), [docs/adr/0016-export-ownership-is-separate-from-preview-currency.md#L5-L11](../adr/0016-export-ownership-is-separate-from-preview-currency.md#L5-L11).

The PCB handoff may legitimately advance its lease after its *own* accepted wiring/protection commit and return the new token for delivery; unrelated edits must not be adopted. Firmware may deliver two still-current concurrent operations while allowing only the newest to update its status. Browser download errors are separately reported. These are independent safety/lifetime responsibilities, not redundant UI policy. ## Deepening assessment

- **Feasible seam location:** the interpretation of output-specific prerequisites where the accepted snapshot/scope is available to both presentation's row projection and Runtime's admission, with ZMK's wiring/instance context accounted for. The seam should not be the `ExportRowView` button (too late for reliable admission), Session's generic export lifecycle (no output-specific knowledge), or `ExportLease`/delivery (different temporal contract). This is an assessment of existing responsibilities, not an interface design. [web/src/presentation/export_workspace.rs#L230-L264](../../web/src/presentation/export_workspace.rs#L230-L264), [web/src/presentation/zmk_firmware_export.rs#L66-L126](../../web/src/presentation/zmk_firmware_export.rs#L66-L126), [web/crates/runtime/src/runtime.rs#L4820-L5101](../../web/crates/runtime/src/runtime.rs#L4820-L5101), [application/src/session.rs#L2428-L2459](../../application/src/session.rs#L2428-L2459), [docs/adr/0016-export-ownership-is-separate-from-preview-currency.md#L7-L9](../adr/0016-export-ownership-is-separate-from-preview-currency.md#L7-L9).
- **Depth, leverage and locality:** there is real potential if one output-prerequisite decision drives the displayed reason and click admission across several rows, while preserving runtime revalidation. Merely wrapping `ready` booleans or forwarding every export method would be shallow: the callers would still need to understand distinct prerequisites and stale-owner rules. The ZMK plan/instance prerequisite is materially different from authored STEP, footprints and outlines; a universal readiness bit would hide rather than reduce that complexity. [web/src/presentation/export_workspace.rs#L323-L485](../../web/src/presentation/export_workspace.rs#L323-L485), [web/src/presentation/zmk_firmware_export.rs#L45-L172](../../web/src/presentation/zmk_firmware_export.rs#L45-L172), [web/crates/runtime/src/runtime.rs#L4820-L5101](../../web/crates/runtime/src/runtime.rs#L4820-L5101).
- **Deletion test:** if a proposed module vanished, would duplicated output-prerequisite logic reappear in rows and Runtime? That is the useful behavior to concentrate. If only an extra forwarding layer vanished while leases, Session checks, provider validation and callback ownership remained unchanged, it would not have earned a seam. Keep output generation and its irreversible/async checks with their owners. - **Invariants at risk:** no stale board/session/instance or executor may produce output; accepted scene must be current; draft KiCad may retain wiring findings while ordinary KiCad must reject them; own export commits alone may advance capture; final delivery must not depend on a settled active operation; saving incomplete hardware must not be blocked globally. ## Evidence and limits

Mounted tests cover the KiCad row's PCB/wiring disabled states, the ZMK row's disabled state, a successful/failing retry through a mounted production hook, and ZMK owner checks for workspace, generation, scope, instance, accepted revision and executor. Runtime browser tests exercise real `RunExport` failures, worker replacement at awaits, owner switch and concurrent delivery/report behavior; PCB handoff's browser orchestration test covers package-failure retry and stale owner before protection. Lease unit tests cover source/worker invalidation and advancement; native Session tests cover same-ID/revision reopen invalidation and failed-export removal, while native firmware-adapter tests exercise split requests and plan-error rejection. These are strong lifetime/output regressions, but do not test that *every displayed Available row* is admissible in a real Session or that its named output can be generated. **Disconfirming evidence / restraint:** the UI deliberately applies some conservative gates that Runtime does not (e.g. wiring-ready KiCad, outline flag), and Runtime deliberately rechecks dynamic input after a click; eliminating these independent checks would weaken safety. The ZMK mounted success test uses a controlled runtime fixture, while the predicate test's plan lacks a reviewed controller profile, so neither alone establishes a user-visible production failure. A cross-output admission matrix using real Session/Core transitions plus targeted mounted row checks would distinguish policy drift from intentional conservative UX. No build, tests, browser session or live reproduction was run for this research.
