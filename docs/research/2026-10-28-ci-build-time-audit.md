## What is actually on the critical path

Native and web start independently, and security is a separate workflow. PR validation ends at the slowest required job, not the sum of their times. Main release additionally waits for both native and web before release build and deploy; those release stages do not run on PRs ([workflow](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/workflows/check.yaml), [security workflow](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/workflows/security.yaml)). Thus even eliminating an entire shorter job saves at most its overlap deficit, not its duration. In the successful [PR 7 run](https://github.com/runinit/boardstudio/actions/runs/40730153041), native took 32m50s and web 22m52s; making web instantaneous alone would save **zero** validation wall time, while native is the bottleneck. These are observed limits for that run, not forecasts.

## Inside the jobs

The successful old PR 10 [native job](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032845622) reports repo 3.2s, tooling 175.8s, lint 518.8s, test 1041.8s. KiCad installation took 97s, checkout 39s and Rust cache setup 11s. Within lint, native clippy took 215.8s, WASM clippy 250.9s, harness clippy 45.5s. The test batch started at 19:10:24; footprints finished at 19:12:16, workspace at 19:23:19, and CAD at 19:27:46. These overlap: the test wall time is 1041.8s, not the sum of child durations. CAD was the last finisher. The captured workspace output reports test-profile compilation 11m03s, but printed output is buffered; do not infer its real completion timestamp from the log emission. CAD output includes release compiles of 5m54s, 4m13s and 2m50s, but those cannot be added to other concurrent jobs as wall savings. The earlier successful [native job](https://github.com/runinit/boardstudio/actions/runs/40730153041/job/122963955813) reports tooling 152.3s, lint 514.4s, test 1157.5s, and KiCad 118s.

The successful warm [web job](https://github.com/runinit/boardstudio/actions/runs/40730153041/job/122963956010) reports build 326.4s and browser 988.4s, with a 31s Rust restore and a wasm-pack cache hit. Its browser time contains compilation and browser execution, not just test execution. In the cold failed [PR 10 web job](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032846330), fast build took 718.8s; drag browser 122.6s; subsequent capture controls 14.8s, cold responses 7.9s, WASM count check 4.5s, provider 6.3s and CAD browser failed after 27.7s. Later suites did not run. The warm 326.4s versus cold 718.8s difference is **not** a controlled cache experiment: revisions, cache contents and runner conditions differ. Setup for pinned Chrome on the latter was 6s, an upper bound on eliminating that observed installation interval, ignoring restoration cost.

[PR 8 web](https://github.com/runinit/boardstudio/actions/runs/40752121251/job/123041295785) last emitted completed buffered browser output at 19:28:34.936, then exit 143 and runner shutdown at 19:37:17, a gap of 8m42s. That proves neither idle time nor a hang cause. [Scheduler source](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/scripts/check.py#L460-L505) captures each parallel child's output until exit and emits it in submission order; start/end messages are flushed. A later child can execute silently or finish behind an earlier child. Runner termination is recorded, but whether infrastructure, cancellation, CPU, memory, disk, or a test caused it is unconfirmed; do not call it an eight-minute test or assume the scheduler caused shutdown.

The scheduler runs native test workspaces and consecutive browser crate launches in bounded parallel batches (default four), while Cargo defaults to 12 jobs; Cargo can also serialize access to a shared target lock. Multiple elapsed compile durations are neither independent nor additive. The CAD owner tests use a separate target and run sequential selections; [source](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/cad/scripts/cad_build.py#L147-L184), [scheduler](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/scripts/check.py#L514-L547), [Cargo config](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.cargo/config.toml). Logs alone do not quantify lock wait, CPU saturation or I/O wait; 12 jobs on a public standard runner with [four vCPUs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) is a reason to measure, not proof of oversubscription cost. Runner 2.338.0 used Ubuntu 24.04.5 image 20261025.353.1 for native and Ubuntu 26.04.1 images 20261012.163.1 or 20261025.179.1 for web; native cache log lists Rust 1.98.0 and 1.99.1 ([native](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032845622), [web](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032846330)). Web tools are checksum-verified wasm-pack 0.15.0 and dx 0.7.10; current PR 10 pins Chrome/driver 156.0.8078.73 ([tool action](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/actions/web-tools/action.yml), [web log](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032846330)).

## Cache accessibility and gaps

The inspected [cache inventory API](https://api.github.com/repos/runinit/boardstudio/actions/caches) returned four entries, all on `refs/heads/dev`: native 1,360,943,252 bytes, two web entries about 1.47 GB each, and wasm-pack 9,214,940 bytes. Default branch is main, while PRs 8–10 target stack branches, not dev; GitHub permits PR access to its current, base and default branch scopes, not arbitrary sibling branches ([GitHub cache restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). This accounts for why a dev cache's existence is not proof it is accessible to the stack. The [old PR 10 jobs](https://github.com/runinit/boardstudio/actions/runs/40749718847) explicitly reported native and web Rust misses, and web missed both wasm-pack and Chrome; PR save-if for Rust was false. Conversely [PR 7 web](https://github.com/runinit/boardstudio/actions/runs/40730153041/job/122963956010) actually restored a dev web prefix key in 31s and hit wasm-pack. Its base/access context differs; do not generalize a hit or miss across stack levels. The Rust cache action uses compiler/environment and lockfile-derived keys; PR 10's web key also changed across runner/toolchain environments in the observed logs. Exact key alone cannot establish accessibility or useful reuse ([native log](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032845622), [web log](https://github.com/runinit/boardstudio/actions/runs/40749718847/job/123032846330)).

Native cache configuration includes root, `cad/monstertruck/target`, and `cad/wasm/target`, but not `cad/monstertruck-qualification/target`, which the CAD test uses ([workflow](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/workflows/check.yaml#L29-L40), [CAD script](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/cad/scripts/cad_build.py#L172-L184)). That is a concrete coverage gap, not a measured saving: even a hit must be compatible and costs restore/save time. The action's PR post-save is disabled for Rust, and failed jobs skipped post-save in the old samples; successful PR 7 web also did not save an already-hit wasm-pack cache ([workflow](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/workflows/check.yaml), [PR 7 job](https://github.com/runinit/boardstudio/actions/runs/40730153041/job/122963956010)). No successful PR Rust save duration was observed. Cache entries may contain executable build products; never include secrets, do not let untrusted PRs populate a trusted shared scope, and preserve provenance and integrity. GitHub documents branch isolation, readable base caches, eviction by least recent access and storage limits; quota pressure and key/version changes can erase gains ([GitHub caching documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)).

## Priorities and measurement

1. **Measure first and repair cache reachability safely.** Record exact restore key, scope, hit/miss, compressed bytes, restore/save times and target coverage per job. Evaluate trusted base/default-branch warming and qualification target coverage with version, lockfile, platform and profile invalidation. Preserve trust boundaries and never make PR code a trusted cache writer. Measure total elapsed job time and storage/eviction, including restores. A cache inventory listing alone is not a hit receipt.
2. **Expose timing without weakening tests.** Emit child start/end and periodic resource/lock-wait measurements while preserving exit status and ordered failure output. Separate compiler, link, execution and queue where observable. Capture CPU, peak RSS, disk throughput and filesystem space; compare identical source, runner image and cache state. Buffered logs are not proof of a stall. Investigate shutdown using Actions run cancellation/runner evidence before assigning a cause.
3. **Benchmark bounded scheduling and target contention.** Compare repeated comparable cold and warm runs with unchanged test inventory and assertions, varying one scheduler/runner setting at a time. Report critical-path wall time, CPU and I/O, cache overhead, first failure and all job outcomes. A larger runner or different parallelism may improve or worsen contention; no projected time is justified yet.
4. **Audit tool installation separately.** Consider trusted, version- and platform-bound verified tools or cache for cargo-audit/deny, with pinned versions and unchanged audit/Miri checks. The measured 5m37s install interval bounds the direct opportunity in one job, but security may remain off the PR critical path and cache poisoning or stale advisories must not be introduced ([security workflow](https://github.com/runinit/boardstudio/blob/aa30da07b22af6356935224e423374d95cfbe43e/.github/workflows/security.yaml)).

Acceptance for an optimization: compare same head and required check set, record cold and warm runs and GitHub run/job URLs, verify test counts and failures remain visible, and retain actual hosted CI conclusions. The current runs are incomplete, and no causal speedup, full acceptance, or resource bottleneck is established by this audit.
