# Research: retro guardrails for CI evidence and ownership

30 October 2026. Scope: reduce wasted CI build time and prevent misleading verification, while preserving planned migrations. Findings below are observations from this checkout and local session evidence; approaches and tests are proposals, not agreed acceptance criteria. No builds or browser runs were performed for this note. Ignored `.evidence` files are local, ephemeral evidence, not durable CI receipts.

## 1. Cleanup ownership

**Observed.** The task reports an unauthorized profile deletion; the supplied report does not establish its exact cause or responsible process. [`IsolatedDirs`](../../tools/browser-harness/src/lib.rs) creates a unique temporary run directory and profile; its drop cleanup removes its recorded run directory. [`shutdown::remove_profile`](../../tools/browser-harness/src/shutdown.rs#L66) instead derives the target from the public profile path's parent and recursively removes it. Existing tests cover isolated directories and lifecycle, but that derivation is not itself proof that the target belongs to this run. [`run-drag-browser.py`](../../scripts/run-drag-browser.py#L114) chooses a shallow temporary root for socket path limits. [Python tempfile](https://docs.python.org/3/library/tempfile.html) documents unique temporary directory creation; uniqueness does not grant ownership of an arbitrary later path.

**Failure mode.** A wrong, substituted, or stale cleanup path could point at another profile or its parent; process shutdown and directory ownership are separate questions. A marker or string prefix alone is not proof against replacement between check and removal.

**Options and smallest approach.** Keep a private owned run-directory handle or identity at creation, route explicit and drop cleanup through the same owner, and remove only that run directory after its owned children are confirmed stopped. Reject ambiguous or mismatched identity and report cleanup failure; never sweep a shared root. For ordinary accidental mistakes, exclusive creation plus recorded identity and narrowly scoped cleanup may suffice. If concurrent path replacement is in scope, consider descriptor-relative operations and identity checks, not a `resolve()`-then-delete claim: [Linux openat2](https://man7.org/linux/man-pages/man2/openat2.2.html) describes resolution constraints and their limits, while [Python shutil](https://docs.python.org/3/library/shutil.html#shutil.rmtree) explains platform-dependent fd-based recursive deletion. Rust implementation and portability need separate investigation; these APIs do not automatically make the proposed Rust cleanup race-free.

**Tests to consider.** Two independent runs and an unrelated sentinel survive each other's cleanup; invalid/replaced profile parent and missing ownership fail without deleting anything; normal and failed launch paths clean only the owned directory after process termination. Exercise path replacement if the chosen implementation claims to handle it. Avoid introducing a broader security project for a routine CI cleanup bug.

## 2. Actual browser and driver selection

**Observed.** [`run-wasm-tests.py`](../../scripts/run-wasm-tests.py#L219) resolves explicit environment, pinned Chrome for Testing, then PATH, prints both paths and sets `CHROMEDRIVER`; Chrome is put into WebDriver capabilities. The [workflow](../../.github/workflows/check.yaml#L52) installs and version-checks the pinned pair before `check.py build browser`. However [wasm-pack 0.15.0 source](https://github.com/wasm-bindgen/wasm-pack/blob/v0.15.0/src/command/test.rs) selects its own driver unless `--chromedriver` is supplied, then sets `CHROMEDRIVER` for Cargo; the parent environment alone does not pin its child selection. Direct wasm-pack commands in [`check.py`](../../scripts/check.py) also need consideration. Local `.evidence/wasm-selection-page.log` records printed paths and five passing tests, while `.evidence/wasm-selection-processes.log` identifies a test-runner executable, not the actual ChromeDriver executable. `.evidence/wasm-pack-selection-diagnostic.log` shows a `--chromedriver /bin/true` invocation and selected test runner; it is not proof of a real WebDriver session.

**Options and smallest approach.** Pass the resolved driver via wasm-pack's explicit `--chromedriver` for every relevant launch, including direct crate commands, and retain the existing browser capability. Add a cheap pre-build mismatch/missing-path diagnostic. Record effective path and version at launch and, where the harness exposes them, the session's returned `browserVersion` and `chrome.chromedriverVersion`; [ChromeDriver documentation](https://developer.chrome.com/docs/chromedriver/capabilities) specifies the binary option and returned driver version. Returned versions establish session-reported versions, not executable path or file identity; process executable observation or a controlled wrapper can provide separate actual-launch evidence. Version compatibility is distinct from exact pin equality ([Chrome version selection](https://developer.chrome.com/docs/chromedriver/downloads/version-selection)). Recheck behavior for the installed wasm-pack version when upgrading.

**Tests to consider.** Put conflicting drivers in environment and PATH and verify the explicit argument reaches every spawned command; missing/non-executable pin fails early. A focused real session should correlate the selected executable and returned versions; a stub test verifies wiring but cannot prove actual browser launch. Compare overhead against current critical-path time.

## 3. Same-run source, build, served content, and attempts

**Observed.** [`verification_receipt.py`](../../scripts/verification_receipt.py#L514) captures HEAD and dirty status at collector creation, plans and observes commands, and only loads page JSON when file metadata changed during that command. This is freshness evidence, not a content or source/build binding. [`run-drag-browser.py`](../../scripts/run-drag-browser.py#L35) hashes selected source state and built site files at smoke time and validates a run-specific receipt; it starts its own server. These snapshots alone do not establish which source was read during an earlier build or which bytes a browser consumed. Git's [working tree documentation](https://git-scm.com/docs/user-manual) distinguishes HEAD from local changes. Local `.evidence/installer-browser-receipt.json.md` reports 24/24 build/browser commands accepted at a dirty tree and explicitly labels the selection partial; it is not a full gate or proof of an immutable source build.

**Options and smallest approach.** Give each build/browser invocation and each retry a distinct ID and preserve each attempt's command, result and relationship to the parent; do not replace failed attempts with the final green result. Record source identity immediately before and after the build using a defined tracked/untracked scope, build output digest after completion, and the served artifact identity and actual request/session observations during the same browser run. Mark missing or inconsistent links unknown or invalid for the claimed scope. Record whether content came from cache or a service worker where observed, and use the existing controlled response probes where applicable. Carry these fields in existing receipts, not copied source trees or new manifests in `.evidence`.

**Limits and tests.** Matching snapshots cannot prove the source never changed and reverted mid-build, nor that every dynamic input, toolchain, dependency, network response, or browser byte was observed. Stronger claims require controlled immutable inputs and complete observation, with costs to measure. Test source change during build, stale site, stale page JSON, wrong run ID, failed first attempt followed by success, missing response provenance, cache/service-worker cases, and interrupted commands. Scope each claim to what was actually measured; an existing served package is diagnostic unless its build binding is established.

## 4. Retained Node gate and planned cutovers

**Observed.** [`check.py`](../../scripts/check.py#L66) registers `scripts/test-ergogen-parity.cjs` in tooling; CI runs tooling in the native job. [`test-check.py`](../../scripts/test-check.py#L38) inventories supported test scripts against registered commands and named opt-ins. It checks existence of Python scripts/manifests, and explicitly tests a previous model-lookup browser cutover, but adding a Node script to opt-ins can satisfy the inventory without proving equivalent replacement. The current inventory is therefore useful coverage, not a verified-replacement policy.

**Options and smallest approach.** Add a focused retained-gate contract test for the current Node parity command and its CI inclusion. Make an intentional cutover an explicit reviewed change to that contract, linked to a plan ticket specifying what behavior the replacement covers, its evidence and remaining gaps; retain the old gate until that evidence and required independent review exist. This is a reviewable change, not a permanent prohibition on removing Node. A machine check can verify presence and a documented transition reference, but cannot decide semantic equivalence or authorize its own removal. Existing ticket conventions require a numbered issue in a plan map with status, type and dependencies ([issue tracker](../agents/issue-tracker.md)); no ticket or new criteria are created by this note.

**Tests to consider.** Removing or moving the retained command to opt-in fails the contract; changed workflow invocation cannot silently omit tooling; a deliberate fixture cutover with a referenced replacement passes the structural check only after its contract is updated. Independently evaluate the replacement's parity, negative controls, and relevant outer CLI behavior; matching fixtures alone does not prove a sandbox boundary. Measure any duplicated-gate cost and retire it only through the planned decision.

## Priority and open decisions

First fix selection wiring and cleanup ownership, then improve receipt correlation using already-produced data, and protect the retained gate with a small structural test. Decide the required strength of source/served provenance and the owner of replacement review in the relevant plan before implementing a cutover. Compare CI critical-path wall time, not the sum of parallel job durations; keep hosted CI evidence separate from local receipts.
