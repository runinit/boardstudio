# Research: verification receipts for test-count reviews

## Finding

The ticket should make the existing check run produce one compact, machine-readable receipt from the command outputs it already captures. The review count error came from manually estimating test-group counts: the final review asserted Case `4→5` and Runtime `14→16`; the recorded verification says the actual counts were Case `3→4` and Runtime `12→14`. The corrected values are established by the focused GREEN logs and recorded in the disposition (`.evidence/collision-check-deepening/green-case-collision.log`, `green-runtime-collision.log`, `review-disposition.md`). Those files are ignored session evidence, so the counts are historical evidence for this investigation, not durable repository data.

## Smallest useful extension

Extend the existing `check.py` run collector to emit a compact optional JSON verification receipt for test commands. Reuse native test-name parsing and the output already captured by `run_serial` / `run_parallel`; parse each direct WASM crate launch independently from its own output; retain the current page runner JSON as one separate scope rather than treating it as the whole browser gate. An opt-in output path keeps current check output and exit behavior stable. A reviewer can then receive the receipt instead of counting summaries manually.

Each command record should identify its exact scope (native command/binary, named WASM crate launch, or page filters), invocation status, exit code, elapsed time, observed passed/failed/ignored/incomplete counts, and parser completeness. Retain every observed test name and outcome, not a sample, so the reviewer summary can derive focused group counts by explicit module prefix from whole-crate output. The historical focused runs were launched outside `check.py`; adding a new filtered-launch interface is unnecessary if whole-crate names support the same grouping. Record the checked-out revision and whether the tree had local changes so a copied receipt retains provenance.

For native tests, report retention-list names matched/missing and newly observed names using the existing full-versus-partial semantics. Identify the list's recording revision and any local changes, but never present it as the reviewed change's before-count: new tests do not fail the guard, so the list may lag the source. A before/after count requires explicit test-run evidence from the base revision; otherwise report the comparison as unknown. The [native guard](../../scripts/check_native_tests.py) supplies retention semantics, not a change-delta oracle.

Preserve the page runner's known-failure policy as a separate dimension. It records raw failed outcomes and `failed_known_exclusions`, while its exit status excludes those named known failures. A receipt must show the raw failures and exclusions, follow the runner for gate acceptance, and never describe an accepted run with known failures as all tests passing. See the [page runner](../../scripts/run-wasm-tests.py).

The receipt must be invocation-scoped: a command launched in this check is fresh evidence; absent commands are `not_run`; malformed or interrupted output is `incomplete`/`unknown`. Do not silently import a previous `browser.json`, smoke receipt, or log as current evidence. If a caller explicitly supplies prior evidence for comparison, label it reused and retain its run identity/revision. A failing check should still write a partial receipt with the failure and unrun planned commands, while returning the same nonzero status it returns today.

## Machine-testable acceptance criteria

- Fixture outputs for multiple native binaries yield separate executed/passed/failed/ignored counts, baseline-name matches/misses and new-name counts; an absent binary in a partial run remains `not_run`, while a missing baseline test in an executed binary is reported as missing.
- Fixture outputs for two WASM crate commands yield two independent records with full observed names and outcomes. Counts come only from each command's own terminal lines and summaries; module-prefix groups can be recomputed from those names. Page-suite JSON is labeled as the page suite and never used to fill missing crate records or claim the complete browser gate passed.
- Full gate acceptance requires every planned command to run and be accepted under its runner policy; terminal completeness and raw test outcomes remain separate. Known-exclusion fixtures retain named failures even when the runner exits zero. A nonzero runner exit with no terminal tests, a timed-out/invoked test without a terminal result, malformed output, or an early stop is represented as failed/incomplete/unknown, never as zero failures or success.
- A partial command selection names the selected scope and explicitly states that omitted steps were not run; it cannot claim full verification.
- Reused evidence carries its original run/revision and is visibly distinct from output produced during the current invocation. The default receipt does not read cached result files as proof of fresh execution.
- Whole-crate output fixtures yield current collision-group counts Case `4` and Runtime `14` from module prefixes; they yield base counts Case `3` and Runtime `12` only with explicit base-revision run evidence. Current-only output or the native retention list must leave the before/after comparison unknown. Do not infer `4→5` or `14→16` by hand-entered arithmetic.

No builds or test commands were run for this research. The recommendation is based on the current check runners and recorded session evidence.
