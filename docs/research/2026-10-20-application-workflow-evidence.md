## 1. Project deletion and interrupted recovery

### Current connected behavior

1. Library uses a native delete confirmation, initially focuses Cancel, disables actions during deletion, and calls `runtime.delete_saved_project`. On success it refreshes listing/selection and focuses search; on error it leaves the dialog actionable with a generic message. The operation continues if Library unmounts; only its later UI write is skipped ([Library action](../../web/crates/library/src/library.rs#L1103-L1177)).
2. Runtime asks before discarding a retained failed save, takes a deletion lease, supersedes pending store-load admissions, then either recovers the active saved copy or waits for Ready plus matching Saved revision. The bounded wait is 1,200 × 25 ms; it fails rather than deleting during an unresolved save. For **current** deletion it opens the first remaining readable project sorted by stored name, or creates a saved replacement when none remains. It checks replacement/current identity before the final token-checked deletion. **Other-project** deletion does not open a replacement or reset active Undo ([Runtime](../../web/crates/runtime/src/runtime.rs#L940-L1165), `delete_saved_project`, `wait_for_saved_active_document`, `ensure_delete_owner`).
3. The deletion lease rejects unrelated Open/Recover submissions while allowing its own replacement. It does **not** freeze all editing: ordinary edits still enter Session. That distinction is why crossing an active edit/save must be checked at the public route, not inferred from a “busy” name ([`submit`](../../web/crates/runtime/src/runtime.rs#L1667-L1721)).
4. Session queues Open behind outstanding Core/save work. A failed save retains its computed candidate, leaves accepted state unchanged, blocks queued dependent work, and permits save-only retry. Successful Open is itself saved before publication and advances the editor-session epoch; it clears selection/active instance. Unknown Core outcome restarts the executor and requires explicit recovery, not replay ([Session](../../application/src/session.rs#L1355-L1371), [`pump`](../../application/src/session.rs#L1469-L1476), [`persist_completed`/`retry_save`](../../application/src/session.rs#L1905-L2042), [`core_failed`](../../application/src/session.rs#L2043-L2079)).
5. Runtime captures the persistence port, candidate document and expected token before awaiting the write. Failed candidates and staged asset bytes remain available to `pending_archive`; retry does not adopt the winner's token. `open_saved` also uses an open sequence so a late store read cannot replace a newer request ([persistence driver](../../web/crates/runtime/src/runtime.rs#L1886-L1924), [`open_saved`](../../web/crates/runtime/src/runtime.rs#L6969-L7027), [pending-copy/recovery controls](../../web/crates/runtime/src/runtime.rs#L7081-L7207)).
6. Store writes document and assets together, checks the observed content token in the same IndexedDB transaction, and validates required asset presence. Deletion removes the **project record**, not asset bytes. Startup collection needs safe exclusive/editor coordination and a readable reference scan; open-editor Undo, extra/legacy windows or unreadable documents can defer it ([storage](../../web/crates/host/src/host/storage.rs#L513-L713), [startup](../../web/crates/host/src/host/storage/startup.rs)). A localStorage active-ID update is best-effort after the database commit, not part of that atomic transaction.

Unreadable records are a separate route: Library offers raw JSON download and an explicitly confirmed, token-guarded `delete_unreadable`, directly on the store. It does not pretend that raw JSON is a validated portable project, nor pass that deletion through Runtime's replacement workflow ([raw controls](../../web/crates/library/src/library.rs#L947-L972), [raw delivery](../../web/crates/runtime/src/runtime.rs#L7092-L7108)). A live editor whose stored record subsequently becomes unreadable is an important crossing to characterize, not proof this direct route already destroys its accepted document.

## 2. Real offline release transitions

### What current source actually guarantees

- `build-web.py` copies page assets, Core/CAD worker entry points, CAD provider and renderer into each requested route, then inventories files into the generated offline bootstrap. Pages uploads the `/boardstudio/` route as one artifact. Provider URLs such as `assets/cad-worker/entry.js` are ordinary relative paths, not individually content-versioned release directories ([builder](../../scripts/build-web.py#L70-L91), [`embed_offline_worker`](../../scripts/build-web.py#L129-L181), [validation and release workflow](../../.github/workflows/check.yaml)).
- Installation uses `cache.addAll` for the manifest inventory. **Runtime CAD creation is lazy, but asset caching is not necessarily lazy:** CAD/provider files are in the package inventory, so completed service-worker installation can already cache them before the designer opens a CAD view. X4's existing 201-entry manifest contains CAD worker/provider files. Do not confuse “never opened Case” with “CAD bytes were never cached” ([installation](../../web/src/service_worker.rs#L52-L64), [representative lazy worker creation](../../web/crates/runtime/src/runtime.rs#L1548-L1552)).
- No forced `skipWaiting`: a new worker waits while old clients remain. Activation removes older caches only for the same encoded route scope, then claims clients. Fetch serves a cache hit, navigation shell fallback, or network on a miss. This protects assets present in the active release cache; it does not make an uncached request immune to network/deploy changes ([worker](../../web/src/service_worker.rs#L66-L103), [scope encoding](../../web/crates/host/src/offline.rs#L57-L74)).
- CAD client checks request IDs, jobs, captured identities/revision, typed buffers and metadata. Runtime verifies the operation-specific source/executor after awaits. These are freshness and protocol-shape checks, **not evidence that page A and provider B implement compatible semantics**. An absent explicit release handshake alone is not a reproduced bug ([CAD client](../../web/crates/host/src/cad_worker.rs), `request`, `validate_request`, `receive`, `decode_result`; [Runtime captured firmware checks as another example](../../web/crates/runtime/src/runtime.rs#L6598-L6857)).
- The local server deliberately adds COOP/COEP; the workflow configures artifact upload/deployment, not the live CDN's response headers, cache TTLs, old-path retention or atomic replacement behavior. X2 verified local headers only ([server](../../scripts/serve-web.py#L39-L42), [workflow](../../.github/workflows/check.yaml)).

**Executed versus missing:** X1 passed `test_offline_worker_waits_for_old_clients_before_activation` and `test_offline_worker_bootstrap_passes_route_manifest`. The former checks source substrings; the latter uses fake WASM/JS payloads. These are useful regression checks, not a real service-worker update. X3 used one existing package online and did not inspect registration/cache state. **No two-release, offline or multiple-tab app experiment was run.** [0022](../adr/0022-static-local-first-rust-application-with-worker-execution.md) requires continuity, conditional on locally available assets; it does not promise remote model fetching offline.

## 3. Renderer failure and recovery

### Actual lifetimes and failure behavior

The renderer owns GPU objects/camera, not the accepted document. `RendererHost::mount` imports/initializes the module, checks live ownership around awaits, constructs the renderer and uses cleanup-on-failure attachment. Attachment sets the scene and **fits** the camera. `install_lifecycle` handles resize/DPR/frame callbacks and context loss; loss marks `context-lost`, cancels rendering and reports it. Render-call failure marks `frame-failed`. Later camera, scene, handle and pick calls reject unavailable/disposed hosts; disposal cancels callbacks/listeners/observers and calls renderer disposal/free ([Host](../../web/crates/host/src/renderer_host.rs#L38-L157), [`install_lifecycle`](../../web/crates/host/src/renderer_host.rs#L383-L489), [renderer-owned camera/objects](../../renderer/src/wasm.rs#L376-L399)).

SharedViewer has a mounted-view owner plus source scope/token/revision, projection generation, viewer instance and renderer sequence. It checks the current source and **applied** projection before picking; old handles/focus requests cannot borrow a newly current document's identity. Drop retires the owner, releases pointer capture and disposes the host. Mount errors keep a visible unavailable message and the forms/2D route; callback errors/loss are written into the status region and emitted to the current owner. No automatic WebGL restoration mechanism is present in the inspected Host listener path ([owner/source](../../web/crates/case/src/shared_viewer.rs#L143-L285), [drop and scene publication](../../web/crates/case/src/shared_viewer.rs#L1622-L1748), [mounted callback/current checks](../../web/crates/case/src/shared_viewer.rs#L1884-L2083), [pick guard](../../web/crates/case/src/shared_viewer.rs#L2110-L2181), [visible status](../../web/crates/case/src/shared_viewer.rs#L3064-L3080)).

This is fail-stop/reopen behavior, not retained independent renderer authority. Reopen is a user route through view unmount/remount; **reopening the project is a different editor-session transition**. The App can hide an Editor behind Library without unmounting it; workspace changes conditionally mount children. Do not use `root.remove()` or a project browser toggle as proof the full production view actually tore down ([App](../../web/src/presentation.rs), [Editor lifetime research](editor-workspace-extraction.md#21-three-lifetimes-not-just-page-and-workspace)).

### Workflow 1 — Keep work safe while changing/deleting projects

**Problem/solution from the user's view:** “I need to leave or delete a keyboard without losing an unresolved edit, deleting the wrong saved record, or breaking models still used by a surviving project or Undo. Show what is pending and make the explicit recovery choice reliable.”
