# Research: Six input-boundary audit findings

This note researches six already reproduced audit findings. Audit logs are ignored session evidence, not portable repository artifacts; durable reproduction cases and required verification are described below and in the linked tickets. It uses the retained probe logs under `.evidence/ponytail-audit/` and `.evidence/ponytail-followup/`; it did not rerun builds or tests. Recommendations below are bounded to those cases and the referenced format/API contracts. They are not proofs of all CAD-kernel mathematics, all hardware variants, or browser acceptance.

## 1. WRL nesting and reference expansion can trap the shared decoder

**Observed case.** The packaged renderer probe in `.evidence/ponytail-audit/wrl-depth.log` decoded 32 nested groups (773 input bytes) and 108 position floats, but 4,096 groups (94,245 bytes) trapped with `RuntimeError: memory access out of bounds`. The subsequent simple-box decode in the same instance also trapped. `.evidence/ponytail-audit/wrl-expansion.log` shows a 24-level repeated-`USE` graph taking 5,207 ms for the same 108 position floats; this indicates traversal work can grow while output remains fixed. The current parser bounds input bytes through [`assets::check_size`](../../renderer/src/assets.rs#L16), and emitted positions through [`append_triangle`](../../renderer/src/wrl.rs#L476), but `walk_node` recursively descends children without a depth or expanded-node budget ([`wrl.rs`](../../renderer/src/wrl.rs#L262)).

**Contract and correction.** VRML97 allows `DEF` definitions and `USE` references to nodes; the specification describes grouping nodes and inherited transformations, so repeated references can expand work at traversal time ([VRML97 grouping and children](https://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.5)). Keep the existing byte and output-position limits, and add explicit nesting-depth and cumulative node-visit/expanded-work budgets charged before recursion. Return a normal unsupported/limit error before exhausting the WASM stack or memory. The active-node cycle check only rejects cycles on the current path; it does not cap deep acyclic nesting or repeated subgraphs.

**Acceptance evidence.** Retest the exact depth-4,096 and 24-level repeated-reference fixtures through packaged WASM. Both should fail promptly with a stable limit error and bounded work; then decode a simple box on the same WASM instance to show it remains usable. Also retain a below-limit nested-group and repeated-reference fixture to prove ordinary traversal still works. Keep byte and position-output boundary tests. These cases validate parser resource boundaries, not general WRL conformance.

**Dependencies.** Independent of the other five findings. The parser traversal owner should coordinate depth and visit accounting so nested child paths cannot bypass either budget.

## 2. Geometry-script emissions allocate before the output limit is checked

**Observed case.** `.evidence/ponytail-audit/script-budget-loop.log` records a 4,149-byte script repeatedly emitting a 4,096-byte string field. In the packaged Core WASM probe, linear memory grew from 1,835,008 to 185,532,416 bytes before Rhai's operation limit rejected evaluation. The 256-byte-string comparison reached 14,876,672 bytes from the same 1,835,008-byte starting point. These are WASM linear-memory observations for these probes, not process RSS or an allocator-wide peak. [`collect`](../../core/src/script.rs#L53) configures operation/string/container limits; both registered emission callbacks clone their string arguments into the output vector ([`part`](../../core/src/script.rs#L70), [`rect`](../../core/src/script.rs#L91)); only after evaluation does it check `MAX_EMISSIONS` ([`script.rs`](../../core/src/script.rs#L119)).

**Contract and correction.** Rhai documents limits on script operations and built-in string/array/map sizes, and supports fallible registered Rust closures ([Rhai function registration](https://rhai.rs/book/rust/functions.html)). Those engine limits do not define the aggregate bytes held by BoardStudio's callback-owned output vector. Also, ordinary `ErrorRuntime` exceptions can be caught by script `try/catch`, while Rhai explicitly marks evaluation-limit errors and manual termination as non-catchable safety protections ([Rhai catchable and non-catchable exceptions](https://rhai.rs/book/language/try-catch.html)). Track emission count and cumulative UTF-8 bytes in shared callback state. Before cloning any field, use checked arithmetic and terminate the entire evaluation with a non-catchable termination/error when either budget is exceeded; a catchable error could let a script swallow rejection and return a successful partial emission list. The callback must set a terminal budget-exceeded state before returning, and every later callback must refuse to copy more fields. Apply the same accounting to both callbacks. Retain source, operation, per-string, and output-count limits separately.

**Acceptance evidence.** A small set of valid `part` and `rect` emissions at the count and aggregate-byte boundaries should return all expected fields. One over-count case and one aggregate-byte-overflow case should terminate evaluation inside callback execution, preserve the prior document on the transactional script-apply path, and stay within an asserted WASM-memory-growth ceiling. Include a `try/catch` script that attempts to catch the budget error and then emit again; evaluation must remain failed and no callback may copy later data after the budget is exhausted. A single large field tests the existing per-string bound; a many-emission fixture is needed to prove the combined-byte budget. Do not present the measured 177 MiB case as an RSS measurement.

**Dependencies.** Independent of other findings. Both callbacks should share one budget/accounting helper to prevent policy drift.

## 3. Concave WRL faces are incorrectly fan-triangulated

**Observed case.** `.evidence/ponytail-audit/wrl-concave.log` records a 178-byte `IndexedFaceSet` U-shaped face with `convex FALSE`. The decoder emits six fan triangles, and triangles cover point `(1.5, 2)` in the source notch. [`append_geometry`](../../renderer/src/wrl.rs#L352) splits every polygon from its first vertex and does not inspect `convex`.

**Contract and correction.** VRML97 defines `convex` as a hint that all faces are convex, and permits concave planar, non-self-intersecting polygons when it is false; it defines a convex polygon by all interior angles being less than 180 degrees ([VRML97 shape hints](https://www.web3d.org/documents/specifications/14772/V2.0/part1/concepts.html#4.6.3.4)). The separate IndexedFaceSet requirements say faces are planar and non-self-intersecting ([VRML97 IndexedFaceSet](https://www.web3d.org/documents/specifications/14772/V2.0/part1/nodesRef.html#6.23)). The smallest safe product correction is to reject non-triangular faces when `convex FALSE` is specified, documenting that this preview supports only convex polygons and triangles for this case. Alternatively, use a triangulator that preserves polygon interiors. Merely reading the convex flag and continuing to fan-triangulate would not fix the geometry.

**Acceptance evidence.** Retain the U-notch fixture and assert a documented unsupported error for its concave polygon; preserve a triangle with `convex FALSE` and a convex polygon as supported controls, plus multiple-face indexing. If implementing general triangulation, test concave polygons with several winding directions and vertices; these tests do not establish correctness for arbitrary non-planar or self-intersecting input, which VRML97 itself leaves undefined.

**Dependencies.** Independent of the WRL resource-budget item; both touch the same decoder and should be integrated/reviewed together to avoid overlapping edits.

## 4. Interrupted native tests can have a complete receipt

**Observed case.** `.evidence/ponytail-audit/receipt-interruption.log` is a parser result for output containing a Cargo `Running unittests` line, `running 100 tests`, one passing result, and then exit code 130. It reports `complete: true`, one pass, zero incomplete tests, and no problems, while correctly keeping `passed: false` because the command exit was nonzero. [`native_record`](../../scripts/verification_receipt.py#L215) currently sets completeness from an empty `problems` list and only detects tests already observed as started-but-not-terminal.

**Contract and correction.** Rust's test runner prints a final result summary after test execution (the Rust testing guide illustrates `running N tests` followed by individual results and a summary), while Cargo's exit status reports command success/failure ([Cargo test command](https://doc.rust-lang.org/cargo/commands/cargo-test.html), [Rust Book: running tests](https://doc.rust-lang.org/book/ch11-02-running-tests.html)). Require an observed terminal summary per invoked native test binary before marking its observation complete. Reconcile announced and observed counts to detect incompleteness, but do not fabricate names or count unnamed, never-started tests as individually observed incomplete outcomes. Preserve partial observed passes/failures; mark the binary incomplete and expose its announced-versus-observed count gap as a problem. An incomplete count may remain limited to named tests seen starting without a terminal result. Preserve command exit status independently from parser completeness and test-result counts.

**Acceptance evidence.** Parser fixtures should cover: complete passing binary, complete failing binary, ignored tests, multiple binaries, announced count larger than terminal results, a started test with no verdict, a binary with no summary, and exit 130 after partial output. Partial observations stay visible, but `complete` must be false; assert the count gap is reported without inventing the 99 unseen test names. `incomplete` may count only a named test observed starting without a terminal result. A nonzero exit remains failed even when a complete summary exists. No Cargo rerun is needed for this parser-only regression.

**Dependencies.** Independent of product-code findings. This is receipt metadata, not a correction to Cargo's runner or an assertion that the previous six-gate pass was freshly rerun.

## 5. Generator text is interpolated without KiCad string escaping

**Observed case.** `.evidence/ponytail-followup/wasm-text-export.log` shows Core returning a successful PCB export for `1" pitch`, but the emitted S-expression becomes `(gr_text "1" pitch" ...)`. `.evidence/ponytail-followup/generator-roundtrip.log` confirms parsing does not preserve the requested string. The issue spans [`ceoloide/utility_text`](../../footprints/src/generators/ceoloide/utility_text.rs#L50), [`infused-kim/text`](../../footprints/src/generators/infused_kim/text.rs#L34), and dynamic labels in [`infused-kim/pads`](../../footprints/src/generators/infused_kim/pads.rs#L84) and [`infused-kim/smd_0805`](../../footprints/src/generators/infused_kim/smd_0805.rs#L197). The report records KiCad 10.0.7 rejecting the quoted-label export while loading its plain-text control.

**Contract and correction.** KiCad's format defines strings as double-quoted UTF-8 values ([KiCad S-expression syntax](https://dev-docs.kicad.org/en/file-formats/sexpr-intro/#syntax)); its graphical text schema identifies the text payload as a quoted string ([KiCad graphical text](https://dev-docs.kicad.org/en/file-formats/sexpr-pcb/#graphic-items)). Serialize user strings with the project's existing JSON-compatible string helper [`json_string`](../../footprints/src/generators/util.rs#L39), after confirming the emitted escaping matches KiCad's accepted syntax, or introduce a shared S-expression string serializer. Do not apply JSON quoting twice. The audit did not establish every possible control-character policy; scope the fix to correct quote/backslash/newline encoding and separately reject unsupported control characters if the format/parser requires it.

**Acceptance evidence.** For each affected generator family, export text containing quote, backslash, and ordinary UTF-8; parse the full emitted S-expression and assert the recovered text equals the original. Load representative generated `.kicad_pcb` and footprint files with the installed KiCad CLI/application parser. Include plain-text controls to guard existing output shape. Avoid treating parser round-trip alone as complete KiCad compatibility; the retained KiCad 10 repro is useful external validation.

**Dependencies.** The generators can share one serialization utility. If the tickets are split by generator family, make the serializer ticket a blocker for each migration slice and include a final inventory check for remaining free-text interpolation.

## 6. PCB outline import only accepts the legacy `tstamp` identity field

**Observed case.** The source at [`stable_source_id`](../../core/src/artifact/mechanical_extract/board_source.rs#L142) reads only `tstamp`. `.evidence/ponytail-followup/pcb-uuid-import.log` records a current Core-exported outline rejected with “missing its stable tstamp”; changing only the field name to `tstamp` makes the same import succeed with four original IDs and a closed contour, as documented in `.evidence/ponytail-followup/report.md`. Nearby source parsing already recognizes both identity keys for another PCB object family ([`board_source.rs`](../../core/src/artifact/mechanical_extract/board_source.rs#L673)).

**Contract and correction.** Current KiCad's common S-expression documentation specifies `uuid` identifiers and notes that legacy pre-6 timestamps are re-encoded as UUIDs ([KiCad UUID syntax](https://dev-docs.kicad.org/en/file-formats/sexpr-intro/#universally-unique-identifier)). The modern board export's Edge.Cuts graphics use UUIDs, and the board format documents UUID identity on graphic items ([KiCad PCB format](https://dev-docs.kicad.org/en/file-formats/sexpr-pcb/#graphic-items)). Accept a nonempty `uuid` or legacy `tstamp` when reading source identity; reject absent/empty values and continue duplicate-ID checking. Preserve the original string in the source geometry identity rather than generating a replacement.

**Acceptance evidence.** Import the same closed outline once with UUIDs and once with legacy timestamps; assert equivalent geometry and retained per-edge identities. Add missing, empty, and duplicate-ID errors. A fresh Core export followed by source import should pass; retain the existing UUID-only current-export repro as regression. This verifies the parser contract and round-trip, not every historical KiCad dialect.

**Dependencies.** Independent of the text-escaping and WRL changes. UUID and legacy timestamp fixtures should share outline geometry so only identity syntax varies.

## Scope and evidence limits

The evidence is six concrete parser/runtime/output counterexamples plus source and format-contract review. It does not establish an exhaustive geometric theorem, full CAD-kernel mathematical correctness, physical qualification of all hardware generators, broad KiCad version compatibility, or fresh manual multi-tab/offline browser acceptance. Existing browser evidence remains limited to the recorded probe/report scope.
