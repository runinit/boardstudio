## Passed public paths

- Added `Macro 2`; the accepted record used generated ID `keymap-macro-4-131077`, display name `Macro 2`, tap 30 ms, between-action wait 0 ms, and one Tap A step. Added `Macro 3` later and observed the same defaults/name sequence.
- Bound Function/SW3 to Macro 2, renamed it `Tap Macro` and later `Cadence Macro`; exported project records kept SW3's `macroId` equal to the same stable ID. The existing SW2 binding to `Reference Macro` also remained intact.
- Changed tap and between-action delay on blur; accepted values appeared in the public archive. The 10,000 ms tap boundary was accepted. Inputs over 10,000 ms for tap, between-action wait, and Wait-step delay produced Core validation feedback without changing the accepted value; a later valid distinct value saved and cleared the feedback.
- Added a step and observed Tap A defaults. Changed a step through Press, Release, Wait, and back to Tap; non-Wait choices exposed keycode A, Wait defaulted to 100 ms, and its delay accepted 250 ms. A keycode draft `A)` showed `Invalid keycode expression A)` and left accepted A unchanged; correcting with ` C ` saved trimmed C. The final macro's ordered steps were Tap A, Wait 250 ms, Release C.
- Removed steps and observed Remove disabled at one remaining step. Removed an unbound macro by its row control; Undo restored it and Redo removed it. A tap edit also round-tripped through Undo and Redo. Other macro IDs and bindings stayed stable.
- Blank macro name produced the existing Core validation message and did not change the accepted name; a valid name recovered. A 33-character fill was capped by the visible input at 32 characters, and that 32-character name saved. The descriptive name `Cadence Macro` was restored afterward.
- Switched Keymap → Layout → Keymap and Left PCB/left half → Right PCB/right half and back. The accepted macro editor stayed available and did not carry a stale selected key or the invalid name feedback into the new board scope. The same invalid-name-then-board-switch sequence was exercised through the real controls.
- Public archive export at revision 64 is `candidate-before-reopen.boardstudio` (SHA-256 recorded below). After a full page reload in the original isolated profile, the Keymap page showed the stable SW3 binding, macro name, timing fields and all three accepted steps at revision 64. A second fresh profile imported that public archive through the visible Import control and displayed the same values (`reopened-archive-ui.txt`).

## Open gates / limits

The public app offered only `Export archive` and `Export STEP`; its visible Keymap and Export snapshots had no ZMK/firmware source action. Therefore generated firmware-provider output was unavailable and remains open. I did not exercise a pending save while changing to a different document, the 128-macro/128-step UI ceilings, or the 256 expanded-cell cap through the public UI. The separate current Core native boundary run accepted 64 Wait steps and rejected 65 (`../macro-editor/current-boundary-native.log`, source SHA in the private contract); it is supporting Core evidence only, not public UI proof. This packet does not close F6K.3 or INT.2, and it makes no claim about firmware semantics or malformed imports.

The root owns build checks and acceptance. No source, Core, storage, or build files were changed for this QA; the only changes are this evidence packet. No Cargo command was run here.
