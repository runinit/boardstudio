# F6K.1 private Keymap page contract

**Status:** design contract for independent review; no implementation changes authorized by this document alone.

**Scope:** `.scratch/dioxus-keymap-layers/issues/01-keymap-projection-selection.md` only: read-only accepted-snapshot projection, layer browsing/labels, and shared-key selection in the Keymap workspace. F6K.2 binding/layer edits, macros, encoder controls, firmware export, Keycaps, and the F3.1 acceptance join remain outside this slice.

## Source-grounded reference behavior

Pinned React source is `app/src/ui/createKeymapWorkspace.tsx`, `KeymapPanel.tsx`, `KeymapLayout.tsx`, `KeyBindingEditor.tsx`, `keyBindingChoices.ts`, `keycapSettings.ts`, `Workbench.tsx`, and `useWorkbenchSelection.ts` at the F6 reference revision. `createKeymapWorkspace` derives one shared key view for the 2D Keymap canvas and the panel. Its exact membership predicate is board-visible part AND (switch-kind definition OR direct matrix member). A direct matrix member must appear in `matrix.partIds`, start with `matrix/{matrix.id}/`, and have no further `/` in the suffix. Thus `matrix/m/r0c0` qualifies through the matrix branch; an ordinary non-switch nested companion such as `matrix/m/r0c0/plate` does not. The source's independent switch-kind branch can admit a nested companion if that part has a switch definition. The issue's broad phrase “matrix companions are excluded” is therefore qualified here to mean companions are not admitted as direct matrix keys; a switch-kind companion remains included to preserve the pinned React predicate. Do not silently replace the source predicate with a universal descendant exclusion. This is a source/spec qualification to carry into paired fixtures/review.

The same key projection feeds `KeymapLayout` and the native `Selected key` `<select>`. Canvas click and Enter/Space call `selectKey(id)`, which sets React's selection-mode state to `key` and calls shared `choosePart(id)`. `choosePart` can observe the prior render's captured mode on that same event, so do not claim its first activation always resolves to a key scope. The select calls the same callback. The Dioxus contract below deliberately uses single-key Replace through the existing selection helper; paired parity must include first activation after prior Layout matrix/row/component selection and report any source discrepancy. `KeymapLayout` highlights every ID in shared selection, while the panel's selected record is the first selected part only when that ID is present in the projected key list. Search filters options by lowercased `reference + bindingTitle`; labels are `reference · bindingTitle`.

The reference map is `(document.keymap if it has layers) ?? virtual Base`. The virtual Base has stable ID `base`, name `Base`, empty bindings/sensors, and no macros; it is derived only and never written to the document. React stores the displayed layer ID as view state (`'base'` initially), resolves by stable ID, and falls back to the first layer when that ID is absent. The fallback does not rewrite the saved map or layer ID. For a persisted map, “Base” semantics mean layer index zero regardless of that layer's ID or display name; core permits the first layer to have another ID/name, and Issue 02 allows renaming it. Legacy firmware-position fallback applies to that first layer only. Every later layer uses transparent fallback for a missing binding. F6K.1 may browse existing layers and update this view state; it must not expose add, rename, remove, binding edit, macro, or encoder writes owned by later slices.

Binding labels follow the reference's `bindingTitle` behavior. For a typed binding, display keycode; `tap / hold` for mod-tap; `tap / layer name` for layer-tap; the referenced layer or macro name for layer/macro actions; and the distinct labels `Transparent` and `Unassigned` for transparent and none. Missing stable references use the reference fallbacks (`?` for missing layer, `Macro` for missing macro). For layer index zero only, when no typed binding exists, consult the active board's legacy `hardware.boards[].keyBindings[keyId]`; `&kp CODE` displays `CODE`, `&trans` is Transparent, and absent/`&none` is Unassigned. A later layer with no entry displays Transparent. Preserve saved distinctions without normalizing data: the UI intentionally displays absent first-layer legacy and explicit none alike as Unassigned, and absent later-layer and explicit transparent alike as Transparent. Typed bindings in index zero take precedence over legacy entries.

The 2D Keymap canvas labels each key with the active layer's `bindingTitle`, while reusing the reference's physical display inputs without edits: accepted scene transform pose when present, otherwise document part pose; current board keycap color/defaults; per-key size overrides and definition/part fallback sizes. React first overlays `scene.transforms[id].pose ?? part.pose` into its visible part records before calling `createKeymapWorkspace`; use the accepted scene only, never `display_preview`, for this pose override. This is a read projection; it does not call `EditKeymap`, `SetKeyBinding`, or keycap edit events. The panel's search query and active layer are presentation state only. Empty actual key membership and search no-match are separate states.

## Dioxus inputs and freshness

The root `Editor` is the owner of page composition and already reads `Runtime::model()`, `Runtime::scope()`, and the App-owned `SelectionAdapter`. Its accepted input is `ReadModel.accepted` (`AcceptedSnapshot`, including immutable document and accepted scene), with the active board from the same `ReadModel`, and the full optional `Scope` from `Runtime::scope()` (`session_epoch`, `document_id`, `board_id`, and optional `instance_id`). Do not use `display_preview` as a key-membership or selection authority. Before rendering or invoking a callback, the root must ensure the captured Scope still equals `runtime.scope()` and still identifies the accepted snapshot/document, active board, and active instance. Capture the adapter generation as well, so a stale render from a same-ID reopen or board transition cannot select into a newer view.

Projection membership is board-scoped: intersect accepted document parts with the active board's `part_ids`. Include switch-kind parts and the source-compatible direct matrix primary predicate above; do not manufacture IDs for empty cells and do not include matrix assembly descendants as matrix keys. Use accepted matrix/part definitions for kind, label, pose, and display defaults. Preserve document order for keys and layer order for layers. Keep stable part and layer IDs as callback/state values; row numbers and labels are display-only.

For each real selected-key ID, the mount's one `on_select_key(String)` callback must re-read the current Runtime model and validate Scope, generation, and current supported-key membership before acting. Resolve the current semantic context through the existing private `objects::context_for_part`; a valid scene-resolved direct primary resolves to the existing key context and a standalone switch to the component context. Route both canvas and `Selected key` through the same callback and the existing `selection::submit_canvas_selection(runtime, adapter, scope, generation, context, SelectionMode::Replace, Vec::new())` helper. That helper updates Session's existing `SelectParts` selection and the scoped `SelectionAdapter` context/anchor stamp; do not add a second selected-ID store, event, selection facade, or public visibility. When the select's placeholder is chosen, the root callback validates Scope/generation, sends the existing Session `SelectParts { mode: Replace, part_ids: [], range_part_ids: [] }` path and clears the adapter's semantic context/anchor stamp; never submit the empty string as a part ID. Existing Session leaves its `selection_anchor_id` unchanged for empty Replace; only the private anchor stamp/context are cleared, and no Session change is authorized. The source callback is shared for pointer click, keyboard activation, and native select changes.

Keep canvas activation local to each key target: click stops propagation; Enter and Space activate without causing page scroll; buttons/targets expose focus and an accessible label based on the key reference. The native search input and select retain accessible labels, native keyboard selection behavior, and the empty `Choose on the layout…` option. No click/select or layer browsing callback submits `Event::Edit`, `EditKeymap`, or any persistent edit. Selection may update Session's selected IDs/anchor only through the existing selection path; it must leave document revision, undo/redo history, durability, keymap bindings, and storage unchanged.

For a selected panel record, derive the selected key from the first Session selected ID and show its details only if it exists in the current supported-key projection, matching `activePart?.id` plus `view.keys.find(...)` in React. For canvas highlighting, use the full current selected-ID set, matching `KeymapLayout`. Selection survives workspace changes according to the shared Session state; the keymap module must not clear it on mount/unmount. On a scope transition, stale key selection, empty-select, and layer callbacks are rejected by full Scope/generation checks; projection and selection are re-derived from the new accepted snapshot.

## Private ownership and exact mount seam

Feature author may own new page-private modules such as `web/src/presentation/keymap_view.rs` and `web/src/presentation/keymap_panel.rs` (or a private `presentation/keymap/` submodule). They may define only page-private projection types/helpers/components (`pub(super)` or narrower) and local view state. They may read `AcceptedSnapshot`, `Scope`, existing `Part`/`PartDefinition`/`Matrix`/`KeymapConfiguration` types and call existing private presentation helpers. They do not own `presentation.rs`, `m1.css`, `objects.rs`/`objects/tree.rs`, `selection.rs`, Runtime, Session/application/core, contracts, generated files, or public exports.

Root owns `presentation.rs` composition and CSS. The feature-private projection builder consumes the current accepted snapshot, active board ID, and root-owned `active_layer_id`, then returns one immutable `KeymapView` with key rows, map, resolved layer, binding labels, and layer order. The concrete private render seam is `KeymapCanvas { view, selected_ids, on_select_key }` plus `KeymapPanel { view, active_layer_id, selected_key_id, on_layer, on_select_key }`; the same `view` and `active_layer_id` drive both. Root adds the private module declaration and keeps `keymap_layer_id` presentation state at the Editor/workbench lifetime so switching workspace does not recreate it. Root mounts the Keymap canvas in the center and the read-only Keymap panel in the existing Inspector slot only when Keymap is active; it passes the accepted snapshot to the private projector and passes current optional Scope, adapter generation, selected-ID set/first selected ID, active-layer ID, and two callbacks through the mount. `on_select_key` is the single shared, scope-checked selection callback described above. `on_layer(id)` updates only the root-owned stable-ID view state. Search can remain panel-local. Keymap should reuse the current shared compact controls/panels without editing their shell implementation; root handles any compact availability changes in `presentation.rs`/CSS. The Parts and Layout pages remain mounted through their current owners.

No author should change `SelectionAdapter` or selection helper contracts for this slice. If a valid React-supported key cannot resolve to a current existing selection context, stop and report the exact fixture/source mismatch for root and Standards review rather than widening visibility or adding another selection route.
