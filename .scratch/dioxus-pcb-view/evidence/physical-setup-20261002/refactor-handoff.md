# Physical setup design handoff — 2026-10-02

## Existing finding links

- **RF-006 — scope/identity:** the TypeScript physical-setup flow keeps the selected physical-instance ID separate from selected board ID. Topology transitions preserve the selected-or-board-matching primary instance and its per-instance board/controller/mechanical data, while a new split secondary receives a new identity. Keep this behavior explicit in Dioxus; board and physical-instance scopes are not interchangeable.
- **RF-009 — parity/source accounting:** reversible intent currently appears in the project-level `parameters.reversibleLayout`, eligible generator definition parameters, eligible generated-part parameters, and the right physical instance’s `flipped` field. The reference helper updates these projections together. This is confirmed source behavior and creates a synchronization/accounting burden; it is not authorization to change the schema or replace the current behavior during the port.
- **RF-001 — root lifecycle/settlement:** Standards review found that a generic edit callback is insufficient for a leaf that can be hidden/unmounted while an edit settles. The root must admit the full current scope and generation, observe the exact operation outcome slot before submit, retain feedback across remount, and distinguish accepted-document advancement from durable save. This is a required correctness boundary and a bounded mitigation; audit the broader Runtime settlement ownership only in the post-port refactor.
- **RF-009 — callable parity seam:** reversible construction relies on existing metadata-aware normalization, including a source-specific Gateron solder-only case, conditional part-parameter updates, new flipped-secondary mechanics, and defaults from the reference mechanical factory. A Dioxus port must prove a callable existing private implementation before dispatch; guessing with raw field toggles risks representation drift. No algorithm copy or public API widening is part of this migration slice.

## Evidence and current mitigation

The pinned TypeScript CodeGraph/source inspection covered `HardwareInstancesPanel`, `projectConstruction`, `main.tsx` `hardwareControls`, `createMechanicalConfiguration`, and Case Inspector source. `HardwareInstancesPanel.configure` retains primary identity/data, creates a new secondary with mechanical defaults and reversible-dependent flipped/openings/mounts, preserves shared construction and board config, and requests primary selection. `withReversibleLayout` uses generator metadata plus normalization for eligible definitions, updates conditional part parameters, and updates right-half flip state. The wired connection safety text is rendered in the Case-context `Assembly setup` details, not in setup-context controls. Both edit paths ultimately use replace-document and Session selection callbacks; Dioxus must express the same user intent through fresh root-owned construction/admission/settlement rather than letting a leaf submit a stale whole document.

The child spec requires the Dioxus port to prove the current private normalization/default callables and root settlement contract, preserve these coupled updates through the single accepted-document/edit authority, and verify retained/new instance identity, generated settings, selection, Undo/Redo, wired Case-copy placement, and save/reopen in paired browsers. Refactoring the representation is deferred to the post-port phase. These observations reinforce existing RF-001/RF-006/RF-009; no new RF ID is proposed.
