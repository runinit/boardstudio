## Current source behavior

- React `app/src/useElectricalPlanning.ts:29-37` supplies the selected board's saved mode, lock map and controller ID to `ResolveElectrical`; `applyWiring` resolves the current document, then calls `ApplyElectrical` at that document revision.
- Dioxus's production `electrical_preview_request` reads mode, locks, controller and selected board from the accepted document. Its native test verifies a revision-1 Direct request with a persisted board lock.
- `CoreEngine::handle(CoreRequest::ApplyElectrical)` checks `base_revision`, then builds a review request with the current Core document and `locks: Default::default()` (`core/src/lib.rs:271-294`). That empty request map does **not** erase project locks: `electrical::resolve` begins with the selected board configuration's persisted lock map at `core/src/electrical.rs:1001-1003`, extends it with request locks at line 1004, and then adds connection locks at line 1005. Thus the current apply re-resolution retains the same selected-board locks when the request contributes none.
- The resolver fingerprints assignments including their `locked` state at `core/src/electrical.rs:1204-1214`. Existing `resolver_scopes_board_and_honors_controller_and_locks` proves the resolver honors request locks; it does not exercise persisted config locks through the `ApplyElectrical` request branch.
- Source inspection therefore identifies a coverage gap, not a confirmed direct-request bug. No lock-bearing `ApplyElectrical` red was observed, and Issue 09 must require a green test on the current implementation rather than claim a defect correction.
- Existing `electrical::materialize` at lines 1218-1219 accepts the exact current resolved plan and checks plan revision, blocking diagnostics, board, electrical pads, generated nets and terminal projection. The F5.2d route uses this existing Core helper on the accepted `Current` plan followed by one normal strict-revision Session `ReplaceDocument`; this is an implementation choice to preserve the private accepted-plan and history owner, not a workaround for a proven Core lock defect.
