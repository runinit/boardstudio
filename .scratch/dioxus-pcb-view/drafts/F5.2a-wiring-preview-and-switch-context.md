# Draft F5.2a: PCB wiring preview and selected-switch context

**Parent:** canonical F5.2, “Electrical resolver and wiring summary.”

**Status:** contract draft for independent review; not yet published or dispatched.

## User outcome

On a PCB board with an accepted selected-board scope, the designer can inspect the current Core-resolved wiring plan and its controller, matrix/direct assignments, peripherals, available pins and findings. Selecting a host switch changes the Inspector to the same switch’s inherited-wiring and named-terminal/net view; returning to board Wiring clears selection through the existing Session selection path. The view never presents stale results as current and does not edit project/history state.

## Exact source behavior in this slice

- Host layers remain in the canvas popover owned by existing F5.1b; this Inspector owns no visibility state or layer controls. The ticket does not duplicate or amend published issues 01/02.
- With no component selected, and with a controller selected, show the board-level Wiring preview. For an absent or non-switch selected component, do not fabricate a switch Inspector; the generic component/net editing panel remains outside this slice.
- For an active selected part whose accepted definition kind is `switch`, show `reference · definition name`, current board/PCB breadcrumb, the reference explanation that switch wiring comes from its key assembly, and a `Named terminals` list. For each `PartDefinition.terminals` entry, show the first selected-board `ProjectDoc.nets` entry containing a `NetPin` for this exact part and any pad in the terminal’s pad-ID list; show `Unmapped` when no such net exists. The `Edit board wiring` action clears the current Session selection/context without changing `ProjectDoc`.
- Board nets use the React selected-board filter: include a net if its ID is in `Board.net_ids` or any net pin belongs to a part in `Board.part_ids`. Do not reuse a different board’s net or infer electrical terminal semantics from pad numbers.
- Derive controller options from board-member parts whose accepted definition is `PartKind::Controller` or has an existing controller profile. The saved board `ElectricalBoardConfiguration` supplies controller ID, mode and locks; absent configuration defaults to Matrix and empty locks. Match React PCB resolution’s `instance_id: null`; do not silently substitute the Case physical instance.
- Resolve by existing `CoreRequest::ResolveElectrical`, using the current accepted `ProjectDoc`, selected `board_id`, saved mode/locks/controller ID, and `controller_profile: None`. The board-level plan identity is `{session_epoch, document_id, accepted_token, revision, board_id, Core worker epoch}`; it deliberately excludes the component selection kind/part ID and UI workspace because React resolves by project and board, not selected component. Render only a plan whose board identity still matches. A pending plan remains eligible while the user selects or clears a switch on the same board; project/session/board adoption invalidates it. The resolver reply’s `ElectricalPlan` remains authoritative for row/column or direct assignments, peripherals, free pins and diagnostics.
- Panel values mirror existing React derivation: show controller name or “No controller selected”, mode, used/free pins, Matrix rows/columns or Direct assignments, peripheral terminals/details, and resolver diagnostics/readiness. Expose a Resolve/retry action. Show Pending/Failed/Unavailable distinctly; do not preserve an old board plan as current.
- For this read/preview increment, omit or disable Apply, manual pin assignments, locks, controller/mode editing, add-controller action, net creation/mapping, protected-remap review, existing-connection replacement, firmware keymap controls and module placement. These belong to existing F5.2/F5.3/F4/F6K workflows. Do not imply any of them succeeded.

## Private ownership seam

- Root/coordinator owns `presentation.rs` registration/mount, accepted-source query and selection route. It passes a cheap accepted snapshot handle, full current `Scope`, current selected IDs/context, current resolver state and narrow Resolve/clear-context callbacks to a private PCB Inspector leaf.
- Root/runtime/controller owns request identity and live admission: capture the exact accepted snapshot, session epoch/document/token/revision/board/Core worker identity and request ID before awaiting `CoreWorker::request`; re-read current Runtime/session state afterward and publish only if that board plan identity is still current. Do not tie a board-level plan to the active part selection or reject it just because the Inspector changes between Wiring and switch context. Verify `ElectricalResolved`, plan board/revision/instance identity. Use the existing Core worker/Session machinery; add no public API, Core type, session state or second plan/selection authority.
- Feature leaf owns only display projection and presentation-only status. It must not access mutable `Session`, submit edits, duplicate Core resolution, or manufacture assignments/diagnostics.
- Reuse the mounted private `PcbScene`/root `PcbPartHit` selection adapter. The parent alone validates scope/token/generation/current `Board.part_ids` before updating the existing selected IDs/context. The leaf uses the selected part ordering the same way React chooses `activeParts[0]`.

Suggested narrow private view state (exact type names are root-owned): `Idle | Pending{board identity} | Current{board identity, ElectricalPlan} | Failed{board identity, message}`. Keep the board source identity on every state; never turn a pending or failed old request into a current result after board/project adoption or same-ID reopen. Only one current accepted board plan is presented at a time. Selection context is separately read from the existing Session selection and does not own the plan lifetime.

## Start and retained joins

**Start after:** F5.1a’s real host scene is mounted with a current accepted board Scope and its hit/selection callback is wired to the existing Session selection; coordinator has identified the page’s existing `CoreWorker::request` entry and Runtime full-scope/current-token read needed for the private async guard.

No dependency on F5.1b host layer controls, INT.2 completion, full F5.1 parent acceptance, F4/F6K/F7, or any firmware-output workflow is required for this private plan-preview leaf. F5.2’s canonical INT.2 acceptance join remains unchanged and mandatory. F5.2’s full acceptance still includes Apply and multi-board behavior; F5.3 still owns manual pin/lock/net/protected-handoff work.

## Paired acceptance for this child

Use one identical imported Sofle v2 archive/demo in fresh paired React and Dioxus browser profiles. In each, enter Left PCB, inspect the no-selection Wiring preview and capture controller/mode/assignments/free pins/diagnostics. Select SW1 and compare its Named terminals and exact mapped net names; a pending/current board plan must remain eligible through this selection change. Activate `Edit board wiring` and confirm board context returns without losing or changing the accepted plan. Switch Left/Right PCB and project or session identity while a preview is pending; the old result must be suppressed and the new board must resolve. Test no-controller/unsupported-controller diagnostics and Retry. Assert revision, saved nets, plan application state, Undo/Redo and export inputs are unchanged by preview/selection. Record actual build source identity, fixture SHA, request/reply board identity, screenshots and any unavailable behavior. This child does not close parent F5.2 or prove Apply.

## Explicit exclusions and limits

No editable mode/controller/pin/lock/net controls, electrical apply, protected handoff/remap, connection release/replacement, firmware keymap, module source projection, Reference Board import, F8 output, Core/schema/API changes, or physical-instance electrical behavior. The async admission implementation must follow installed `Runtime`/Session/Core worker identities; this contract does not certify an unreviewed adapter.
