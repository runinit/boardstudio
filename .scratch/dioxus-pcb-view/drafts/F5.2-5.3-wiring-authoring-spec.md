# F5.2/F5.3 follow-on: contextual PCB inspectors and wiring authoring

## Problem Statement

The PCB inspector is a context-sensitive authoring surface, not one generic wiring card. On the reference app, clearing part selection shows the selected board's Wiring panel; selecting a built-in switch shows inherited wiring and named terminals with an Edit board wiring action; selecting other supported parts exposes applicable scan-mode, terminal/pad-net, and generator binding controls. The current Dioxus port has a private board resolver and read-only switch/board projections, but it does not yet provide the complete contextual Inspector or wiring-edit path. The remaining work is spread across the existing F5.2 resolver/summary and F5.3 manual editing/protected-handoff parents and must not close either parent early.

A source discrepancy also needs to remain visible: the current React `WiringPanel` receives `controllerOptions`, `selectedControllerId`, and `onControllerChange`, but does not render a controller selector when candidates exist. The canonical F5.2 story asks for controller selection. Do not claim this criterion has paired-reference proof or silently invent a new control placement. Record the discrepancy for coordinator disposition and preserve the parent criterion as open until its expected behavior is resolved.

## Solution

Finish the PCB Inspector as paired, contextual user journeys backed by the existing Rust electrical resolver, normal project edit/history operations, and Core apply/remap requests. The board-level panel remains board-scoped and owns no second project or selection authority. Component Inspectors derive their display from the accepted selected board part and existing definitions/nets. Mutations enter the normal accepted document/edit path; resolver output is only preview until the user applies it. Preserve the current React pane placement, labels, default/open states, action hierarchy, and selection-clearing behavior.

Plan four separately reviewable, agent-grabbable vertical slices after the existing F5.2a read-only preview/switch-context capability. The contextual component Inspector and board controls may advance in parallel once each uses the shared accepted board/selection projection; apply/remap, and part/net editing are separate slices so their history and stale-operation contracts can be reviewed independently.

## User Stories

1. As a PCB designer, I want the right Inspector to change with the accepted board and current selection, so I see controls appropriate to the object I selected.
2. As a PCB designer, I want clearing the selected part to show the same board-level Wiring context, so I can inspect the electrical plan without changing the board or project.
3. As a PCB designer, I want a selected switch to explain that wiring is inherited from its key assembly and show its named terminals and first matching selected-board net, so I can understand the switch's connection without editing a duplicate wiring model.
4. As a PCB designer, I want Edit board wiring to clear only the current Session selection/context and return to the same board-level panel, so I can move between object context and board context without a document edit.
5. As a PCB designer, I want selecting an eligible part to show its existing named terminal and eligible pad assignments, so I can map supported pins to existing board nets.
6. As a PCB designer, I want applicable press-input controls to offer the same Matrix key, Direct GPIO, and Unassigned choices and current eligibility restrictions, so a supported key or encoder input can be configured from its Inspector.
7. As a PCB designer, I want supported Ergogen net and anchor parameters to remain editable in the selected part's Inspector, so the Dioxus port preserves the existing reference's generator-facing authoring workflow.
8. As a PCB designer, I want to create a named board net and assign supported terminals or pads to it, so manual mapping remains possible without editing project JSON.
9. As a PCB designer, I want every saved part/net edit to use normal project validation, save durability, Undo and Redo, so authoring remains recoverable and portable.
10. As a PCB designer, I want the board panel to show the current controller, wiring mode, assignment rows, used/free pins, peripherals, and findings from the current accepted plan, so I can review what the resolver intends to do.
11. As a PCB designer, I want resolver output to refresh when accepted document or board inputs change and to reject stale replies, so the panel cannot present another board's plan as current.
12. As a PCB designer, I want to retry Resolve automatically and see pending, no-controller, resolver-error, and finding states, so failure and recovery remain explicit.
13. As a PCB designer, I want supported controller/mode choices and pin/lock edits to be represented in the existing electrical board configuration, so a later resolve uses the changes I made.
14. As a PCB designer, I want assignment conflicts to be reviewable and lock/unlock actions to affect the next resolution, so intentional pins are retained without pretending an invalid plan is ready.
15. As a PCB designer, I want an error-free current plan to apply as one ordinary undoable edit, so generated nets and assignments are saved together and can be reversed.
16. As a PCB designer, I want a plan from an older revision, board, session, or Core worker to be rejected before application, so an asynchronous result cannot modify a different accepted source.
17. As a PCB designer, I want existing-net replacement to explain affected connections and preserve unrelated nets, so resolving an automatic plan cannot silently delete unrelated wiring.
18. As a PCB designer, I want a protected PCB/firmware handoff to explain the effect of remapping and require the explicit Start a new PCB revision action, so a normal pin edit does not silently clear protection.
19. As a PCB designer, I want remap review to verify the exact current protection fingerprint and base revision, so stale or changed handoff details remain protected.
20. As a PCB designer, I want all these panels and actions to be reachable by pointer and keyboard with labels and feedback consistent with the reference, so the workflows remain accessible in the Dioxus app.

## Implementation Decisions

- Preserve Rust Core, document schemas, generated contracts, and existing `Edit` / electrical request APIs. This is frontend and private host-adapter work; do not add a public request, schema field, or visibility widening.
- Use the currently reviewed F5.2a board-level electrical resolver identity and accepted Session document. Electrical resolution is `Scope(instance_id = None)` and must remain separate from Case physical-instance scope.
- Keep board query lifetime above selected-part presentation changes. A switch click changes the contextual Inspector, not the electrical plan's source identity or request lifecycle.
- Use existing accepted-document edits for electrical configuration, per-part parameter/scan-mode edits, net creation, and terminal/pad pin assignment. Resolver plans remain previews; only the existing apply request materializes a current plan, with the Core fingerprint/revision guard authoritative.
- Preserve React selection routing: no selected part or selected controller presents board Wiring; built-in switch selection presents inherited Wiring and named terminal projection; other supported selected definitions present their contextual part Inspector. Do not create a second selection store. “Edit board wiring” goes through the existing selection adapter and only clears selection/context.
- The current React controller option callback is unused in the visible `WiringPanel` when controller candidates exist. Keep current visible control parity for this source discrepancy; do not add an unpaired controller selector. Record the parent F5.2 controller-selection requirement as unresolved until coordinator review determines whether the target is a reference correction or an explicit exception.
- For panel actions, capture and validate the accepted document/session/revision, selected board, current plan fingerprint, and exact current worker/operation identity as applicable. Show stale, pending, failure, and success outcomes without optimistic mutation. Do not introduce generic async infrastructure for these bounded actions.
- Apply uses the existing electrical apply request and returns through the normal application acceptance/edit path. Remap review uses the existing protected-remap request with the current board, revision, and exact protected fingerprint. A remap review is not equivalent to changing a pin or resolving a plan.
- Preserve ordering and filtering of board nets/parts, the first matching selected-board net for switch named terminals, eligible plated-pad rules, generator parameter support, and existing format-specific restrictions from the reference implementation.
- Existing TypeScript input/output/workspace inventories remain authoritative. The project-level mounted PCB scene and part hit selection are an acceptance prerequisite for full paired public proof; private adapter work may be prepared earlier only where its specific accepted-source and callback contracts are already demonstrated.

## Testing Decisions

- The completion seam is a paired browser journey on the same Sofle v2 project through React and the packaged Dioxus build. Compare the board-level Wiring pane, selected SW1 inherited terminals, Edit board wiring return, selected supported non-switch part Inspector, and an actual edit/apply/remap action relevant to each ticket.
- Assert externally visible control placement, text, selected values, pending/error/finding states, resulting accepted document, revision/history, Undo/Redo, and save/reopen. Do not make private component structure the acceptance oracle.
- Reuse the existing public Core electrical request tests for plan fingerprints, stale base revisions, apply/materialization and protected-remap rejection. Reuse application edit/history tests for accepted edit and durability behavior. UI tests supplement rather than duplicate Core rule tests.
- Exercise more than one board and a split physical project. The board-level resolver stays board-scoped, while physical Case selection remains instance-scoped. Switch selection on the same board must not trigger a second board plan or contaminate the other board's plan.
- Use a real placed-controller project for the positive wiring path and a no-controller/unsupported-controller fixture for truthful empty and error handling. Preserve the reference candidate predicate and its difference from resolver acceptance.
- Exercise pin locking/conflict review, input mode, terminal/pad mapping, new net, protected handoff, remap confirmation, and unrelated-net preservation only through supported fixture states and real browser controls. Do not infer manufacturing readiness from a successful UI action.
- Verify keyboard activation, focus, accessible names, desktop/compact Inspector scrolling, Light/Dark/System, no browser errors, and no document revision for selection-only context changes. Actual assistive-technology evidence remains separately identified.
- State exact source/build/project fixture identity and every blocked or unrun check. A read-only preview screenshot or a successful Rust build alone does not accept the authoring workflow.

## Out of Scope

- Any Rust Core electrical algorithm, contract, schema, exported/public API, module/firmware/PCB generator or persisted-project format change.
- Creating new catalogue controllers or changing which hardware definitions the resolver accepts.
- Changing reference UI placement, labels, interactions, selection semantics, or normal save/history behavior without a separately reviewed exception.
- Physical Case PCB design selection and per-instance PCB flip controls; those are covered by a small independent F5.6 follow-on contract.
- Closing canonical F5.2/F5.3, F5.1, INT.2, or global F5 acceptance. The physical setup guide's “Review controller & wiring” navigation is a separate guide-owner join that must reach the actual PCB board-level panel.
