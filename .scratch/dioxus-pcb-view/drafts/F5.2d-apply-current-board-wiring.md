# Draft F5.2d: Apply the current selected-board wiring plan

**Parent:** F5.2 — Electrical resolver and wiring summary. This child does not close F5.2/F5.3, F5.1, INT.2, or any canonical parent acceptance join.

## User outcome

From the selected PCB board's Wiring Inspector, the designer can apply the current Core-resolved Matrix or Direct GPIO plan. The exact current plan becomes the selected board's generated electrical nets and matching generated-terminal assignments through one normal accepted edit. The designer can undo/redo the edit and confirm it after save/reopen.

## Proven capabilities and bounded route

The current private Editor path already provides an accepted board-scoped `PcbWiringSource`, a board-level `PcbWiringResolution::Current { identity, plan }`, a Core-resolved `ElectricalPlan` keyed by accepted session/document/token/revision/board/worker identity, and a typed owner that admits an exact `ReplaceDocument` proposal, registers its `OperationId` outcome before submitting one strict-revision normal edit, and settles only after durable `SaveCommitted`. `boardstudio_core::electrical::materialize(&mut ProjectDoc, &ElectricalPlan)` is an existing callable Core-owned materializer; it checks plan revision/diagnostics/board and electrical pad validity, removes only that board's generated electrical nets, synchronizes generated terminal parameters, and writes the existing mode/controller/assignment projection.

The feature-specific path is: revalidate the current accepted source and current plan identity synchronously; clone that accepted document; call the existing Core materializer once with the immutable current plan; then submit the resulting proposal through the already-reviewed `ReplaceDocument`/Session outcome owner. There is no async gap between validation/materialization/submission; the Session's strict base-revision admission rejects a queued proposal if the accepted revision moved. No second document/history owner, request type, schema, public API, or Core algorithm copy is required.

The direct `CoreRequest::ApplyElectrical` re-resolution supplies an empty request lock map, but `electrical::resolve` merges the selected board's persisted locks before request locks. Exact-source review found no confirmed direct-request defect; draft Issue 09 adds direct request-level coverage for that behavior. The Dioxus route below is a private accepted-plan choice that uses the existing `electrical::materialize` helper and normal edit owner, not a workaround for a proven Core defect.

## Contract

- Present `Apply wiring` in the same board-level Wiring action group and placement as the pinned React reference. Do not show it in switch or generic-part contextual Inspectors. Keep controller/mode, assignment editing, connection replacement, and protected-remap controls outside this child.
- Enable Apply only for the exact current selected-board resolution when its board ID, plan revision/mode and `WiringPlanIdentity` match the current accepted document/source; the Editor is Ready and Saved, the active workspace is PCB, and no preview or gesture is active. A failed, pending, absent, old-token/revision, wrong-board or wrong-worker plan is not actionable.
- Capture the full current `PcbWiringSource` UI identity separately from the selection-independent plan identity. Before materializing, rederive and compare the accepted source, current board scope, workspace, selected part/generation and resolver identity. Selection changes reject a retained callback even though the plan itself remains board-scoped.
- Call the existing `boardstudio_core::electrical::materialize` on a clone of that exact accepted document and exact immutable current plan. Do not resolve a different plan, infer controller/lock state, permit draft findings, duplicate materialization logic, or mutate the accepted document optimistically.
- Submit exactly one existing `Event::Edit`/`EditOperation::ReplaceDocument` commit at the captured base revision, target the selected board, and register/retain the exact operation outcome before submission. The Session is the sole accepted-document, durability and undo-history authority.
- Show success only when that operation completes and the accepted Session snapshot equals the exact materialized proposal at an advanced revision with `Durability::Saved`. Rejection, stale revision, blocked recovery, cancellation, executor failure, materialization failure or persistence failure keeps the prior accepted document/plan visible with honest feedback. After success, the old plan ceases to be current and the Editor-lifetime resolver requests the newly accepted revision/mode.
- Core materialization's current behavior is authoritative: it replaces only generated electrical nets for the target board, preserves manual/unrelated nets and board data, synchronizes generated terminal parameters, and projects existing mode/controller/assignment state. No remap or protected handoff is authorized by this action; related diagnostics stay blocking.
- Verify one accepted revision/history entry, exact operation settlement, Undo/Redo, save/reopen, second-board/unrelated-net preservation, selected context staleness, non-actionable currentness states, and errors. Public paired evidence must show the action and result in both React and the exact packaged Dioxus PCB journey, with same archive/source/build identity.
