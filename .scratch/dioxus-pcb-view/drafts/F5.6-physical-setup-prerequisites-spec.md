# F5.6 physical-setup prerequisites — proposal and Editor ownership

## Problem Statement

The existing F5.6a setup ticket is correctly gated. Dioxus has an existing Rust preset for initial mechanical settings and an existing browser-packaged Ergogen normalizer, but no approved private path that applies reference reversible-construction policy to accepted project definitions and eligible part parameters. The Editor also has no assigned lifetime owner for setup topology intents, their submitted outcomes, and the accepted primary-instance selection. Implementing the setup controls before these two boundaries are explicit risks stale full-document replacement, stale selection, Gateron construction drift, and lost edit feedback.

## Solution

Add two bounded child slices under the existing F5.6 parent, in dependency order:

1. Provide one private, tested proposal builder that consumes an immutable accepted project snapshot and a typed physical-setup intent, reuses the existing bundled normalization and mechanical-default callables, and returns a proposed document without submitting it or changing Session state.
2. Add the unconditional Editor-lifetime physical-setup owner and connect the Dioxus setup controls through typed intents. The owner admits the full current scope, reserves the exact operation outcome before submission, settles its terminal result, and reconciles board/instance selection only from a still-current accepted proposal.

The existing F5.6a paired-journey ticket remains the user-visible acceptance target. These child tickets satisfy its previously recorded dispatch gate; they do not close F5.6a, alter its start edge, waive its paired browser/history/reopen evidence, or change any F5.6/F5.8 acceptance join.

## User Stories

1. As a keyboard designer, I want setup proposals to start from the accepted project I am currently editing, so that an outdated screen can never overwrite newer work.
2. As a keyboard designer, I want the supported Ergogen definitions to be normalized through the packaged implementation when reversible construction changes, so that the saved generator inputs match the reference behavior.
3. As a designer using the Gateron KS27/KS33 footprint, I want reversible construction to select the reference’s solder-only behavior, so that the generator does not retain an incompatible hot-swap socket.
4. As a designer, I want each generated part’s reversible parameter changed only when that part already carries the reference-supported override, so that custom and unrelated part state remains intact.
5. As a designer, I want reversible intent written to the project-level `reversibleLayout` parameter, so the setting survives reconstruction and reopen consistently with generated definitions and instances.
6. As a designer creating physical instances for a project with no instance-specific mechanical settings, I want existing board-level mechanical configuration or the supported default factory used, so that a newly selected assembly starts with the expected values.
7. As a designer enabling reversible layout, I want every physical instance’s flipped state recomputed by the reference policy, so that only right-half instances are flipped while the option is enabled.
8. As a designer splitting a project while reversible layout is active, I want the new right instance initialized flipped with the reference mechanical opening/mount behavior, so that it is internally coherent from its first accepted revision.
9. As a designer, I want the primary instance’s stable ID, board, controller, authored mechanical settings, and shared construction retained (or initialized from the resolved mechanics if absent), so that changing topology preserves my work.
10. As a designer, I want setup choices to be represented as typed intents instead of mutable whole-document snapshots, so that an event emitted by a stale or hidden panel cannot replace the current project.
11. As a designer navigating between workbenches during an edit, I want one Editor-lifetime owner to retain pending feedback and settle the exact edit, so that hiding a contextual panel does not lose its result.
12. As a designer, I want a failed, stale, superseded, busy, or identical-retry request handled against its exact scope and operation, so that errors do not corrupt or masquerade as accepted state.
13. As a designer switching from an instance that is removed during a topology change, I want the primary instance selected only after its proposed document is accepted, so that selection never points to an uncommitted ID.
14. As a designer, I want acceptance and durable save reported separately, so that the UI does not claim the new setup will survive reopen before persistence succeeds.
15. As a designer, I want these changes to use normal document history and survive Undo, Redo, save, and reopen, so that setup behaves like every other accepted project edit.

## Implementation Decisions

- Keep the proposal builder and its provider calls private to the page binary. It does not widen `boardstudio_web` public APIs, serialized contracts, or project schema.
- Reuse the page’s existing packaged Ergogen module and exact `isErgogen`, `parameters`, and `normalizeDefinition` path already used for catalogue construction. Expose only the smallest `pub(super)`/private-module adapter needed for accepted project definitions; do not duplicate JS normalization, parameter metadata, or generator algorithms.
- Reuse the existing Rust `case_settings::initial_settings` implementation for new board mechanical defaults. Preserve the retained instance’s mechanical settings first (the selected instance, falling back to the first instance matching the selected board), then matching canonical board settings, then use that factory, in the same order as the pinned TypeScript behavior.
- For an intent that changes reversible construction, process accepted definitions through the metadata-aware normalizer; set eligible definitions’ reversible parameter; retain non-Ergogen and unsupported definitions; update each part’s reversible override only when the reference’s conditional-presence test is true. Preserve the Gateron solder-only normalization.
- A reversible intent also writes the project-level `reversibleLayout` parameter in the same proposed document, keeping this persisted source setting aligned with normalized definitions, conditionally present part overrides, and instance flip projection.
- Build topology from the immutable accepted snapshot exactly once for each actual intent. The already-active topology button is a no-op. A topology transition preserves the chosen-or-board-matching primary instance's existing `flipped` value and authored fields, as well as board electrical configuration, controller, and non-owned project fields; it preserves existing `sharedConstruction`, or initializes it from the resolved retained mechanics when absent. It resets split communication to the reference default (wireless/none), initializes only a newly created right peripheral from the current reversible setting, and clears that new flipped secondary's openings/mounts. A reversible-layout intent alone writes the project-level reversible parameter and recomputes every instance's `flipped` flag by the reference rule. A transport-only intent changes only transport. Add a fresh right-peripheral ID only when the split transition requires it. Do not submit `ReplaceDocument` from the leaf.
- Keep one unconditional root owner under the existing Editor lifetime. It captures document/session/board/instance Scope, accepted snapshot token and revision, editor/scope generation, and the live selected-instance identity. It rechecks these after asynchronous normalization and immediately before submission.
- The root obtains an operation ID and registers/observes its exact `OutcomeSlot` before submitting the existing normal Edit event; it settles that same operation only after a matching terminal outcome. A callback failure before submit is a local rejected request, not a terminal Session outcome. Do not treat preflight admission as settlement.
- Keep pending feedback rooted independently of the setup leaf mount. Superseding context, hide/unmount, busy state, retry with the same intent, accepted-token advancement, and durability changes must retain or settle the original request without confusing it with a later request.
- Reconcile the primary physical-instance preference and board navigation only after the exact proposed document has been accepted and the captured owner/scope remains current. A failed or stale proposal must never select a generated ID. Use the existing selected-instance preference and Session-derived active instance; no second selection/document store.
- The shared `presentation.rs`/Runtime/feature-registration integration point remains coordinator-owned. The author receives a specific typed-intent mount slot and root file allocation before coding; do not race-edit shared composition or CSS.

## Testing Decisions

- Ticket 05 verifies the real packaged normalization callable with project-owned Ergogen definitions, not only catalogue defaults or a mocked normalizer. Assert non-mutation of accepted input, exact normalized definition/part results, project-level reversible parameter, Gateron solder-only behavior, unsupported/custom preservation, default mechanical creation, topology preservation of a previously flipped primary and existing shared construction (or mechanical fallback if absent), new-secondary initialization, transport-only preservation, and reversible-only all-instance recomputation.
- Ticket 06 verifies the root owner with real Session/Runtime accepted snapshots and operation settlement. Assert the exact operation is observed before `Edit`, only its matching terminal result settles it, selection changes only after accepted document admission, and failures/stale/retries/unmount/durability cannot orphan feedback. Capture traces and evidence for the shared acceptance journey; do not create a second paired suite.
- F5.6a remains the single paired public journey: the same fresh layered Sofle archive in the pinned TypeScript and candidate Dioxus apps, identical topology/transport/reversible actions, Case-context wired guidance, assembly selection, Undo/Redo, and save/reopen. Tickets 05 and 06 contribute their assertions and owner/operation traces to this journey. Compare visible control placement/state and accepted project outcomes, and record build/fixture identities plus screenshots once at the F5.6a join.
- Include a legacy project with no physical instances/configuration and a reversible-capable project containing Gateron. Cover a newly created right instance while reversible is on, switching back to one keyboard, removed selected secondary, failed persistence, hidden setup panel, board/session supersession, and retry.
- Run relevant native tests, strict WASM/page checks, and the actual page/browser journey. A WASM target compile is not proof the JS normalization executes, and a unit test alone is not public UI parity evidence.
- Retain every inherited shared acceptance gate, exact React UI behavior, paired journey, and parent completion criterion. Report checks not run and limits honestly.

## Out of Scope

- Changing Rust engine semantics, the project archive/schema, public API/member visibility, CAD generators, hardware electrical behavior, or mechanical design policy.
- General-purpose command framework, generic document replacement service, shared state-store redesign, or speculative refactoring.
- Case viewer/model readiness, board association/flip editing in the Case Inspector, routed PCB assets, PCB rendering, and electrical wiring; these remain in their existing F5/F7 slices.
- Closing F5.6, F5.6a, F5.8, or any F7 integration join.

## Further Notes

The current branch already contains the reference-compatible Rust mechanical initializer and a private parts-catalogue helper that invokes the packaged normalizer. The gap is reuse for accepted project definitions and ownership/admission for physical setup intents, not absence of the generator implementation or Session operation primitives. The full source grounding and exact current commits are in the PCB-owned evidence handoff.

Stable takeaway IDs remain RF-001 (shared Editor/runtime and request lifetime), RF-006 (board versus physical-instance scope and selection lineage), and RF-009 (source-to-projection parity accounting). No new RF ID is proposed. This prerequisite plan does not modify the 62-parent graph or shared run/refactor ledgers.
