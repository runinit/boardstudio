# F3.2 matrix and component authoring source contract

**Audit date:** 2026-10-02. Read-only source inspection; no Rust/web implementation or canonical graph change.

## Canonical boundaries

F3.2 is `Matrix and component authoring`, with canonical `start_after: [F3.1]` and no acceptance joins. Its original scope is: create preset/custom matrices and mirrored pairs; preview/place/cancel; add standalone components; edit cell overrides and matrix setup using existing commands. These drafts are children of F3.2 for execution tracking only. They do not modify the 62 canonical tasks, start edges, acceptance edges, or F3.2's original acceptance criteria. T1-10/T1-11/T1-12 are F3.1 children, not new direct graph edges for F3.2.

The pinned React surface is in `app/src/ui/Workbench.tsx`, `MatrixSetupPreview.tsx`, `MirroredPairSetup.tsx`, `ExistingHalfSetup.tsx`, `existingHalf.ts`, `createWorkbenchPlacementActions.ts`, `createProjectActions.ts`, `placementState.ts`, `MatrixInspectorPanel.tsx`, `MatrixInspector.tsx`, `matrixPresets.ts`, `matrixResize.ts`, `workbenchGeometry.ts`, and `workbenchTypes.ts`. The present Dioxus `web/src/presentation.rs` projects and selects matrix/key/component entries and renders the current canvas; its inspected public Layout route has no equivalent matrix setup, placement form, parts placement workflow, or matrix/cell inspector.

## Existing producer behavior and Rust authority

- **New matrix:** Objects → Add object → Matrix opens Rows, Columns, key assembly preset, a live count/shape preview, origin-at-(0,0) guidance, Create matrix and Cancel. Valid dimensions are positive integers with `rows * columns <= 4096`. Submitting this guided form commits the matrix at the origin and expands/selects it; it does not enter a placement ghost. The separate Parts-library assembly action begins a 1×1 matrix placement ghost; arrows/pointer position it, click/Enter commits, Escape cancels. Keep these two entry paths distinct. Existing `EditOperation::SetMatrix` and core matrix/layout synchronization own durable state and history.
- **New linked pair:** the form takes distinct left/right names, positive rows/columns with the same 4096-cell limit, key assembly preset and finite non-negative edge gap. Preview placement shows both halves and the mirror axis; cancel leaves the accepted document alone. Commit uses the existing `CreateMirroredPair` operation with two layout identities and distinct matrix identities. Existing mirrored layout behavior propagates linked changes and allows an explicit local component substitute or unlink.
- **Mirror existing half:** only unpaired matrices are offered; the user may mirror all eligible matrices or one selected source about a finite X axis. The original remains. The existing helper creates the linked copy from accepted document data, and the change is submitted through the current replacement/history path. This differs from creating a new pair and should be exercised separately within the same linked-layout vertical ticket.
- **Standalone component:** Add object exposes grouped/searchable available definitions and a destination of Board/ungrouped or a named layout. Choosing a definition begins an in-canvas placement at the current view center; pointer or keyboard placement supports the existing snap/Alt behavior, Enter commits, Escape cancels, and arrow keys move the pending item. Reversible Ergogen definitions are normalized to the current construction before placement. Commit retains definition, project part, selected board, outline part-envelope and optional layout membership, then selects the placed component and opens Inspector. The reference helper produces one accepted-document replacement. Existing Rust edit/session history remains authoritative.
- **Selected key component:** Add object → Parts always starts standalone canvas placement. Separately, in the Parts workspace, selecting a definition while the accepted selection scope is a matrix key calls the reference `placeLibraryDefinition` path: an applicable switch/input definition replaces the key assembly; another definition appends an attached assembly. With other selection scopes that Parts action starts standalone placement. The cell inspector can replace/remove attached members. On linked halves the current linked/local component policy is explicit. Matrix/key structural changes use existing `SetMatrix`; existing renderer projections remain the geometry source.
- **Matrix/cell inspector and actions:** matrix fields include name, dimensions, pitch, assembly/switch preset and orientation, diode direction, edge gap and matrix deletion; Add object also offers Add row/column for a selected matrix. “Duplicate design as variant” is a root-owned project action: it clones the whole project under a new ID/name, opens the copy, applies the selected matrix preset and saves it. On failure it reopens the original project and reports the error. Cell fields include enabled, switch assembly, attached-component replacement/removal and local transform. Existing object transforms, offsets, splay/origin, constraint/align/nudge and direct manipulation remain in F3.3; keycap sizing/reflow remains F6C.3; outline behavior remains F3.4.

Existing core operations in `core/src/model.rs` include `SetMatrix`, `CreateMirroredPair`, `AddPart`, `RemoveMatrix`, `MoveParts`, and `ReplaceDocument`. Core `SetMatrix` admits supplied definitions, updates matrix state and synchronizes linked layout state; `CreateMirroredPair` validates linked identities and updates through the existing edit/history path. No new schema, public API/type/member, edit operation, geometry rule, CAD algorithm, or duplicated state is required by these UI tickets.

## Private ownership and sequencing

Feature authors should own disjoint private presentation modules for matrix setup, linked layout forms, standalone component placement and structural matrix/cell inspection. Root/coordinator retains the `presentation.rs` route mount, current accepted read projection, ID allocation, typed callback translation into existing operations, selection/focus/navigation closure, global CSS, Runtime, and build/package integration. Do not let children write root callback wiring or invent ID generators. Each implementation must demonstrate the current public Dioxus route after root integration; a helper-only completion is not a vertical slice.

All four draft tickets retain the true F3.2 canonical start gate F3.1. No child-to-child dependency is added: their behavior and private form ownership are distinct, while root mounts callbacks serially. The component placement child owns both source-defined entry points: Add object → Parts for standalone board/layout placement, and the Parts workspace action for selected-key assembly/attached-component insertion. The inspector child owns viewing/replacing/removing attached members after insertion. F3.2 acceptance remains its own complete slice; F3.3/F6C.3 and F3.7 joins remain unchanged. F8.1's existing ready-for-agent Export UI ticket is separately independently startable from accepted INT.1 and does not need a duplicate child ticket.
