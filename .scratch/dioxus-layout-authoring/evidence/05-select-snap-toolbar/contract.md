## Capability-level start proof and seams

This child can begin without declaring F3.2 or the F3.3 parent complete. F3.3 is already defined with `start_after: [F3.1]` and `acceptance_after: [F3.2]` in `tasks.json`; those graph edges must remain unchanged. The implementation should report the capability evidence below and keep the full F3.3/F3.2 acceptance joins open.

1. F3.1 supplies active-board selection scope, selected real IDs, current board/session identity, canvas-to-selection synchronization and cancellation for stale context. T1-10 supplies the selected tree context semantics; this child reuses the same selection/session rather than duplicating it.
2. A real REVIUNG41 matrix fixture and real standalone parts/constraints exist in the selected board. No fake matrix, empty-cell part, dummy reference target or synthetic constraint is needed to render disabled/enabled UI or exercise a real edit.
3. Existing operation/authority paths cover the toolbar actions: `Event::GestureBegin/Sample/End/Cancel`, `application::interactions::normalize_drag`, core `EditOperation::{MoveParts,SetMatrix,SetMatrixSplay,SetConstraint,RemoveConstraint}`, and Session undo/redo. Core remains responsible for geometry, document validation and history; Session remains the selection/gesture/history authority. The current gesture protocol encodes Off as fraction `0`, matrix-pitch fractions as positive values and millimeter increments as negative values; `GestureBegin` snapshots pitch, fraction, geometry-snap and optional gap, while Sample/End only provide updated positions and Alt. Root must source a fresh current matrix pitch (and the existing 19.05 mm fallback when no matrix owns the target), then copy the already-validated settings into that exact Begin. Use `gap=None` while geometry snap or envelope-gap snap is disabled; otherwise use a finite nonnegative override, falling back to the selected matrix's `edgeGap.x` or 1 mm as React does. Keep the gap text draft editable even while its toggle is disabled by turning geometry snap off. Read and clear `ReadModel.snap_guide` through the existing read model; do not re-run `normalize_drag` in the UI. These existing fields establish standalone/world-position snapping only: the current Dioxus `GestureBegin→normalize_drag→MoveParts` route does not establish React's matrix-origin/row-offset/column-offset/cell-offset edits or local snap coordinate basis described above.
4. The current concrete Dioxus integration seam is `presentation.rs` plus the private Layout composition in `presentation/layout_workspace.rs`; use the existing lifetime/current-scope subscription and shared root adapters. Toolbar children receive read-only current-context projections and typed callbacks; they do not own a copy of the document or a second selection store. The root Editor owns one transient `LayoutSelectionKind` (`Matrix/Row/Column/Key/Part`) preference used by the Select control and every later unmodified canvas click/drag target resolution. This is distinct from `application::SelectionMode` (`Replace/Add/Toggle/Range`), which continues to carry pointer modifiers. A toolbar mode change updates the active valid matrix context immediately when one exists; without a current selection it changes only the preference. For canvas cell/part hits, the root converts the source `TreeContext` through the selected kind and current `resolve_selection` before dispatch. Matrix/Row/Column use current accepted scene cells and live board membership (including enabled linked companions); Key targets the real primary member when present; Part targets only a live real part. An empty cell remains a semantic Key context with `Some(empty)` selection and no invented part identifier. Plain pointer hits use the chosen kind; existing Shift/Ctrl/Cmd modifier selection behavior stays on its existing path and is not redefined here.
5. The root owns transient `LayoutSnapSettings` (fraction, geometry-snap enabled, envelope-gap enabled and editable override draft) and passes them to the toolbar. The canvas click/drag resolver reads the same current preference and settings. A newly admitted drag captures settings exactly once into `GestureBegin`; subsequent preference changes do not rewrite an active gesture, while Alt continues to be sampled on pointer movement/release. Use the accepted owning matrix pitch when available and preserve the current 19.05 mm × 19.05 mm fallback for non-matrix targets. Keep current Workspace/Scope/generation freshness checks at menu and canvas admission. Current Layout drag is already operational but hardcodes settings, so preferences are not behavior until copied into Begin. Keeping unresolved Transform/Align/constraint controls hidden remains required until their guards and edit routing exist.

No `CONTEXT-MAP.md` is present in the restored checkout; this is also recorded in the F3.3 parent. Domain behavior remains grounded in `CONTEXT.md`, `CAPABILITY-MAP.md`, ADR 0003, `CONSTRAINTS.md`, and the pinned React/core/application sources listed here. No member/API widening, new geometry algorithm, Runtime/Event redesign, or Core change is required by the observed toolbar gap.

## Recommended child boundary and acceptance journeys

The existing F3.3 is an oversized parent and has no registered implementation children. It should remain intact. Recommended first child: **F3.3a Layout selection and snap toolbar**, limited to the Select scope menu, grid increment, geometry/gap snap controls, current status/guide, and the operational footer's world-coordinate readout. Fit/zoom/finding controls should remain their existing independent navigation/finding capabilities; Transform, Align and Constraints remain distinct later vertical children under F3.3, not fake or disabled decorative controls.

This first child is a vertical slice through the current tree-selected context, persistent canvas selection preference, visible snap controls, the existing Session gesture adapter, the same Rust snap policy, guide/status feedback and public-browser verification. It does not claim Position/rotation, matrix transform, alignment, constraints, Fit, or finding parity. Keep existing F3.3 acceptance unchanged and add the child only after issue-graph review confirms there is no already-published duplicate.

Required paired public journeys on the same saved REVIUNG41 fixture:

1. **Select/context journey:** select the existing right-keys matrix from tree/canvas; choose Matrix, Row, Column, Key and Part; verify active semantic context/IDs and Inspector synchronization, and verify the next unmodified hit uses that mode. This proves selection target resolution only; it does not claim matrix/row/column/cell drag-operation parity. With no selection, change mode and prove the next hit uses it. Switch board/workspace during a stale callback and verify it cannot retarget the new context. Use the real populated cell for Part selection; separately prove that an empty cell remains a semantic cell context without inventing a component ID. Keep current Shift/Ctrl/Cmd selection outcomes unchanged.
2. **Snap/drag journey:** select a real standalone component on the board (not a matrix member); choose ¼u, 1 mm and Off; verify the unit fraction uses the established 19.05 mm pitch fallback for a target with no owning matrix, millimeter values use world units, geometry snap can be toggled, and the editable gap override affects the captured `GestureBegin` only while both geometry and gap snap are enabled. Alt sampled during the gesture bypasses snapping. Compare preview, committed coordinates, guide/status and exactly one Undo in React and Dioxus. Escape/cancel, pointer-cancel, lost capture and board switch must clear guide and leave saved geometry unchanged. Include a stationary click and sub-threshold nonzero drag to retain existing F3.3 interaction gates. Do not use a matrix, row, column, key or assembly-component drag as evidence for transform/local-snap parity; keep those paired traces open in F3.3.
3. **No false controls:** Verify Transform/Align/Relationships remain absent in this first child until their complete adapters are assigned. The later transform journey must use a selected matrix/column to splay and pick origin, then Undo; the later alignment journey must align a real unlocked selection to a same-board independent reference and prove it did not move the reference; a locked/driven target and splayed row must show the exact disabled explanation and issue no edit. Constraint journey adds/edits/removes a real offset or mirror relation and verifies driver status plus Undo/redo.
4. **Environment:** capture desktop and compact viewport, light and dark theme for implemented controls, keyboard operation and focus, browser console, final project geometry/history and current scope. An isolated profile used here has no persisted-state proof; implementation QA must use the project’s public test/browser procedure.
