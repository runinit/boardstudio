## Dependency audit: preserve joins, remove only proven capability waits

The graph already models the right distinction in its schema. The execution risk is interpreting `depends_on` (the union) as the start gate, or treating a parent’s final paired/browser acceptance as the prerequisite for every child authoring action. Root reports the user has approved **proven capability-level child start gates**. Apply that narrowly: a child may start only after its named minimum capability is evidenced at a stable seam; the original parent acceptance and all downstream `acceptance_after` joins still gate completion. Do not make a blanket “start everything” waiver and do not rewrite parent criteria.

### Best-supported candidate: Layout projection versus full F3.1

F3.1’s full acceptance includes tree/canvas synchronization, Ctrl/Cmd toggle, Shift rectangular range anchored to the right scope, board/matrix invalidation, desktop/compact focus behavior, and history neutrality. Current evidence indicates a subset already exists: the candidate has visible hierarchy/board selection and selected-context projections (T1-10/T1-11/T1-12 evidence; context summary mounted at `e510dd4c`). That can be sufficient to let a private F3.2 author build against an agreed board/matrix/component identity and existing core matrix/add-part operations, even while F3.1’s outline navigation, anchored range/modifiers and paired compact proof remain open.

Recommendation for the scheduler, subject to exact artifact check in the Layout packet: replace the **operational start test** for F3.2 (and any F3.3/F3.4/F3.5/F3.8 child whose contract needs only basic active-board/project identity) with a named capability proof such as “stable active board + matrix scope and selection identity available from candidate read model; authoring callbacks route through accepted operations; no cross-scope stale state.” Retain the F3.1 final parent and any explicit acceptance joins unchanged. Do not release children that need outline target navigation or anchored range behavior until those specific capabilities are proven. The smallest valid gate may be the already mounted scoped projection, not the whole F3.1 parent.

F3.3 and F3.8 already demonstrate the intended graph pattern: F3.3 starts after F3.1 and only joins F3.2 for acceptance; F3.8 starts after F3.1 and joins F3.5 for acceptance. That is evidence the graph does not require all sibling completion before independent work. F3.7 is deliberately an aggregate acceptance task with broad starts/joins; it should remain a final join, not a lane starter.

### Bottleneck findings

The current ownership text makes the integration coordinator/root the sole editor for shared presentation, Runtime, global CSS, build files, and shared mount/composition. Shared-viewer issues similarly reserve page registration/composition/build work to root. That protects shared-state boundaries but creates a serial lane if every stream needs bespoke edits there. Q4 now authorizes a **limited private workbench composition extraction**; use that approved seam to expose stable private slots/props so each of the six feature authors can own disjoint private modules, while one merger owns the composition file and integrates small changes continuously. Keep Session/Core/public API authoritative and broad refactoring deferred.

Suggested role model: six persistent stream queues with a domain author, a different source/spec reviewer, and a paired UI verifier; a shared composition merger controls only integration hotspots. Authors own one stream-private module set, reviewers verify behavior/contract without editing the authored file, and verifiers use the shared current build to run an actual named React/candidate journey. Feature work does not wait for another stream’s final acceptance unless a canonical join says so. Use short serial windows for composition/Runtime/CSS, with a reviewed private contract before the author starts, instead of routing all stream work through one feature-implementation queue.

## Execution proposal for user review

1. Freeze a one-page behavior map per stream from the paired browser audit: entry/menu path, exact pane/tab and labels, empty/default state, user actions, feedback, and durable/history consequence. Separate “observed in React” from “currently implemented/candidate-wired.”
2. Resolve/retain the minimum private composition and scoped selection contracts. User-approved Q4 is limited to composition extraction; do not open a broad framework refactor.
3. Schedule authoring by **capability-ready**, not full-parent-complete. Each exception names the capability proof and artifact; if absent, the child waits. Canonical parents and final acceptance joins are unchanged until explicitly adopted after the grill.
4. Let six stream owners implement disjoint vertical slices continuously. Integrate behind the private composition seam as soon as each source/spec review clears; do not accumulate six isolated branches for a late merge. One integration owner serializes shared file changes and verifies no stream displaced another’s UI.
5. Close a bounded ticket only after its code is implemented, wired on the current route, and a paired public journey matches source behavior. Where relevant, include Undo/Redo, save/reopen/archive and error/retry; parent-specific broader gates and joins remain open until separately exercised.
6. Keep the Project-menu support slice shell-owned and visible to all stream tests. Track paired journeys per stream, not only by module/test counts.

## Decisions for the final execution grill

- Which exact active-board/tree/context capability is enough to start each F3 child while F3.1 remains open? The Layout paired audit should provide the minimum evidence and exceptions.
- Does the limited private composition extraction expose six stable slots in one step, or is the first stream the proving slice and others follow immediately after its mount contract review?
- Where does the Project menu appear and which exact React actions belong to it versus dedicated workspace controls? Assign one owner and verify all six routes without turning it into a seventh stream.
- What counts as a paired journey for each persistent stream: fixture, route, visible pane, edit/revert/history, durable reopening, and any required keyboard/compact checkpoint?
- What is the concurrency limit for authors versus independent review and public QA? Six persistent owners need not mean six simultaneous edits to shared integration files.

Until those answers are adopted, this report recommends **no graph or ledger mutation**. Preserve all 62 canonical parents, child histories, RF findings, documented blockers, and every existing `acceptance_after` join.
