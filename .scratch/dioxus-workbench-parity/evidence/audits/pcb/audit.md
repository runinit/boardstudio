# PCB workbench parity audit

Audit date: 2026-10-02. This is an exploration/source audit only: no repository source was edited, no ticket status changed, and no Cargo/build command was run. Screenshots and the browser action record are in this directory.

## Finding

The largest immediate gap is a missing mounted PCB workbench, not a missing Rust PCB domain. React displays a scoped PCB scene and its contextual wiring inspector; Dioxus routes the PCB tab into an explicit “not available yet” placeholder. The Dioxus shell already has a live project, board selector, tree, selection/session/history, Runtime, Core worker, and normal edit path that a private PCB composition can reuse. The next bounded slice should connect an actual accepted board projection to a PCB canvas and its selection/context callback; it should not wait for the whole F5 portfolio, F3 completion, or the firmware output workflow.

## Source and capability trace

Checkouts were pinned to React 5a472a9426e6e38993361da402cd4ec730feb369 and integration 89b1de8a28fdf02db91d972c90a69235bfbbbffb.

Reference CodeGraph exploration established the path Workbench → usePcbWorkspace → WiringPanel and Workbench → WorkbenchLayers/CanvasLayers; main.tsx supplies the plan and FirmwareKeymapPanel callback. Relevant exact locations:

- app/src/ui/Workbench.tsx:1027 routes PCB to pcbWorkspace.panel(); :1337–1351 renders PCB contours/parts/modules; :1377–1386 composes standard and module layer controls; :1403 mounts BoardReferencePanel in Design/Case.
- app/src/ui/usePcbWorkspace.tsx:21–51 contains scoped part/net edits and wiring-panel composition; app/src/ui/WiringPanel.tsx owns wiring controls; app/src/ui/FirmwareKeymapPanel.tsx:12–31 is the key-position control. app/src/main.tsx:115–130 supplies selected board, wiring status and current plan projection.

- app/src/ui/BoardReferencePanel.tsx:84–123 parses/imports with PreviewBoard, stores content-addressed bytes and rejects a late result if the project revision or board changed.

Candidate source evidence:

- web/src/presentation.rs:459–495 has common workspace navigation. :521–530 defines the literal PCB placeholder. :601–645 derives the current selected scope/workspace and limits Inspector workspaces to Layout/Parts/Keymap/Case. :2122–2143 renders Layout/Keymap/Case/Export then falls through to the placeholder; :2145–2223 composes Inspector contents without a PCB branch.

These are domain capabilities, not a Dioxus panel.
- core/src/model.rs:1422–1432 has SceneDelta.module_scenes; CoreEngine handles ResolveModules (core/src/lib.rs:117–124); module edits/resolution are present. Dioxus presentation does not render PCB overlays from them.

Suggested new ticket detail (if the planner wants to split the current broad F5.1 delivery further):

1. **PCB-01A, selected-board scene and context bridge (P0):** private page composition only; accepted snapshot + full board/optional physical-instance Scope + real host scene/definitions + selection callback. Render/select real host geometry, selection updates existing Objects/Inspector context, stale board/project results are discarded, and no document/history/export state changes. Start after INT.1 plus that exact root mount contract. Parent F5.1 acceptance remains open until the paired scene/layer and shared requirements pass.
2. **PCB-01B, host layer controls (P0):** after 01A; dynamic real host footprint/artwork layer names and standard groups, React defaults, persistent transient lifetime, independent toggles and desktop/compact/keyboard checks. Keep module overlays out of this first slice.
3. **PCB-02A, read-only wiring and resolver preview (P0):** after 01A's accepted board scope; real current board/controller projection, mode, plan order, diagnostics, used/free pins, peripherals and Resolve. Use existing Core request/reply, with exact scope/revision validation. No Apply until preview freshness is demonstrated.
4. **PCB-02B, review/apply/locks/manual assignments (P0):** after 02A; existing edit/remap/protection commands only, with single undo, stale-plan/error/review flows and retry. Preserve F5.3's F3/F4/F6K acceptance joins.

These are implementation sequencing suggestions, not ticket publication: the published F5.1 children 01/02 already cover the relevant scene/layers. Coordinator ownership of web/src/presentation.rs, shared CSS, worker/runtime surfaces and selected-scope callbacks must be assigned to avoid a shared-file race.

## F6K.4b relationship

The private F6K.4b draft describes the firmware-position selector as a consumer of an already-current F5 selected-board electrical plan. It correctly says its own control does not resolve electrical state, construct IDs, own history, or mutate the typed Keymap editor. F5.2 and F8.2 remain F6K.4 acceptance joins, but they are not a reason to delay F5.1 or to block a basic F5.2 wiring summary. The actual firmware package output remains the separate F8.2/F6K.4 handoff.

## Refactor evidence / RF

No new RF ID is introduced by this audit. The F5.1 dispatch already requests existing RF-009 source-accounting reconciliation at publication; retain that handoff. The concrete design takeaway supported by source is ownership separation: shared host-layer visibility must span Design/PCB; module visibility is independent; board scope and physical-instance scope are different; and a generic PreviewBoard artifact or Layout FootprintGraphics module must not be described as the missing interactive PCB host scene.

## Integrity / limits

- Agent-browser sessions were isolated and closed after the checks. There were no React edit/save actions; one React host layer was hidden and the selected board/workspaces were changed locally during navigation. Dioxus candidate page errors/console output were empty.
- Module overlay visibility was observed; automated selection was inconclusive because the SVG hit target was covered. No claim is made about module click-through from this audit.
- Routed-reference UI was observed through React Case text and its import input, but no file was imported. Firmware controls were source-audited and the Export menu was observed; no firmware output was generated.
- This audit does not claim parity acceptance, F5.1/F5.2 completion, or availability of every physical artifact source. It identifies which current Core/host capabilities can be reused and the missing frontend seams.
