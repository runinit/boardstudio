## Worker architecture routes: plausible, not demonstrated

A Rust UI can own `web_sys::Worker` and a separate Rust wasm worker can own the engine, receive messages through `DedicatedWorkerGlobalScope`, and post replies. A generated/build-produced script must initialize wasm in each worker: a browser Worker is created from a script URL, not directly from an rlib. The [official wasm-bindgen worker example](https://wasm-bindgen.github.io/wasm-bindgen/examples/wasm-in-web-worker.html) demonstrates Rust/web-sys worker interaction and initialization; it does not validate this repository's Dioxus asset packaging, Cadrum build or cancellation behavior.

Exact installed primary source: `/home/chris/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/web-sys-0.3.106/src/features/gen_Worker.rs` provides `new`, `new_with_options`, `post_message`, `post_message_with_transfer`, `terminate`; `gen_DedicatedWorkerGlobalScope.rs` provides reply posting with transfer; `gen_IdbDatabase.rs` provides transactions gated by the corresponding Cargo features. Published source coordinates are [web-sys 0.3.106](https://docs.rs/crate/web-sys/0.3.106/source/src/features/gen_Worker.rs) (remote retrieval unavailable). Existing locks pin wasm-bindgen 0.2.129, js-sys/web-sys 0.3.106, serde-wasm-bindgen 0.6.5; do not casually mix a framework-selected incompatible bindgen version. Enabling needed browser features in a new trial crate is a future implementation decision.

Route A: compile core with each relevant Rust worker and invoke its typed `handle` internally; serialize at worker boundary. CAD can initially remain a separately built wasm module with generated bindings and Rust-maintained orchestration. Route B: link CAD into its own Rust worker with existing `JsValue` entrypoints, preserving its initialization/build environment. Linking heavy CAD directly into the Dioxus UI still executes synchronously on the UI thread; an async Rust function alone does not move it away. Route C: a server-side engine would change offline/deployment behavior and is outside the browser-preserving default unless explicitly chosen.

[WHATWG HTML worker standard](https://html.spec.whatwg.org/multipage/workers.html): workers have separate globals, cannot manipulate DOM directly, and communicate by message copying or transfer. Termination kills a worker. Therefore keep the existing HTML canvas/GPU renderer on the page and expensive scene preparation/CAD/core work in workers as a candidate starting route; worker GPU rendering would require an additional canvas interface design. Transferring owned ArrayBuffers detaches sender ownership; preserve caches through copies/retained canonical data as needed, and measure copies from Rust vectors to JS typed arrays separately from worker transfers.

## Behavior that a Rust transport port must carry

- [app/src/CoreClient.ts](../../../app/src/CoreClient.ts) tracks pending request ids, persists committed scene snapshots, settles outstanding calls on crash/close and restarts/reopens the last accepted snapshot. Reopen resets Rust Undo history: crash recovery is not evidence of history preservation. [app/src/core.worker.ts](../../../app/src/core.worker.ts) restores transport ids after malformed request decoding and adds timings.
- [app/src/createProjectActions.ts](../../../app/src/createProjectActions.ts) schedules actions and restores the prior core document when accepting/saving an opened project fails. Preserve save ordering and rollback rather than letting Dioxus signals make persistence incidental.
- [app/src/CaseClient.ts](../../../app/src/CaseClient.ts), [app/src/case.worker.ts](../../../app/src/case.worker.ts), [cad/src/preview.ts](../../../cad/src/preview.ts) own queued CAD requests, progress throttling, superseded preview cancellation, cached body deltas and reconstruction, stale revision rejection, model transfers and worker reset. Consume completed deltas even when cancellation raced, then reject stale UI display; otherwise client and worker caches diverge.
- Current preview work checks cancellation between bodies and yields after an expensive body; keycaps yield in batches. A synchronous OCCT operation cannot process a cancellation message mid-call. Hard worker termination abandons caches and settles other pending imports too; reproduce these limits honestly rather than promise immediate cooperative kernel cancellation.
- [app/src/scene.worker.ts](../../../app/src/scene.worker.ts) supersedes outdated scene preparation, preserves removed-body patches and transfers collected typed-array buffers. [app/src/renderClient.ts](../../../app/src/renderClient.ts) keeps GPU state/camera and coalesces pointer/render work. Generation ids, scene revisions and camera lifetime are separate concerns.
- [cad/src/kernel.ts](../../../cad/src/kernel.ts) lazily initializes CAD and clears failed initialization for retry. [cad/src/index.ts](../../../cad/src/index.ts) bounds STEP imports to 32 MiB and exports all bodies through cached assembly. [cad/wasm/src/model.rs](../../../cad/wasm/src/model.rs) also bounds STEP and copies buffers into Rust/JS, which transport benchmarks must count.

CAD is Rust application logic over a native OCCT dependency, not a pure-Rust kernel. [cad/wasm/Cargo.toml](../../../cad/wasm/Cargo.toml) pins Cadrum 0.8.20; [cad/scripts/prepare-cadrum-occt.mjs](../../../cad/scripts/prepare-cadrum-occt.mjs) pins OCCT 8_0_1_rev2 archives/hashes; [cad/wasm/Containerfile](../../../cad/wasm/Containerfile) supplies Rust 1.98.0, wasm-bindgen CLI 0.2.129 and a customized WASI SDK 33 exception/sysroot setup. [cad/wasm/src/lib.rs](../../../cad/wasm/src/lib.rs) invokes ctor initialization/WASI anchoring. Reusing that package avoids silently assuming ordinary Dioxus linking supplies its native build prerequisites. Direct-link compatibility, start initialization and bundle size remain trial gates.

## The remaining executable generator boundary

[ergogen/src/index.ts](../../../ergogen/src/index.ts) imports executable catalogue modules. `render` invokes `generator.body(p)` after building parameters, net and local-net callbacks, anchors, reference/side/pose and mirrored coordinate helpers. The same execution path feeds catalogue normalization, physical geometry, terminals and model bindings, not only PCB downloads. [kicad/src/ergogen.ts](../../../kicad/src/ergogen.ts) upgrades legacy arcs, rewrites safe relative model paths, converts module/footprint forms and serializes routing/graphics. [app/src/export.worker.ts](../../../app/src/export.worker.ts) obtains a Rust export plan, executes jobs with deterministic reserved/local-net allocation, then supplies generator result forms to Rust finish-export with snapshot/revision identity. Rust final assembly/serialization does **not** imply generators or this adapter are already replaced.

Eventual routes requiring a human decision:

1. Rewrite the supported generator catalogue and normalization/transform/serializer behavior in Rust, keeping stable source ids and generator versions (or explicitly versioning conversions). Highest flexibility; costs scale with the supported bundled catalogue and parameter combinations.
2. Translate a deliberately restricted generator language into Rust/data with audited build-time tooling; reject unsupported constructs explicitly. Valid only if the runtime contains no maintained executable JS application logic and supported semantics actually match.
3. Replace executable generators with declarative/native footprint and utility definitions plus explicit project conversion. Preserve the supported saved generator source/version/parameter definitions, or explicitly agree to their conversion. Imported KiCad footprint source and custom pad/courtyard definitions are data and need separate preservation, not a JavaScript execution mechanism.

Running bundled JS through an embedded interpreter, retaining hand-written JS workers, or calling a remote JS service may be staging bridges but does not satisfy all maintained application logic in Rust. Precomputing finite fixed footprints also cannot establish parity for the supported bundled generators' net-, pose-, parameter- and reference-dependent outputs. The unresolved compatibility decision concerns supported saved bundled-generator definitions and parameter behavior, not user-supplied executable JavaScript. Current [README.md](../../../README.md) explicitly says user-supplied JavaScript generators are not executed. `render` rejects unknown source ids and versions other than `bundled-1`. README also distinguishes non-generator custom/imported definitions with pad/courtyard editing; [core/src/artifact/source.rs](../../../core/src/artifact/source.rs) imports and patches KiCad footprint source as data.

Parity gates: all supported catalogue sources/defaults and parameter overrides; front/back/mirror/rotated placements; net numbering/reserved and local-net identity; anchors/references and escaping; physical envelopes/terminals/model transforms used before export; footprint and board utility forms; old arc conversion; safe portable model paths; standalone versus placed exports; snapshot/revision mismatch rejection; archives and KiCad re-import. Compare semantic S-expression/geometry outputs and normalized deterministic text, permitting UUID/order differences only where proven insignificant. Existing [ergogen/scripts/runtime.test.mjs](../../../ergogen/scripts/runtime.test.mjs), [kicad/test](../../../kicad/test), Rust artifact output tests and [app/e2e/kicad-artifact.spec.ts](../../../app/e2e/kicad-artifact.spec.ts) are evidence to preserve and extend, not proof that a new implementation passes.

## Candidate trial evidence for the human architecture/acceptance decision

The following are candidate checks, not decided acceptance criteria; the human architecture/acceptance ticket chooses the exact trial scope and gates. Layout: real project open, SVG selection/drag/preview/commit, Undo/Redo, save and reload into both apps; stale/draft rejection; failed save rollback; worker failure/close without hanging requests. Case: current Rust preparation -> CAD worker -> meshes -> existing Rust canvas renderer -> STEP download; an edit regenerates only current bodies, cancellation/races do not display stale output, cached assembly export matches uncached output, import/retry and mount/disposal work. Measure cold/warm startup, main-thread pointer responsiveness during CAD, queue latency, copied/transferred bytes, retained caches/GPU memory and repeated-edit soak behavior against existing benchmark fixtures/budgets. A runnable screen alone does not prove migration feasibility.

Human decisions remain: packaging/linking strategy after measured compatibility, precise performance thresholds/browser coverage, bundled-generator replacement and saved-definition compatibility route, Rust storage/session ownership, and whether C++ CAD dependencies are acceptable (the stated requirement rules out maintained TS/JS, not C++). Preserve active encoder/VIK evolution and use current Rust contracts when implementation starts; research does not mark that ongoing work complete. Required existing affected checks and user testing remain gates for the future trial; none were run by this research-only task.
