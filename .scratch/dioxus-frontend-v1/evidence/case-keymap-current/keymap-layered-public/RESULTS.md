# Public layered Keymap fixture and import inspection

## Fixture provenance and production actions

The producer started from the actual `sofle.boardstudio` archive shipped by `frontend-case-keymap-20261002`, not a constructed ProjectDoc. The initial archive is retained as `fixture/initial-sofle.boardstudio` (SHA-256 `0e1e06beabfce1c5a2d6bfc472c85ed281435ff2382174b32f9a2bd3d6d58899`); the candidate build’s `provenance.json` records that fixture hash and has SHA-256 `c6f99930d921c51d3588d593bc46051d57befc253d93d6c9caf27b09af7db221`. Build id/source: `frontend-case-keymap-20261002`, `dc81237c51c9d4f43ddb7f0d3f6f7eda9cf685fc`.

In a fresh task-owned React profile at `http://127.0.0.1:5173/`, the public file input imported the initial archive. Through the Keymap panel I added a layer, renamed Base to `Main`, named the new layer `Function`, assigned Function’s `left-keys-SW1` to the public `Key press` behavior with keycode `Q`, and selected `Unassigned` for Function’s `left-keys-SW2`. The remaining Function bindings were left at the layer’s default transparent behavior. The public Export → Save `.boardstudio project` action produced `fixture/layered-sofle-export.boardstudio`, SHA-256 `5b17071a819e4cfa28531913685e8fedf84cbdd361cefccb3b16befd6c0776df`.

Its embedded `project.json` is preserved. The two layers are `base`/`Main` and `dc238a57-6d6c-4eaa-b6c2-061d2eedec00`/`Function`. Function has typed `{kind:"key-press", keycode:"Q"}` at stable key id `matrix/left-keys/r0c0` and typed `{kind:"none"}` at `matrix/left-keys/r0c1`; other Function bindings are absent. Main has no typed entries. The original hardware board legacy `keyBindings` maps are empty, so this real archive does not exercise the legacy fallback. No legacy values were injected or authored outside the UI.

The exact same exported archive was publicly imported in fresh, separate, disk-backed profiles at `/var/tmp/frontend-run/case-keymap-followup/profiles/reference` (React reference, `:5173`) and `/var/tmp/frontend-run/case-keymap-followup/profiles/candidate` (candidate build, `:34663`). Both views show the renamed ordered layers `0 Main`, `1 Function`. Selecting Function shows `left-keys-SW1 · Q`, `left-keys-SW2 · Unassigned`, and missing non-base bindings such as `left-keys-SW3 · Transparent`. Selecting the real SW2 canvas control changes only selection; its public inspector heading is `left-keys-SW2`. The candidate Keymap view exposes layer selection, key search, and selected-key presentation; it does not expose a binding behavior/keycode editor. In the candidate, searching `SW2` filters to SW2, SW20–SW24, and `left-thumbs-SW2`; selection and layer changes left the exported project unchanged.

The candidate app remained on the imported project after browser reload, and the two saved layers remained visible. An isolated Undo click on the candidate’s generic toolbar also left the UI on the same project. Candidate public exports before view-only navigation, after view-only navigation, after reload, and after Undo have the same archive SHA-256 `8c1614b5e30c8e10d4dd503a5794271f1db4f8e1a0740c419878b8a23bf9e5ff` and embedded `project.json` SHA-256 `981c8978101286985b2f5220e8af18a612037f5fc7cd892a52fcb881f39eae7f`. Undo/Redo are exposed and enabled as generic toolbar controls; Undo was tested once, Redo was not invoked.

The React reference re-export is byte-identical to the imported archive and embedded project JSON: archive `5b17071a…d0776df`, project JSON `d8e8ed8b285ed99dd11ac99f095abecf640022dee845ae6ffaac4c374e18eabd`. The candidate embedded JSON is not byte-identical: its decoder/serializer changes 599 equal-valued integer JSON numbers to floating-point spellings (for example `1` to `1.0`). Parsed document comparison found no changed values or structure; the entire typed `keymap` object is exactly equal across input, reference, and candidate. Candidate before/after view/reload/Undo exports are byte-identical to each other. This is semantic document equality, not literal JSON-byte equality.

This numeric formatting is consistent with the candidate Core wire model: `contracts/rust/src/lib.rs` represents `Vec2.x/y` and `Pose2.rotation` as `f64`; the exact source at candidate commit `dc81237c` hashes to `85691e99b31d16722bd823fe971e802620fc1a05903ab976d4692e40bab181ee`. The relevant source hashes at that commit match the current checkout: `core/src/matrix.rs` `e45cf1d34d11d96eea09fbad41b74108e02f84a75bd3e056446dcc4d25ca6cbf`, `web/src/presentation/keymap/view.rs` `2bdc79466dd88e1a42f18158188fc74cad89cb1fef6d45450c76b9ba1c27dc9e`.

## Legacy and imported variant limits

The actual Sofle archive’s legacy `hardware.boards[].keyBindings` are empty, and its Main typed bindings are also empty. Thus the public fixture verifies typed non-base action, explicit None, missing non-base Transparent, and empty base Unassigned, but does not verify a nonempty legacy fallback. The candidate Keymap projection source uses typed layer values first, treats missing non-base entries as Transparent, then checks legacy board bindings for the base layer; legacy behavior remains unexercised here because no authentic legacy binding was present.

I also reconciled the retained VIK paired trace at `public/layered-fixture/` without changing it. Its source archive is `vik-review-ui-export.boardstudio` (SHA-256 `952b26565a4df3ae1122fd0716017560279c938ee19fb6c15af966c88c1d35b0`); its source `project.json` already has two `properties.variant` values. The preserved candidate IndexedDB document has zero parsed differences from that source, and the preserved React reference differs only in three floating-point spellings (`-9.020000000000001` to `-9.02`). Both paired documents retain the same two variant entries and exact typed keymap. This does not reproduce the existing VIK README’s claim that candidate import adds variant properties to many parts. In Core, the inspected `set-matrix` operation inserts/removes `properties.variant` (`core/src/matrix.rs` around lines 799–819); this read-only import comparison gives no evidence that that operation ran or that import itself added variants. No importer change is indicated by these retained artifacts; the README/artifact mismatch remains a reconciliation gap.
