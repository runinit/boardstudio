## Prioritized actionable findings

1. **[P2] Stabilizer assignment excludes the placed stabilizer definitions it should serve.** `web/src/presentation/mechanical_settings.rs:2835–2837` filters the stabilizer target list by `switch_profile`; `mechanical_settings_mount.rs:1187–1191` sets that flag only for Switch/Choc-generator definitions, and `mechanical_settings_controller.rs:544–551,771–777` repeats the restriction at admission. A placed Custom stabilizer without a configuration profile cannot receive either builtin stabilizer profile; with only Custom targets the entire stabilizer section disappears. Actual catalogue STAB_MX_2u/6.25u definitions are `kind: custom`, illustrating the domain mismatch (their existing inherited profiles are not claimed missing). Pinned TS `MechanicalAssemblyPanel.tsx:593` offers all placed unassigned definitions for library assignment. Use separate stabilizer eligibility through projection/UI/controller, preserving active-board and duplicate checks. The retained MX-switch journey does not qualify this branch.

2. **[P2] First family assignment treats an unknown family as unchanged.** `web/src/presentation/mechanical_settings_controller.rs:488–498,525–529` uses `existing_family.is_some_and(...)`, so `None` preserves the prior plate thickness and skips updating configured gap/foam. For an unknown Switch definition with a saved 4 mm plate, choosing Choc v1 requests a −0.5 mm engagement and Core rejects it before assignment (`core/src/mechanical.rs::builtin_profile` requires positive engagement). Pinned TS `mechanicalProfileController.ts:54–62` treats the first family as a change, sets the 1.3 mm default, and requests a valid 2.2 mm gap. With smaller prior thicknesses Rust can instead save a profile while retaining inconsistent configured gap/foam until another dimension edit. Treat unknown→known as a family transition and apply the coherent existing default/derived-settings policy. The browser receipt covers MX at already-compatible thickness, not this first-family recovery case.
