# Independent planning review: F7 Case and shared viewer

**Verdict:** The Case/viewer scope is thorough and the canonical-board versus physical-Case split is correct. The plan needs three ownership/acceptance clarifications and one retry-state correction to stay exact to the pinned React behavior and existing renderer boundary.

## Material findings

1. **Do not describe renderer methods already exported by wasm as a missing public Rust/application contract.** The plan correctly calls this a host-wrapper feasibility question, but F7.1 asks the first slice to identify public contract/visibility gaps. At this baseline, `RendererHost` lacks wrapper methods for state/display, handles, and picking, while the wasm `Renderer` already exports `setState`, `setHandles`, `pick`, prepared-scene operations, and camera operations. This supports private wrapper/adapter work; no Core/application contract gap is demonstrated. Have F7.1 exit with the smallest private adapter mapping and proceed unless a specific existing wasm operation proves insufficient. If adding methods to the public `web::renderer_host` module, keep feature-only capabilities crate-private so the plan’s no-public-visibility-widening rule remains true.

   Evidence: [renderer_host.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/web/src/renderer_host.rs:101) currently wraps scene updates and camera calls; [wasm.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/renderer/src/wasm.rs:505), [wasm.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/renderer/src/wasm.rs:647), and [wasm.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/renderer/src/wasm.rs:723) already export the state/handle/pick operations. `web/src/lib.rs` currently declares `pub mod renderer_host`, so a new public method there would widen the Rust crate surface.

2. **State the Parts viewer’s third, isolated scope explicitly.** F7 correctly requires canonical-board scenes for Layout/Keymap/Keycaps and selected physical-instance projection only in Case. Parts is a third case: React `LibraryWorkspace` constructs an isolated `sampleAssembly` project for the selected definition and companions, then sends that sample project to the same viewer inside `ModelPreviewBoundary`. “Parts and other consumers use their own agreed project/module scopes” is too vague to protect that behavior. Add F7.3/F7.8 acceptance that Parts receives its isolated library sample input, never the active physical Case projection or an implicitly mutated canonical project.

   Evidence: [LibraryWorkspace.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/LibraryWorkspace.tsx:100); the canonical-versus-physical selection is explicit at [Workbench.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/Workbench.tsx:420) and the viewer mount at [Workbench.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/Workbench.tsx:1386). Rust’s `captured_case_document` enforces the Case scope in [cad_jobs.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/web/src/cad_jobs.rs:252).

3. **Distinguish reusable F4 part profiles from F7 case configuration profiles.** F7.4 lists “inherited/custom part profiles” and supported KiCad geometry extraction, which can read as taking over F4’s saved `PartDefinition.mechanicalProfile` editor. React has two distinct interfaces: F4’s Parts editor saves a reusable definition profile; F7’s mechanical editor assigns inherited library profiles or edits the case configuration’s `profiles`/custom KiCad extraction. Clarify F7.4 acceptance as configuration-scoped assignment/overrides/extraction, with the reusable definition profile and its evidence editor remaining F4-owned.

   Evidence: [F7.md](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/issues/07-case-3d.md:22) and F7.4 in [F7.json](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/workflows/F7.json); React’s reusable library profile is in [LibraryWorkspace.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/LibraryWorkspace.tsx:98) / [PartMechanicalProfileEditor.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/PartMechanicalProfileEditor.tsx:63), while per-configuration assignment and editing are in [MechanicalAssemblyPanel.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/MechanicalAssemblyPanel.tsx:582) and [MechanicalAssemblyPanel.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/MechanicalAssemblyPanel.tsx:596).

4. **Narrow promised renderer retry to retry paths the reference actually offers.** CAD/model preview failures have provider retry actions, and Parts’ `ModelPreviewBoundary` has a retry button. A renderer initialization failure in `AssemblyScene` is currently an alert while preserving the surrounding UI; context loss stops rendering and reports status, without a dedicated canvas retry button. F7’s broad “rendering failure with a usable retry” story and viewer-wide retry acceptance overstate that source behavior. Preserve the provider/model retry actions and the 2D return route where present; require clean stop/report/unmount for renderer failure. If the port intends to add a canvas reconstruction button, identify it as an intentional UX addition rather than React parity.

   Evidence: [ModelPreviewBoundary.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/ModelPreviewBoundary.tsx:3), [AssemblyViewer.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/AssemblyViewer.tsx:112), [AssemblyScene.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/AssemblyScene.tsx:114) (initialization error), and [renderer_host.rs](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/web/src/renderer_host.rs:177) (context loss status/stop).
