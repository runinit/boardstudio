# Independent planning review: F5 PCB and hardware

**Verdict:** The mounted-module versus definition/profile boundary is largely correct, and the F5 slices are source-grounded. Two integration details need normalization before implementation; neither blocks fixture-backed panel work.

## Material findings

1. **The shared file/asset bridge is assigned ambiguously to F4.** F5.7/F5.8 use `F4-shared-file-and-asset-import-seam`, and the ownership map calls the routed-board editor “F4/shared host” work. The React reference’s routed-board importer reads a KiCad file, calls the existing preview artifact, hashes/saves bytes, then commits a `BoardReference`; this is generic browser file/asset I/O, distinct from F4’s definition-specific model import. The F4 plan assigns the missing shared Runtime/file-to-asset bridge to the coordinator. Please normalize the dependency and ownership to that coordinator-owned shared host bridge, leaving F4 as owner only of its library/model import presentation. F5 can still build and validate the panel against fixtures before that bridge is ready.

   Evidence: F5 ownership map and service notes at [F5.md](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/issues/05-pcb.md:116) and [F5.json](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/workflows/F5.json); pinned React behavior at [BoardReferencePanel.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/BoardReferencePanel.tsx:6) (size/hash/storage), [BoardReferencePanel.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/BoardReferencePanel.tsx:84) (parse and stale guard), and [BoardReferencePanel.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/BoardReferencePanel.tsx:124) (individual/directory model assets). The current Rust browser store/artifact worker already provide the underlying operations; the gap is the composed UI/runtime host seam, not a new parser contract.

2. **The routed-reference viewer check is an actual F7 join but sits inside an F5.7 acceptance whose dependencies do not include it.** F5.7 correctly says F7 is unnecessary for the reference editor itself, but its acceptance also says F7 confirms the reference’s visible assembly effect. Preserve that independent implementation boundary by keeping F5.7 acceptance limited to import/edit/persist/reopen and moving the Case-viewer effect assertion into the integrated F5.8 acceptance, with the actual F7 common-viewer/physical-instance join named there. This is a real acceptance dependency, not just a symbolic dependency-name issue.

   Evidence: [F5.md](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/issues/05-pcb.md:68) and F5.7 in [F5.json](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/.scratch/dioxus-frontend-v1/workflows/F5.json); the React reference is consumed by `AssemblyViewer` through `Workbench`’s Case-scoped document at [Workbench.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/Workbench.tsx:420) and [Workbench.tsx](/home/chris/.local/share/boardstudio/worktrees/migration-m1-continuation-20261001/app/src/ui/Workbench.tsx:1386).

## Boundary confirmation

No ownership defect found in the central F4/F5 module seam: F4 owns the reusable module definition, source/readiness summary, profile editor, and library assets; F5 owns mounted placement, host/instance scope, pose/face/clearance/support drafts, VIK connection and embedded-circuit joins. F5’s ownership table already places `HardwareReadiness` with F4 and describes F5 as consuming the summary. Keep F5’s module-inspector gate display read-only, and make the F5 user story about seeing source gates refer to that F4-provided summary.

The remaining PCB stories match the pinned React behaviors reviewed: module source geometry remains a separate overlay from host copper; board wiring is resolved/applied through existing Rust requests; physical instances retain their current board/role/flip identity; and routed-board parsing remains the current preview artifact. No backend/API or schema gap was found.
