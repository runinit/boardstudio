# Post-port refactor candidates (source-checked)

These are findings to preserve for a later design review, not authorization to widen APIs or change backend behavior during the port. “Confirmed limitation” means the current source boundary/behavior is directly visible. “Design risk” is a plausible maintenance consequence that needs validation after the frontend is complete; it is not a claim that the present design is wrong.

1. **Shared shell and Runtime are high-churn composition points — confirmed structure; risk of coordination bottleneck.** `web/src/presentation.rs` contains workspace navigation, route presentation, layers, canvas interaction and substantial Layout behavior; `web/src/runtime.rs::Runtime` currently stores the Session, CoreWorker, assets/artifacts, CAD workers/jobs, export state and browser scheduling. Execution plans correctly assign these files to the coordinator. **Impact:** F2–F8 integration and independent feature work. **Current workaround:** named private feature modules, small callbacks/read models and serialized coordinator edits (INT.1/INT.2). **Later refactor:** after routes stabilize, extract workspace composition/controllers and narrow Runtime into private typed ports while retaining one Session/document authority. **Validate:** each workspace change should avoid edits to the central composition except its mount seam; parallel feature integration should not create merge conflicts or duplicate state.

2. **Library-to-binary visibility makes “private wrapper” policy hard to realize for some shared web services — confirmed boundary tension.** `web/src/lib.rs` exports `pub mod renderer_host`, `pub mod host`, and `pub mod cad_jobs`; `web/src/main.rs` separately declares private `presentation` and `runtime` modules and imports services through the `boardstudio_web` library. A feature-only method implemented in the library cannot be `pub(crate)` and still be called from that separate binary crate. **Impact:** shared renderer, artifact/CAD/asset adapters for F3/F4/F5/F6/F7/F8. **Current workaround:** coordinator-owned smallest typed bridge, explicit review of any visibility expansion, avoid re-exporting implementation details. **Later refactor:** consider moving browser application composition and service wrappers into one crate boundary or providing a deliberately small stable browser-host facade, with an API-consumer audit. **Validate:** compile a feature-only call from the UI while checking the library's exported API surface; ensure tests/integration consumers do not acquire unstable renderer DTOs.

3. **RendererHost is a thin dynamic wasm shim rather than a typed viewer facade — confirmed limitation.** `web/src/renderer_host.rs` exposes scene update and camera wrappers via `Reflect`/string method names; state/display, handles and picking are not wrapped there, while `renderer/src/wasm.rs` already exports operations such as `setState`, `setHandles`, and `pick`. This is a wrapper gap, not evidence that Core or the renderer lacks those operations (see the F7 review). **Impact:** single shared viewer for Layout, Parts, Keymap/Keycaps and Case. **Current workaround:** F7's private adapter maps current wasm exports and owns lifecycle; F3/F4/F6 provide typed inputs only. **Later refactor:** replace reflective strings with a small typed Rust viewer adapter/capability set and one versioned scene projection; keep it internal to the app. **Validate:** exercise all consumers' scene/display/pick/handle operations and mount/update/error/context-loss/unmount paths against the same public UI traces; verify no renderer method is duplicated by a consumer.

4. **CAD work has more than one provider protocol and unequal output coverage — confirmed limitation.** Case generation/export uses Rust `CadRequest`/`CadReply` identity and the Rust CAD worker (`web/src/cad_jobs.rs`, `cad_worker.rs`, `runtime.rs::generate/step_bytes`). React keycap preview/STEP uses `CaseClient.keycaps` and the `@boardstudio/v2-cad` JavaScript worker (`app/src/CaseClient.ts`, `case.worker.ts`); current Rust `CadOperation` has no keycap operation. F8 review independently confirmed that keycap STEP is not an existing Rust provider. **Impact:** F4 model previews, F6 keycap fit/preview/STEP, F7 Case, F8 output orchestration. **Current workaround:** retain current providers behind provider-owned adapters and report the keycap STEP path as a real capability gap; do not claim `ResolveKeycaps` creates CAD output. **Later refactor:** after parity, evaluate a common typed CAD job envelope/result/cancellation contract or a cleanly documented set of provider-specific capabilities; migrate algorithms only under separate authorization. **Validate:** compare existing provider outputs byte/mesh-wise, and prove identity, cancellation, stale result, cache, retry and disposal behavior for every operation before consolidating.

5. **Session exports are bound to one immutable accepted token, but the React PCB exporter can adopt its own committed preparation edits — confirmed semantic mismatch.** `Session::start_export_now` captures a snapshot token/scope and `export_is_current` accepts only that token; there is no Session transition that adopts an export-owned accepted edit. React `ExportContext.adopt()` advances its expected document after `exports/pcb.ts` commits wiring preparation/protection (`app/src/exports/context.ts`, `pcb.ts`; detailed in the F8 review). **Impact:** F5 protected electrical handoff and F8 full/draft PCB packaging/delivery. **Current workaround:** do not mutate an export's captured snapshot silently; model each accepted edit as an ordinary Session commit, recapture its accepted token, and keep the exact workflow ordering/transaction behavior as an explicit unresolved gate until verified. **Later refactor:** decide whether exports should be read-only snapshots or first-class short transactions with a narrowly defined adopt/commit transition and rollback semantics. **Validate:** public tests for already-applied and unapplied wiring, packaging failure, protection ordering, Undo/Redo, unrelated concurrent edits, board/project changes and stale delivery.

6. **Some consequential interaction policy currently lives in UI-owned TypeScript — confirmed ownership fact; maintainability risk.** `app/src/ui/planKeycapResize.ts` computes selected-size changes and linked-half identity; `keycapReflow.ts` applies neighbor spacing; `assemblyPreview.ts` owns independent keycap/module/PCB request sequences, abort controllers, caches and retry. F6 already records that no callable Rust resize/reflow equivalent was located and requires a behavior-preserving private frontend port. **Impact:** F3 Layout sizing, F4 isolated previews, F6 Keycaps and F7 viewer inputs. **Current workaround:** port the UI policy into Dioxus-private controllers; keep core geometry/resolver/CAD as authority and retain the existing helper regression scenarios as oracles. **Later refactor:** after parity, decide which UI policies should become shared typed application services versus remain presentation controllers, and reduce duplicated scope/cancellation/cache rules. **Validate:** differential fixtures for resize/reflow and async preview sequences, plus one-step Undo, save/reload, linked halves, stale replies, retry and resource disposal. Do not infer from TS ownership alone that the current behavior belongs in core.

7. **Viewer provenance has three real scopes, while session `Scope` describes only document/board/optional physical instance — confirmed domain distinction; design risk.** F7 review confirms canonical board scenes for Layout/Keymap/Keycaps, selected physical-instance projection in Case, and an isolated sample project for Parts (`LibraryWorkspace.tsx`/`sampleAssembly.ts`). `Scope` has document, board and optional instance identity, but does not tag “isolated library sample” as a distinct viewer input kind. **Impact:** F3/F4/F6/F7 shared-viewer composition and stale-response rejection. **Current workaround:** consumers provide their own immutable scene inputs and scope guards; F7 owns one viewer and must keep Parts sample inputs isolated. **Later refactor:** consider a tagged viewer input/provenance type (canonical board, physical instance, isolated sample) rather than relying on unstructured document IDs and consumer conventions. **Validate:** same board across canonical/physical/sample fixtures; switching each scope during pending model/CAD work must neither leak geometry nor cancel unrelated consumers.

8. **Revision values cross a JavaScript-number boundary with an explicit safe-integer ceiling — confirmed technical limit; low-probability scale risk.** `web/src/cad_jobs.rs` sets `MAX_CAD_REVISION` to `9_007_199_254_740_991` and rejects larger values because CAD worker revisions travel as JavaScript numbers. **Impact:** long-lived projects using Case/CAD jobs; not a near-term frontend parity blocker. **Current workaround:** explicit validation and error instead of lossy identity comparison. **Later refactor:** if project lifetime can plausibly approach the ceiling, encode revisions as decimal strings/bigints through the worker envelope while retaining stable comparison semantics. **Validate:** boundary tests at max/max+1 across serialize/worker/reply checks and compatibility tests for old worker payloads before changing the contract.
