# F8 independent planning review

Reviewed F8.md/F8.json against pinned React `5a472a9426e6e38993361da402cd4ec730feb369` and Rust/Dioxus baseline `c827c4e69389a77b1f0e8d647ce86a4c41529611`. No repository files were changed; no build or browser session was used.

## Material findings

### 1. Keycap STEP is not an existing Rust/CAD export provider

F8.4's boundary says “Rust firmware generation and CAD keycap STEP requests already exist,” and F8 Further Notes says “CAD has ... keycap STEP provider.” The Rust baseline does not support that claim. Core `ResolveKeycaps` returns keycap specs/findings and `GenerateFirmware` returns a firmware package (`core/src/lib.rs`, CoreRequest/CoreReply in `core/src/model.rs`); the browser CAD operation enum is only Preview, Exact, ExportStep, ReadStep (`web/src/cad_jobs.rs`). Its ExportStep path requires a `PreparedCaseAssemblyIR` and calls the case assembly export worker (`web/src/runtime.rs::step_bytes`, `web/src/cad_worker.rs`); no keycap-spec-to-CAD request or keycap STEP operation exists in the Rust web/CAD integration. By contrast, pinned React uses `CaseClient.keycaps(revision, specs, exportStep)` and `exports/keycaps.ts` calls it after Core keycap resolution.

**Fix:** retain F6 ownership of the Keycaps-local button and F8's route integration boundary, but change F8.4 and the evidence note to mark the keycap STEP CAD handoff as an actual provider/adapter gap, not an existing Rust provider. State that F8 may reuse the existing React behavior only if an already-approved private wasm/CAD path can produce the same artifact; otherwise enumerate the required gap and stop before adding an engine/public API. `ResolveKeycaps` alone is not sufficient evidence of STEP generation.

### 2. Portable project copy's optional bundled-model embedding is missing from current Runtime

F8 says the Rust archive provider already owns the portable archive and treats the used-model checkbox as an existing-owner handoff. The pinned React behavior is precise: `app/src/storage.ts::packProject` always includes local `doc.assets`; when `embedUsedModels` is enabled, it also discovers used bundled Ergogen/model assets, reads their bytes, appends asset records with hashes, and packages those bytes. The Export workspace owns the checkbox and action in `Workbench.tsx`; the Project menu also invokes the same project action. Current `web/src/runtime.rs::pack_archive` only loads `document.assets`, serializes the unchanged document, and packs those files. It has no `embedUsedModels` input or bundled-model resolver. Thus archive ZIP support exists, but archive asset semantics do not yet match React.

**Fix:** split ownership: F2 may own the archive/store provider and Project-menu action; F8 owns the Export-route `.boardstudio` action and “Embed used models” control because both are visibly on the React Export workspace. Record optional bundled-model embedding as a concrete private asset-provider/runtime gap to close or explicitly qualify; do not claim current Runtime has it. Preserve that local assets are included regardless of checkbox. Also qualify the boardstudio filename: React uses `${document.name}.boardstudio`, while current Runtime currently delivers `keyboard.boardstudio`.

### 3. F8 overstates that the current Session can adopt export-owned accepted edits

F8.2 says “Application Session already models StartExport/CancelExport/snapshot identity and stale completion,” then requires PCB export's own accepted wiring/protection edits to advance that captured context. Rust `Session::start_export` captures an immutable accepted snapshot token and scope, and `export_is_current`/`ExportFinished` only accept that same token and scope (`application/src/session.rs`, around `start_export`, `snapshot_matches`, and `Completion::ExportFinished`). There is no export-owned snapshot-adopt transition. The React precedent does have one: `ExportContext.adopt()` accepts only its own committed edit and advances expected document/scene; `exports/pcb.ts` applies wiring and accepts protection only after packaging succeeds.

**Fix:** describe this as a private orchestration boundary that F8.2 must resolve, rather than saying existing Session semantics already cover it. Preserve order—own wiring commit, package creation, protection commit, then guarded delivery—and keep ordinary edits/scope changes invalidating the operation. If the current Session interface cannot express a safe private orchestration around ordinary commits, record the exact needed contract and seek approval before changing application APIs. Do not weaken stale-result validation.

### 4. Case STEP and generated-mechanical scope are conflated

F8.5 says authored and generated outputs follow the selected board/current physical instance. React's two operations have different data inputs. `exports/cases.ts::exportCase` uses `context.document` and `context.scene`, checking authored case readiness and building `caseAssembly(document, scene, boardId)`; it does not apply `effectiveCaseDocument/Scene`. `exportMechanical` explicitly applies those functions using `context.snapshot.instance`, requires exact current generation, and names the package with the instance suffix. The `ExportContext` still guards the CasePreviewContext (including board and instance) for both operations, but that alone does not mean authored STEP geometry is projected through the selected physical instance.

**Fix:** specify authored Case STEP as the selected board's saved authored bodies from the canonical document/scene (with the operation still rejected if its captured scope goes stale, if that matches the paired source behavior). Specify generated mechanical package as selected-instance effective document/scene and exact generation. Do not make the authored artifact instance-specific unless paired React evidence demonstrates that behavior.

### 5. Export-route/project-copy ownership is internally inconsistent

The plan correctly includes portable-copy UI in F8.1, but Implementation Decisions and F8.2 state “F2 owns ... control” / “portable copy/archive UI/service.” The pinned React Export route itself renders the `.boardstudio` button and embed-model checkbox (`Workbench.tsx`, Export branch), while the Project menu has another route to the same copy action. Treating all copy UI as F2-owned conflicts with both source and the task's stated Export workspace scope.

**Fix:** F8 owns presentation of the Export-route row and checkbox; F2 owns shared archive packing/storage and any Project-menu entrypoint. Keep the same provider/action underneath. This also keeps feature-private ownership and avoids assigning the route control twice.

## Verified reference behavior and useful constraints

- Export shows seven always-present design rows: KiCad board; Draft KiCad board; ZMK firmware; KiCad footprints; SVG board outline; DXF board outline; and Case STEP. The Case row label is conditional: “Authored Case STEP” when generated mechanical configuration is active, otherwise “Case STEP.” The generated mechanical package is an additional conditional row only when `generatedCase` is true. The portable-project section/button and optional “Embed used models” checkbox are also on this route (`app/src/ui/Workbench.tsx`, Export branch).
- Full KiCad readiness is selected-board PCB readiness plus `wiring.ready`; draft readiness is selected-board PCB readiness only. Firmware row readiness is `wiring.ready && controller && assignments.length`; footprints requires at least one definition; SVG/DXF use selected-board outline readiness. Case authored readiness and generated readiness are distinct. Disabled reason copy is coarse: firmware/full KiCad say “Review the layout and resolve controller wiring in PCB.” Case says “Add and generate case geometry in Case.” Other disabled rows—including footprints—fall through to “Review the board outline and layout findings.” Keep this source behavior if the goal is exact copy parity; do not imply each export has a unique precise blocker message.
- Export route return uses `lastDesignMode`; the Export trigger, `WorkflowReturn`, and Escape call `closeExport`, which restores that mode and preserves board selection. Review wiring and Review case are buttons on the route. There is no visible export progress, cancel control, or dedicated retry. `createProjectExporter.ts` queues work, asserts captured context after provider awaits, and retry is invoking the same action. Most TS export operations do not have an explicit abort signal; cancellation should be described as internal only where the Dioxus service actually supports it.
- React artifacts are: `${document.name}.boardstudio`; full/draft PCB handoff ZIP `${document.name}-pcb-handoff.zip` / `${document.name}-draft-pcb-handoff.zip`; ZMK ZIP `${document.name}-zmk.zip`; Case STEP `${document.name}[-<sanitized board>]-case.step`; keycaps STEP `${document.name}-keycaps.step`; generated mechanical ZIP `${document.name}[-<sanitized instance>]-mechanical.zip`. Outline/footprint filenames and MIME come from the Rust artifact reply. The package copy includes every board, all local assets regardless of checkbox, and optional bundled models selected by the checkbox.
- PCB workflow ordering in React is resolve wiring → accepted apply-electrical edit if not already applied → selected-board KiCad package and per-instance electrical records → pack ZIP → protect-electrical-handoff commit → deliver. Protection is after successful packaging; draft may preserve incomplete wiring/findings. `ExportContext` accepts its own preparation/protection document only through `adopt`, while unrelated document/scene/session/board/instance changes reject delivery.
- The Rust browser `CoreWorker` already exposes private `core`, `artifact`, and `archive` transport methods; Core and artifact request/reply contracts include firmware, electrical, prepare/finish export, footprints and outline operations. `Runtime` currently routes `StartExport` only to archive or generic captured case STEP (`RunExport`, `pack_archive`, `step_bytes`). Thus the provider/worker primitives exist for much of F8, while typed Runtime orchestration is missing; this does not by itself justify an engine API change.
- `Runtime::deliver` revokes its object URL on both its normal delayed cleanup and its error path. React `downloadArtifact` schedules URL revocation only after `anchor.click()`; if setup/click throws first, it does not reach the revoke timer. F8's stronger cleanup story is a reasonable Dioxus lifecycle target, but should be described as hardening rather than exact React behavior.

## Overall assessment

F8's task decomposition and “no public API change” posture are largely sound, and the UI format/readiness inventory is close. Correct the provider/asset/snapshot/scope ownership statements above before using F8.2/F8.4/F8.5 as implementation dependencies. The keycap STEP provider claim is the clearest false capability assertion; the archive's optional bundled-model embedding is a concrete missing behavior, not merely a UI migration.
