## Problem Statement

The Dioxus candidate can display the restored Layout layers, keycaps and generated footprint graphics, and it has a basic public 2D canvas with selection, drag previews, snapping and camera movement. Designers still cannot complete the React Layout workflow in Dioxus: navigate the full board/object hierarchy, create and configure matrices, place or directly edit components, author transformations and constraints, inspect and edit outline versions/features, navigate findings, or switch to the reference's functional Layout assembly viewer. The remaining work is a group of connected UI workflows around existing document/session services, not missing CAD algorithms.

## Solution

Build the complete Layout experience as small Dioxus presentation modules integrated through one Layout composition and one shared session/runtime seam. Keep durable geometry, validation, transaction grouping, history, outline semantics and snap geometry in the existing Rust authorities. Let the application session own selection, board scope, 2D navigation/camera and gesture lifetimes; Dioxus owns control visibility, focused item, and temporary form/drawing drafts. Use the existing renderer for 3D when its public browser adapter supports the Layout assembly scene; add only the narrow host/presentation adapter required to mount, resize, interact with and dispose that viewer. Do not port geometry algorithms into UI code or widen public Rust visibility to make the UI compile. Private presentation/module adapters using existing public providers remain ordinary implementation work.

Each slice below delivers a testable user path through the public Dioxus surface and existing APIs. The submodules may be implemented in parallel after their shared integration contracts are fixed. Merge in dependency order, retaining the React reference and its existing characterization evidence until the full flow has paired parity results.

## User Stories

1. As a keyboard designer, I want to see each board and expand its Layout objects, so that I can understand which geometry and parts belong to the active board.
2. As a keyboard designer, I want to browse matrices, rows, columns, keys, components, outline versions, outline bridges and findings in a contextual tree, so that I can reach the object I mean without searching the canvas.
3. As a keyboard designer, I want tree disclosure and selection to be separate actions, so that expanding a group does not unexpectedly change the active edit target.
4. As a keyboard designer, I want tree selection and canvas selection to remain synchronized, so that I can locate an object in either representation and continue editing it.
5. As a keyboard designer, I want tree grouping by rows or columns and visibility controls, so that large matrices remain navigable and the tree agrees with canvas layers.
6. As a keyboard designer, I want to select a matrix, row, column, key or individual component from the selection control and canvas, so that each edit applies at the scope I intend.
7. As a keyboard designer, I want Shift-click to select the rectangular key range from the current anchor and Ctrl/Cmd-click to toggle an item, so that multi-selection remains predictable across keyboard layouts.
8. As a keyboard designer, I want selection to filter to the active board and enabled matrix members, so that another board or hidden/empty cell cannot receive accidental edits.
9. As a keyboard designer, I want selection and 2D camera position to remain stable when I open and close panels or switch away from and back to Layout, so that the canvas does not lose my place.
10. As a keyboard designer, I want to create a matrix from a preset or custom row/column setup, so that I can start a layout with the same supported matrix defaults and definitions as React.
11. As a keyboard designer, I want to preview a new matrix or mirrored pair before placing it, so that I can position and cancel the proposed geometry without changing the saved document.
12. As a keyboard designer, I want arrow keys to nudge a pending placement by the active snap step and Enter to commit it, so that matrix and component placement is usable without a pointer.
13. As a keyboard designer, I want to add a standalone component from existing definitions and place it on the canvas, so that I can add supported hardware without leaving Layout.
14. As a keyboard designer, I want to select and drag keys, components, rows, columns or matrices with the same pointer semantics as React, so that direct manipulation stays familiar.
15. As a keyboard designer, I want pointer-down on an unlocked target to capture the pointer, a stationary pointer-up to remain a click, and drag initiation to match the characterized reference, so that click selection and drag do not conflict. React starts at non-zero world displacement, while the current Dioxus adapter has a 4 CSS px threshold; F3.3 must retain paired sub-threshold/stationary-click regression evidence and resolve this mismatch without weakening existing click, cancellation or pointer-budget gates.
16. As a keyboard designer, I want Shift/Ctrl/Cmd-modified pointer-down to select without beginning a drag, so that range/toggle selection is not converted into a move.
17. As a keyboard designer, I want Alt-drag to bypass grid and geometry snapping while normal drag uses the selected increment, so that I can choose precise free movement when needed.
18. As a keyboard designer, I want Escape, pointer-cancel, lost pointer capture and board/project switching to cancel an active gesture and restore committed geometry, so that unfinished movement never becomes an accidental edit.
19. As a keyboard designer, I want the final pointer-up sample included even if it arrives before the last animation frame, so that the committed location matches where I released the pointer.
20. As a keyboard designer, I want a complete drag to preview continuously and commit as one Undo step, so that history does not contain a step for each pointer frame.
21. As a keyboard designer, I want arrow keys to nudge selected parts by 0.1 mm and Shift+arrow to nudge by 1 mm, while ignoring typing fields and locked or constraint-driven targets, so that keyboard edits remain exact and safe.
22. As a keyboard designer, I want position and rotation fields to retain an editable draft until Enter, blur or an explicit cancel, so that partially typed numbers do not issue invalid or repeated document edits.
23. As a keyboard designer, I want to use stagger, column splay, origin picking, row offsets and direct position/rotation controls, so that I can shape matrix geometry using the same specialized controls as React.
24. As a keyboard designer, I want align commands to use the selected envelope bounds and selected anchor, while disabled for locked/constrained selections and rows spanning distinct splay, so that alignment does not violate placement relationships.
25. As a keyboard designer, I want to add, edit and remove offset or mirror constraints between same-board components, so that a driven part follows its source and the relation is visible and undoable.
26. As a keyboard designer, I want mirrored layout links and paired layout creation to expose their linked/unlink and local-replacement behavior, so that a split layout remains understandable and edits retain the intended side scope.
27. As a keyboard designer, I want grid snapping, geometry landmark snapping and optional envelope-gap snapping to use existing Rust interaction behavior, so that previews and committed placements agree with the established geometry rules.
28. As a keyboard designer, I want snap guides and their labels to appear while a snapped preview is active and clear on commit/cancel, so that I can see why an item moved to a particular location.
29. As a keyboard designer, I want the Layout camera to zoom around the pointer, pan with Space-drag, fit the board, fit the selection and respect supported zoom limits, so that I can navigate small and large designs.
30. As a keyboard designer, I want Fit board and Fit selection to include rotated component/keycap bounds, visible outlines and required UI-control clearance, so that fitted geometry is not clipped or obscured.
31. As a keyboard designer, I want 2D and 3D assembly to be separately selectable views, so that I can inspect the same canonical selected PCB board without changing document geometry.
32. As a keyboard designer, I want entering 3D to cancel pending 2D placement/gesture tools and returning to 2D to restore its camera and selection, so that the two view lifetimes do not corrupt each other.
33. As a keyboard designer, I want the Layout assembly viewer to expose its supported orbit, zoom, preset, fit and picking behavior, so that the reference's working 3D selector is functional rather than decorative.
34. As a keyboard designer, I want the assembly scene and selection to be scoped to the canonical selected board and theme (physical-instance reflection belongs to Case), so that split boards and their geometry are not mixed.
35. As a keyboard designer, I want renderer mount, resize, context-loss/error and unmount to settle and clean up browser resources, so that repeated view switches do not leak canvas listeners or GPU state.
36. As a keyboard designer, I want to open outline controls for Generated or a fixed outline version, so that I can edit the active board boundary and understand which version drives the board.
37. As a keyboard designer, I want to change automatic outline settings, regenerate an outline, copy/rename/delete a fixed version and switch the active version, so that alternate boundaries retain the accepted fixed-versus-linked behavior.
38. As a keyboard designer, I want to draw supported additions, cutouts and generated-outline bridges with a live draft preview, snap guides, finish, cancel and per-point undo, so that incomplete contours never become saved geometry.
39. As a keyboard designer, I want to edit outline feature dimensions and points, insert/remove points, and drag a point with a captured pointer, so that contour edits are direct, precise and recoverable.
40. As a keyboard designer, I want Alt to bypass outline snapping, arrow keys to move the selected point one snap increment, Shift+arrow to move ten increments, Delete to remove a supported point, and Escape to cancel its drag, so that outline editing is accessible and consistent.
41. As a keyboard designer, I want editing a generated outline into a manual shape to preserve its generated source and create a fixed copy where required, so that moving components continues to update only linked/generated geometry.
42. As a keyboard designer, I want linked refinements, protected gaps, bridges, cutouts and corner finishing to remain independently scoped to the correct outline version, so that existing outline contracts stay intact.
43. As a keyboard designer, I want findings grouped by severity with their affected object/outline and a live action to select or show that target, so that I can move from a warning to the relevant geometry.
44. As a keyboard designer, I want unresolved finding targets to remain readable without a dead navigation action, so that stale diagnostics do not mislead me.
45. As a keyboard designer, I want Layout edits, outline version changes and direct placement to participate in the existing preview/commit and Undo/redo history, so that every saved change can be reviewed and reversed.
46. As a keyboard designer, I want visibility layers and the Footprints toolbar/popover to retain F3a's presentation-only state, so that changing visibility never increments document revision or moves the camera.
47. As a keyboard designer, I want Layers and all inspector/tree controls to keep keyboard access, accessible names, visible focus and focus restoration when menus close, so that I can finish Layout tasks without a pointer.
48. As a keyboard designer, I want the Layout tree, editors and 2D/3D controls to remain usable at the supported compact widths, zoom levels and light/dark themes, so that required actions do not disappear on smaller screens.
49. As a maintainer, I want each Layout source responsibility and existing React regression case mapped to a Dioxus owner and public scenario, so that migration completion can be proven without claiming a whole shared React file migrated prematurely.
50. As a maintainer, I want each slice to have a public UI before/after proof and paired reference scenario, so that independently authored modules can integrate without hidden APIs or a single fake milestone gate.


51. As a designer, I want to add and select a geometry script, edit its name and Rhai source, choose Enable on Apply, and apply it through the existing engine, so that the supported React script workflow remains available.
52. As a designer, I want Apply unavailable for blank script text and core findings visible after application, so that incomplete source never appears to have run successfully.
53. As a designer, I want script drafts to reset at the same script/document change boundaries as React and applied changes to survive save/reload and Undo, so that editing source does not create a second execution or document authority.

## Implementation Decisions

- Split Layout UI responsibilities into private Rust/Dioxus modules for tree/read-model projection, canvas objects and pointer/key event adaptation, matrix/component authoring, placement/transform/constraint inspector, outline controls/drafts, findings navigation, and camera/assembly view switching. Keep a thin Layout composition responsible for shared scope, scene/snapshot inputs, view selection and the workbench's single session/runtime reference.
- Use the existing session as the sole owner of accepted read model, selection, active board, 2D camera, gesture preview/commit/cancel, and serialized mutations. Route edits through existing `EditCommand` and public session events. Session/project scope owns cancellation; component unmount alone must not cancel accepted saves.
- Keep per-field numeric text, matrix-setup form values, tree disclosure, active tool/menu, outline drawing points, selected outline control point and inspector tab in Dioxus presentation state. Submit validated typed intents only at the same React commit boundaries. Clear or restore drafts on Escape, scope change, switch, failure or successful commit as characterized.
- Keep geometry algorithms authoritative in core/application. Reuse existing matrix projection/membership, selection envelope, snapping, outline snap/edit, validation/findings and generated/refined outline scenes. UI may project read models and perform view-coordinate conversion, but may not duplicate geometry, constraint resolution, validation, or outline repair policy.
- Preserve reference interaction semantics: characterize React non-zero-world-delta drag against the existing Dioxus 4 CSS px threshold and port the reference with paired regression evidence; stationary pointer-up remains a click, including panel reflow; Ctrl/Cmd/Shift selection modifiers do not start a drag; Space+primary drag pans; Alt bypasses snap; Ctrl/Cmd+Z is Undo, Ctrl/Cmd+Shift+Z and Ctrl/Cmd+Y are Redo; arrow nudge is 0.1 mm and Shift+arrow is 1 mm; outline point arrows use one/ten snap steps. Text entry and editable controls keep their native keys.
- Treat the Layout 3D viewer as an explicit browser/renderer adapter boundary. Consume the already available semantic board/assembly scene through the public renderer integration; keep live GPU/camera state in the renderer and view preset/scope selection in the application session. If a needed scene or picking operation is private, first identify the narrow approved adapter contract; do not widen visibility or change shared scene schemas implicitly.
- Keep F3a layer/keycap/footprint code and its unchanged generator service under their already accepted contracts. Remaining F3 work may compose their controls and existing projected output, but must not duplicate that work in a second tree/canvas path.
- Keep styles and shared tokens in the existing design system. Do not introduce a new design system, add product-format fields for panel/tool state, or use a persisted document as a presentation store.
- Keep temporary React/Dioxus coexistence explicit in the F3 record: React remains the reference and fallback through paired acceptance; inventory rows retire only when each public Dioxus scenario and the full F9 cutover pass. No production entrypoint switch is part of F3.

## Testing Decisions

- Prefer the highest seam: browser scenarios through the real Dioxus UI and existing public services, paired with the same document/action trace in React. A UI test should assert user-visible selection, preview, saved geometry, revision/history, error/cancel state and camera/scene behavior rather than private component structure.
- Reuse existing `OutlineControlOverlay`, `Workbench`, `WorkbenchLayers` and `useWorkbenchNavigation` regression intent. Retain the current F3a public browser evidence as a prerequisite and add separate coverage for remaining behaviors; F3a's successful checks do not prove full Layout parity.
- For gesture traces, cover pointer capture, zero-motion click, first non-zero move, Ctrl/Cmd/Shift pointerdown, range/toggle selection, Alt snap bypass, lost capture, pointercancel, Escape, board/project switch, final pointer-up position, one-step drag Undo and presentation-only visibility.
- For authored edits, cover matrix and mirrored-pair create/cancel/commit, per-key/cell overrides, direct position/rotation, align guards, constraints, snap guide appearance/removal, invalid form values, stale revision and undo/redo grouping.
- For outline flows, cover generated versus fixed versions, version selection/copy/rename/delete, draft draw/point undo/cancel, insert/remove/drag with modifiers, linked refinements/protected gaps, save/reload, located finding navigation and stale target handling. Existing Rust geometry/outline tests remain authoritative and should not be replaced with UI calculations.
- For camera/view, cover pointer-centered zoom, pan, fit board/selection including rotated bounds, preserving 2D camera across view changes, correct canonical-board scene selection, 3D mount/resize/picking/orbit/fit/disposal, and errors/context loss where supported.
- Compare controlled desktop and compact captures in light and dark for the tree, active selection, matrix editor, outline draw/edit, findings, and 2D/3D states. Require no new axe violations and manual keyboard/focus checks; report actual assistive-technology coverage separately.
- Run affected application/core tests and the established Dioxus web build/browser checks for each integrated slice. The project currently has no paired React/Dioxus runner and no Dioxus production browser gate; those are known acceptance-enforcement gaps, not reasons to weaken the parity oracle. Follow `CONSTRAINTS.md` task-completion tier for final F3 acceptance.

## Out of Scope

- Reimplementing or changing matrix generation, geometry, snapping algorithms, outline generation/repair/refinement rules, constraint solving, validation, finding semantics, serialization, transaction/history, persistence, or renderer internals.
- New project/document formats, new geometry or constraint families, unsupported scripting capabilities, manufacturing-readiness changes, product redesign, or a new design system.
- F4 Parts catalogue/editor, F5 PCB authoring, F6 Keymap/Keycaps editing, F7 Case authoring and F8 Export workflows except for the minimum shared navigation/scene integration required to keep existing view switches coherent.
- Production entrypoint switch, React deletion, full frontend retirement, user-data cutover, API visibility widening, shared contract changes, or unreviewed performance/accessibility/visual gate changes.

### Parallel ownership and integration seams

Use private UI modules, not new crates and not a second session store. Suggested ownership map (specific source paths belong here, not in Implementation Decisions): tree/navigation and selection projection; canvas object rendering and pointer/key adapters; matrix/component setup and placement forms; transform/constraint inspector; outline controls/drafts; findings/inspector routing; camera/view/assembly mount. These map to React responsibilities in `tsx-inventory.json` and may be owned independently.

Before parallel implementation, agree a small shared UI contract: a read-only `LayoutReadModel` projection of accepted document/scene/session selection/camera; a typed `LayoutIntent` translated once into existing session events/edit commands; an explicit draft/view-scope key; and callbacks for select, navigate, mutate, cancel, fit and switch view. The composition owns these adapters, current board/snapshot identity, stale-result rejection and tool cancellation. Child modules own only local display/drafts and receive typed values/callbacks. Do not expose mutable copies of ProjectDoc or have modules submit bespoke serialized engine requests.

F3.2, F3.4 and F3.5 can be authored concurrently after F3.1 publishes that contract; F3.3 can be authored concurrently with F3.4 if they share the snapped-point/placement interface rather than implementing snap policy separately. F3.6 implements the Layout consumer beside the F7-owned common viewer after its contract is inspected; do not create a competing renderer adapter. Integrate and verify one complete public path per slice; the parent F3 milestone is the aggregate, not a hidden all-at-once blocker.
