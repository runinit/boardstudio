# Parts create-component capability receipt — 2026-10-02

This receipt records the narrow start evidence for draft child 13. It does not claim the feature is implemented or public-browser accepted.

## Reference behavior

The React Parts library renders a `New custom component` button in its catalogue action area (`app/src/ui/PartsLibrary.tsx:34–42`). Workbench always passes its create callback (`app/src/ui/Workbench.tsx:1283`), so this button remains independent of VIK-module `modulesPending`/`modulesError` (`PartsLibrary.tsx:30–31`). Its action creates `ui-${crypto.randomUUID()}` where supported, with the existing `Date.now().toString(36)` fallback (`app/src/ui/workbenchGeometry.ts:17`), and a project-owned custom definition named `Custom component ${document.definitions.length + 1}`, kind `custom`, courtyard corners `(-5,-3)`, `(5,-3)`, `(5,3)`, `(-5,3)`, and no pads. It submits one replacement edit, clears search, selects the new definition, closes assembly mode and transitions panels (`app/src/ui/Workbench.tsx:759–777`). The existing Name editor then appears in the right Inspector for that accepted non-generator project definition (`PartsInspectorPanel.tsx:71–73`).

## Current Dioxus capability

- The Parts library receives the accepted snapshot, scope, query signal, selection signal, and a panel-selection callback. It has a loaded-catalogue success state but no `New custom component` action or create callback (`web/src/presentation/parts.rs`, `web/src/presentation/parts_workspace.rs`).
- Today, Dioxus `PartsLibraryPanel` returns early for catalogue loading/error before rendering action controls (`web/src/presentation/parts.rs:100–116`). This differs from React's always-rendered custom-create action; issue 13 explicitly owns keeping that action available independent of catalogue load state, rather than treating load/error as an accepted disabled state.
- The selected project-owned non-generator definition already mounts the Name editor in the Inspector (`web/src/presentation/parts.rs`). Issue 12 owns its exact draft/commit behavior and is a required child dependency for the complete create-then-rename workflow.
- The crate already dispatches accepted edits as `Event::Edit` using `Runtime::operation()` and `Runtime::submit()`. Issue 12 exercises this path through an accepted `ReplaceDocument` command and normal Session/Core history. The create action needs only a private Parts-owned proposal/dispatch path; it does not require a new public Core command or generic Runtime facade.
- Runtime's private `browser_uuid()` helper uses Web Crypto `crypto.randomUUID()` (`web/src/runtime.rs:58–78`) and `Runtime::create_new_keyboard` uses it for project, board and outline identity (`web/src/runtime.rs:238–277`). It is not an exposed Parts API. The feature must preserve React's `ui-` prefix, prove accepted-project collision avoidance and exercise the package-supported ID path; any reuse should stay private to the web crate. Do not add a public Core command or API.
- The current Dioxus catalogue groups Custom definitions, uses shared selected/query signals, and the shell's `on_select` callback already handles the existing Parts panel transition. New-component behavior can remain in the Parts feature module and use those private inputs.
- `Runtime::observe_operation` returns an operation-correlated terminal slot (`web/src/runtime.rs:231–236`, `web/src/operation_outcomes.rs`). The create child can use this feature-owned seam to gate UI reconciliation on its own accepted terminal result. It must also guard the captured session/document scope and Parts view generation so an abandoned view, owner switch or later user query/selection cannot be overwritten.
