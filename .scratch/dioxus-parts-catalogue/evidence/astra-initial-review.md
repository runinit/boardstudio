## Material findings

1. **All three first tickets incorrectly claim INT.1 provides their workspace contract.** INT.1's reviewed extraction supplies Library/Objects/Inspector in the page crate, not Parts, PCB, Keymap mounts, shared canvas callbacks or new feature read models. Keep INT.1 as the existing parent start edge, but replace the parenthetical blocker claims and each dispatch note with a coordinator-owned, feature-specific proof: actual private mount, accepted document/scene inputs, current scope, selection/edit callbacks and owner files. F5.1a also needs a private PCB canvas/controller; the Layout component and placeholder are not an already reviewed PCB API. Do not block everything on INT.2 automatically: these existing local read/edit paths can be bounded private composition. Add a specific INT.2 join only if the chosen implementation actually consumes that shared request/assets seam.

2. **F4.1 source coverage is incomplete and its catalogue facade is unspecified.** The reference Workbench combines `ergogenCatalogue()` with `importedPartDefinitions()` and then project-definition overrides; it does not simply list definitions already in the current document. `partsCatalog.ts` also excludes the legacy `infused-kim/nice_nano_pretty` duplicate and assembly placement snapshots while preserving current assigned choices where relevant. Require that merge, precedence, labels, aliases and exclusions explicitly. Current `assets/layout-generators.js` exports only `isErgogen` and `render`; it is not a catalogue-list API. The already packaged `layout-generators/src/index.js` does contain the existing `catalogue()` export. A private page adapter may import that existing implementation and pair it with the imported static snapshots, with real asset packaging/provenance and typed deserialization. Prove the selected path before dispatch; do not claim a public Rust catalogue facade exists, duplicate generator algorithms, or widen library visibility.

3. **F4.1b misses the actual assembly source and overpromises retry controls.** The reference PartsLibrary receives the eight `matrixPresetDefinitions` entries from `assemblyCatalog.ts`; describing only “saved assemblies” from the accepted document omits the real reference rows. Cover those bundled presets and their actual names/selection; include additional saved entries only if a real supported reference path is identified. The module catalogue loads `imported-modules.json`, merges project snapshots by ID with project precedence, groups rows and selects the first variant; the detail surface handles variant switching. Include this exact source path and meaningful read-only selected-definition/assembly/module details, not just an arbitrary selected heading. Full editors/previews stay with later owners. `PartsLibrary` renders module loading/error and the existing no-match message, but has no explicit Retry button. `useModuleCatalogue` retries failed loading on re-entry through its active lifecycle. Preserve that supported behavior; remove an invented retry control and ordinary-definition source states that are not the reference UI. A new asynchronous packaging failure may use truthful existing error feedback, not be misrepresented as empty data. Use Luna High for the new module/asset async lifecycle, Medium only after a proven adapter is consumed.

4. **F5.1b's view-scoped visibility wording risks a reference behavior change.** React Workbench has one transient `hiddenLayers` set shared by Design/PCB and retained through board/workspace changes; it has a separate module-layer set. Do not reset host visibility on every board/view or introduce isolated PCB-only semantics under “scoped to the active PCB view.” Name the actual lifetime and shared controls while retaining stale-scene rejection and module ownership. Specify reference layer derivation: dynamic footprint layers with front/back mapping plus Edge.Cuts, Courtyards, Pads, Holes and References; the copper/pad/drill visibility interaction is important. The current FootprintGraphics draws generator graphics for Layout and is not the complete host PCB projection. A first render ticket and subsequent toggles remain valid, but the first ticket must prove real accepted-scene/definition/retained-generator sources, face transforms and canvas mount. Do not use the mere existence of ArtifactRequest::PreviewBoard as proof of the reference rendering path.

5. **F6K.1a needs explicit legacy/default and selection semantics and High ownership.** `createKeymapWorkspace` supplies a virtual Base map when the document has no layers, resolves active layer by stable ID with first-layer fallback, gives absent non-base bindings transparent semantics, and uses legacy base bindings (`keyBinding`) with key-press/transparent/none interpretation. “Boards without keymap data have explicit states” must not turn an ordinary legacy board into an empty/no-keymap screen. Key membership includes switches and the supported direct matrix key parts, while excluding matrix companions. Reference selection highlights the shared selected-part set and chooses keys through the existing selection controller; the searchable control is a native Selected key select whose options include reference and binding title. Require appropriate read-only selected context without implementing F6K.2's binding editor. This is new selection/scope/canvas state, so author/verifier should be Luna High now, not Medium unless a future proven callback makes the packet mechanical. Preserve the F3.1 acceptance join on the parent and all child acceptance that depends on the real handoff; fixture preparation cannot close it.

6. **F6K.1b incorrectly restricts renaming to non-base layers.** In `KeymapPanel`, Layer name applies to the selected layer including the first; only Remove layer is absent for the base layer. Rust RenameLayer also permits base rename; RemoveLayer protects only the first. Adjust title/outcome to add layers, rename any permitted layer, and remove only non-base layers. Record the source-backed reconciliation of the parent shorthand rather than implementing a regression. Preserve rename-on-blur, 32-layer add limit, field maximum length, ID-based fallback and existing core validation/error behavior. This can stay Medium if it consumes a proven edit callback and ID-selection controller, otherwise High for any new edit/failure coordination.
